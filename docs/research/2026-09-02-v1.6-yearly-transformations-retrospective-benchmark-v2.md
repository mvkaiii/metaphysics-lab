## Method

The benchmark fixes the methodological problems found in v0/v1 by deriving both arms from the same actual branch pipeline.

### Baseline arm

1. Resolve the actual Project forecast context for the historical target year.
2. Remove only `ziwei.yearly.transformation_layer` from a deep copy of the forecast context.
3. Run the existing structural interpretation.
4. Run the existing Phase 3 evidence ranker.
5. Run the existing EFA attribution bundle.

This reproduces the old frozen yearly evidence boundary without reimplementing the old mappings.

### Candidate arm

Use the same forecast context with the new yearly `transformation_layer` retained, then run the same structural interpretation → Phase 3 ranking → EFA path.

### Outcome separation

Prediction generation and outcome adjudication are separate scripts:

- `tools/v16_yearly_transformations_benchmark_predictions.py` contains only chart inputs, years and case identifiers; it has no historical event outcomes.
- `tools/v16_yearly_transformations_benchmark_adjudicate.py` reads the frozen prediction artifact and only then applies the existing verified-event oracle.

This is still retrospective research because the implementation hypothesis was motivated by known historical gaps, but outcomes do not enter evidence formation.

## Important precision finding

The Candidate adds 52 child families across the nine cases. Only three can be positively linked to already-verified components under the fixed oracle. Forty-nine cannot be labeled wrong from silence because the historical ledger is not a complete census of every possible domain/event family.

Therefore the correct conclusion is **not** “+3 hits and no downside.” The correct conclusion is:

> Yearly transformations improve retrospective verified-family coverage on three components while materially expanding the child universe. The precision cost of that expansion is unresolved with current historical data.

This is exactly why the result cannot authorize promotion without prospective evaluation.
