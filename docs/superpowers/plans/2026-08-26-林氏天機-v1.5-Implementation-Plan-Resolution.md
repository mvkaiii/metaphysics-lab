# 林氏天機 v1.5 Implementation Plan｜Self-Review Resolution

本文件解決 `2026-08-26-林氏天機-v1.5-Implementation-Plan.md` self-review 中唯一尚未釘死的 runtime integration point；後續執行以本 resolution 覆蓋原 plan 的模糊描述。

## Phase 1 exact runtime files

已由目前 repo 實際程式確認：

- `engine/distribution/runtime.py`
  - `dispatch()` 是 portable runtime action dispatcher。
  - `runtime_info()` 暴露 `supported_actions` 與 capability manifest。
  - Phase 1 新增 `resolve_query_anchor` / `lock_prospective_forecast` 時，dispatch route 在此加入。
- `engine/distribution/constants.py`
  - `SUPPORTED_ACTIONS` 是 action name registry。
  - Phase 1 新 action 必須在此加入，並由既有 runtime-info tests 驗證。
- `engine/distribution/manifest.py`
  - `load_capabilities()` 聚合 capability registries。
  - 若 v1.5 prospective/evidence actions 需要正式 capability metadata，新增 `engine/distribution/capabilities.py` 並把 `distribution/capabilities.py` 加入 `_REGISTRY_FILES`；不得把 action maturity metadata 硬塞進 `runtime.py`。
- `engine/distribution/case_pack.py`
  - 現有 `update_case_record()` / `_update_case_record()` 已接受標準 JSON tracking entry、支援 06/07/08 progressive append，且 front matter 不要求 forecast-specific fields。
  - Phase 1 **預設不修改** `case_pack.py`。先以測試證明 v1.5 locked forecast payload 可透過現有 API round-trip；只有測試證明 Case 1.1 無法表達時才停止並提出 schema/contract 設計變更，不可臨場擴張修改。

## Validation implication

- 新 action 名稱與 dispatch 必須同時通過 modular runtime 與 generated bundle parity。
- capability metadata 若新增，必須由 `runtime_info()` 透過 `manifest.py` 讀出，不建立第二套手寫 metadata source。
- Case Schema 1.1 round-trip 先測現有 generic record API；測試通過即禁止為 v1.5 額外改 front matter/schema。

本 resolution 不改 v1.5 架構、不改 Phase 順序、不改權重政策，只消除 implementation plan 的檔案定位歧義。
