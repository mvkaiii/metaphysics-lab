# 林氏天機 v1.5 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 在不改寫 v1.4.0 baseline、不用 Kai 2026 已知結果調參的前提下，建立「林氏天機」的 prospective forecast evidence / interpretation 架構，讓流年、流月、流日、流時、運限、Historical Calibration 與問事當下各自有明確證據角色、可否證邊界與使用者語言規範。

**Architecture:** 保留 `engine/distribution/forecast.py` 只負責 deterministic forecast context；新增獨立的 prospective governance、evidence normalization、eligibility/ranking、historical personalization、interpretation contract 與 prospective evaluation 模組。Phase 0 先獨立修 blind-lock validator；Phase 1～6 逐步建立 v1.5 主體，每 Phase 必須 RED→GREEN、focused tests、full regression、distribution parity 與必要 qualification 全綠才可進下一 Phase；Phase 6 後再做 sandbox「預測驗證測試」。

**Tech Stack:** Python 3.9+、stdlib dataclasses / datetime / zoneinfo / hashlib / json、現有 `engine.distribution` portable runtime、unittest/pytest、現有 AI distribution builder、GitHub Actions qualification workflow。

**Spec:** `docs/superpowers/specs/2026-08-26-林氏天機-v1.5-Prospective-Forecast-Evidence-Architecture-設計.md`

## Global Constraints

- Baseline 是 Metaphysics Lab v1.4.0 release commit `9065fec2a71a1ba07c8e6b7ef2106599d2d28a85`；既有 release / tag / legacy forecast 不改寫。
- `main` 目前 tree 必須保持與 v1.4.0 release tree `932b9bb1ac051ffe3ba00b5aff165d264b6eb480` 相容；兩筆 accidental noop/cleanup commit 只留歷史，不得 force-reset。
- Kai 2026 已知事件只可作 failure reproduction、cutoff / contamination fixture、legacy baseline preservation；不得調 weight、event mapping、threshold 後再用同一事件證明新版較準。
- v1.5 先維持 Case Schema 1.1；除非獨立證明現有 record block 無法安全表達 contract，否則不得升 Case Schema。
- 不提升任何既有 `experimental` capability maturity；maturity promotion 必須另案。
- 不改 Bazi / Ziwei 原始排盤公式。新 evidence/ranking 只能消費既有 deterministic output。
- `forecast.py` 不做命理解讀、不產生使用者自然語言。
- Target period owns event attribution；粗時間層只能 modifier，不能單獨生成較細時間層 concrete event。
- Historical Calibration 只 narrowing / re-weighting 已有候選，不得生成 unsupported domain。
- Strength / score 不得對外冒充事件機率。
- 一般對話只用自然台灣繁體中文；禁止晶晶體與內部 field / runtime plumbing 外洩。
- 一般使用者即使詢問演算法，只提供高層可稽核理由，不公開精確 weight / threshold / feature vector / gate formula / anti-gaming mechanics。
- 每個正式 prospective claim 在 lock 前必須有固定時間窗、`matched_if`、`not_matched_if`、cutoff、method version 與 evaluation eligibility。
- Phase Gate 是硬閘門：該 Phase 只要 focused / full regression / distribution parity / relevant qualification 任一失敗，不得開始下一 Phase。
- 每個 Phase 以獨立 PR 為預設；驗證完成後停在 merge-ready，除非使用者明確授權合併。

# Phase Gate Protocol（所有 Phase 共用）

每一個 Phase 依固定順序執行；不得把「full suite 最後再跑」當替代方案。

1. **Pre-flight exact base**：記錄 base SHA、tree SHA、當前 full regression test count、三個既有 qualification gate 狀態。
2. **RED**：先加入只針對該 Phase requirement 的測試，確認失敗原因只有預期缺口；舊測試應維持通過。
3. **Minimal implementation**：只做使 RED 轉綠的最小實作，不順手改 metaphysics formula / maturity / unrelated schema。
4. **Focused GREEN**：只跑該 Phase 新增測試＋直接相依既有測試。
5. **Distribution parity**：若 portable runtime surface / docs 有變，執行 `python tools/build_ai_distribution.py` 與 `--check`，確認 modular runtime 與 `dist/ai/metaphysics_lab.py` parity。
6. **Qualification replay**：只要該 Phase 消費或路由 Bazi/Ziwei flow-time context，就重跑：
   - `python tools/build_bazi_flow_time_qualification.py --check`
   - `python tools/build_ziwei_flow_time_qualification.py --check`
   - `python tools/build_ziwei_month_boundary_qualification.py --check`
7. **Full regression**：`python -m pytest -q` 必須全綠；不可只報 focused tests。
8. **Compile / clean-tree**：`python -m compileall engine tests tools`；builder/check 後 working tree 必須乾淨。
9. **Phase evidence**：PR body 記錄 RED exact head/run、GREEN exact head/run、test count、artifact digest、changed-file boundary。
10. **Merge gate**：停在 merge-ready，等待明確授權；下一 Phase 以已合併 main 為 base，避免 stack 隱性相依。

若 GitHub Actions workflow 尚未包含新增 focused test，Phase 自己要同步 workflow focused list；但不得降低 full regression gate。
