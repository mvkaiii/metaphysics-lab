- 狀態：Design Approved / Pending Written Spec Review

- Base main SHA：`6c74579c8b3d22ca430f65f483394021b49303f6`

---

## 1. 決策摘要

Phase 4 正式採用方案 A：

> **獨立 Historical Personalization Layer**

資料流固定為：

```text
Deterministic Chart / Forecast Context
        ↓
Phase 3.5 Structural Interpretation
        ↓
EvidenceFeature
        ↓
Phase 3 Eligibility / Ranking
        ↓
Immutable Unpersonalized Base Ranking
        ↓
Phase 4 Historical Personalization
        ↓
Personalized Ranking
        ↓
Phase 5 Interpretation Contract
```

Phase 4 不把歷史事件轉回當期 EvidenceFeature，也不把 personalization 寫進 `evidence_ranker.py` 的 base ranking policy。

正式 personalization profile identity 固定為：

```text
lin_tianji_historical_personalization_v1-exp
```

Phase 3 base ranking authority 維持：

```text
lin_tianji_rank_v1-exp
```

Phase 4 的核心責任只有：

1. 讀取已 finalized、machine-readable 的 Historical Calibration records；
2. 對既有 base domains 做有限、可追溯的個人化排序修正；
3. 對 base event-family candidates 做有限、可追溯的偏好排序；
4. 永遠保留 base ranking 與其 digest，不回寫、不覆蓋、不重新計算 Phase 3 truth。

---

## 2. 問題定義

Phase 3.5 已解決 cold-start 的主要缺口：完全沒有歷史事件資料時，deterministic chart / forecast context 仍能形成 structural evidence，再由 Phase 3 ranker 產生非空、可重現的 base ranking。

因此 Phase 4 現在可以把歷史資料放回正確的位置：

```text
current-period evidence
→ base ranking
→ historical personalization
```

而不是：

```text
history
→ invent current signal
```

Phase 4 要回答的是：

> 當同一個命主過去已做過盲測校準時，哪些「原本已由當期命盤開啟」的領域與事件型態，在這個命主身上較值得前置、較值得保守、或目前證據不足？

它不回答：

- 哪個事件一定會發生；
- 哪個 domain 可以憑歷史紀錄被新增；
- 歷史事件能不能取代本命／流年盤；
- 某個事件的機率是多少。

## 3. 核心 invariants

### 3.1 Base Ranking Immutability

Phase 4 必須接收一份已完成的 Phase 3 ranking snapshot，並驗證其 `ranking_digest`。

Phase 4 不得修改：

- `policy_version`；
- `target_scope`；
- `evaluated_features`；
- `opened_domains`；
- base domain set；
- base `ordinal_score_scaled`；
- base `allowed_specificity`；
- base `event_families` candidate set；
- `ranking_digest`。

輸出必須保存：

```text
base_policy_version
base_ranking_digest
```

而不是生成一個冒充 Phase 3 ranking 的新 `ranking_digest`。

### 3.2 No Signal Creation

歷史資料不得：

- 新增 base ranking 沒有的 domain；
- 新增 base EvidenceFeature 沒有支援的 event family；
- 建立新的 Bazi / Ziwei structural relation；
- 改寫當期 strength class；
- 把過去事件當成當期 timing trigger；
- 把過去的某年結果搬成現在的 target evidence。

### 3.3 Specificity Ceiling Authority

Phase 3 的 `allowed_specificity` 是正式硬上限。

Phase 4 v1：

- 不提高 specificity ceiling；
- 不降低或改寫 formal ceiling；
- 不因歷史吻合就把 `event_family` 升成 `concrete_event`；
- 不因個人化支持度高就生成 highly-specific event。

Phase 5 若要用更保守語言，可以選擇低於 ceiling 的表述，但 Phase 4 不改正式 ceiling truth。

### 3.4 No-history Identity / No-op

以下任一狀況成立時，Phase 4 必須是 deterministic no-op：

- 沒有 Historical Calibration records；
- `historical_calibration_status == uncalibrated`；
- 只有 contaminated records；
- 只有 `cannot_recall` / unscorable records；
- 沒有任何可安全對應到當前 base domain 的紀錄；
- 單一 domain / event family 的有效樣本未達最低門檻。

No-op 時：

- personalized domain order 與 base order完全相同；
- 每個 historical modifier 為 0；
- base digest 完全不變；
- 仍產生 deterministic `personalization_digest` 供 audit。

### 3.5 Non-probabilistic Semantics

Phase 4 的所有數值都是 deterministic ordinal adjustment，不是概率。

禁止輸出：

```text
career_probability
confidence_probability
78% likely
prediction_probability
```

允許：

```text
historical_modifier_scaled
historical_support_class
personalized_ordering_score_scaled
```

這些欄位只代表排序修正。

## 4. 正式資料來源邊界

### 4.1 Phase 4 v1 可使用

只有目前 `finalize_historical_calibration()` 已產生並寫入 `05_驗證事件紀錄.md` 的：

```text
record_type == historical_calibration
```

且只讀 machine-readable 結構欄位。

主要可用欄位包括：

```text
record_id
calibration_id
origin
blind_prediction.role
blind_prediction.predicted_flow_year
blind_prediction.primary_domains
blind_prediction.event_family
blind_prediction.blindness_status
evaluation.verification_state
evaluation.domain_status
evaluation.event_form_status
evaluation.timing_status
evaluation.offset_flow_years
evaluation.boundary_ambiguity
```

### 4.2 Phase 4 v1 明確不使用

不得把以下內容餵入 personalization scoring：

- `user_confirmed_actual.actual_event` 自由文字；
- `blind_prediction.hypothesis` / `interpretation_text` 自由文字；
- 一般 verified-event records；
- `06_流年追蹤紀錄.md`；
- `07_問事追蹤紀錄.md`；
- `08_重大決策紀錄.md`；
- 使用者偏好推測；
- 研究筆記；
- 未 finalized 的 calibration 草稿；
- 已知 Kai 2026 outcome 作為 tuning ground truth。

自由文字可以保留於 Case audit，但 Phase 4 v1 的結果與 digest 不得因 `actual_event` 或 hypothesis wording 改變。

### 4.3 為何不讀自由文字

現有 Historical Calibration finalize 已經把：

- verification result；
- timing result；
- domain match；
- event-form match；
- blind / contaminated state

正式結構化。

因此 v1 沒有必要再用 AI 重新解讀事件描述。這可以避免：

```text
事件文字
→ AI 自由分類
→ 反向製造個人化訊號
```

## 5. Historical Record Eligibility

每筆 historical record 進入 Phase 4 前必須先正規化與分類。

### 5.1 必要條件

可進 scoring 的 record 至少必須：

1. `record_type == historical_calibration`；
2. `blind_prediction.blindness_status == blind`；
3. `evaluation.verification_state != cannot_recall`；
4. 對應 scoring dimension 不是 `unscorable`；
5. record 結構符合 finalized Historical Calibration contract；
6. `record_id` 可追溯且不可重複。

不符合者不得偷偷丟棄，必須記錄 exclusion reason。

### 5.2 Contaminated records

```text
blindness_status == contaminated
```

只進 audit count，不得影響 domain modifier、event-family preference 或 ordering。

### 5.3 Control records

`role == control` 的紀錄在 Phase 4 v1：

- 保留作 calibration-quality audit；
- 不直接給任何特定 domain 加分／扣分；
- 不用 control 的 domain label 開啟或壓低某個 current domain。

原因：control 的主要角色是測試低活化年份與 false-positive tendency，不應被粗暴轉成 domain-specific 個人化權重。

Control-based global damping 留待後續有足夠 prospective evaluation 證據再設計，v1 不做。

### 5.4 同一年重複 calibration

同一 Case 可能在不同 calibration session 再次測到同一 flow year。

為避免知道結果後重測造成灌票，Phase 4 v1 採：

> **同一 `predicted_flow_year` 的第一筆有效 blind record 才有 scoring authority。**

後續相同年份紀錄：

- 保留 audit；
- 標記 `duplicate_reference_year`；
- 不再計入 modifier。

「第一筆」以 `05_驗證事件紀錄.md` 的 canonical append order 為準。Runtime 若直接接收 structured records，必須保留 Case record order；輸入順序屬於 source provenance 的一部分。

## 6. Canonical Identity 與 Legacy Compatibility

### 6.1 Current authority

Phase 3.5 正式 domain identity 來自：

```text
lin_tianji_domain_v2-exp
```

例如：

```text
career
finance
peers
expression
learning_support
partnership
health
home_property
...
```

Phase 4 不能用模糊文字相似度把歷史紀錄硬配到這些 IDs。

### 6.2 Closed legacy alias registry

既有 Historical Calibration v1 測試／紀錄存在人類可讀 label，例如：

```text
工作／職責
```

因此 Phase 4 可新增一個**版本化、封閉式 legacy normalization registry**。

規則：

1. canonical ID exact match 永遠優先；
2. legacy label 只能透過明確列在 registry 的 exact alias 對應；
3. 不使用 fuzzy matching、embedding、LLM semantic guess；
4. 每新增一個 alias 必須有明確 contract evidence + regression test；
5. 未列入 registry 的 label 標記 `unmapped_domain`，不得自行推測。

v1 至少需覆蓋現有正式測試契約已存在的：

```text
工作／職責 → career
```

其他 legacy domain alias 不得在沒有正式依據時自由補造。

### 6.3 Event-family legacy labels

Event family 的舊人類可讀描述通常比 domain 更模糊，例如：

```text
職務或責任結構改變
```

它可能同時接近：

```text
role_change
responsibility
career_role
friction_or_change
```

因此 Phase 4 v1 **不對 legacy event-family 自由翻譯**。

Family-level personalization 只接受：

- exact canonical event-family ID；
- 或未來明確加入 versioned closed alias registry 的無歧義 mapping。

未能安全 normalization 的 legacy family 仍可保留 domain-level evidence，但不得做 family-specific modifier。

## 7. Ambiguity Guardrails

### 7.1 Multi-domain historical prediction

如果同一 historical blind prediction 同時列出多個 domain，而 evaluation 只有一個 aggregate `domain_status`：

```text
primary_domains = [A, B]
domain_status = matched
```

無法知道 A、B 哪一個真正命中。

因此 Phase 4 v1：

> 只有 normalization 後**恰好一個 domain**的 high-activation record 可以進 domain-specific scoring。

多 domain record：

- 保留 audit；
- 標記 `ambiguous_multi_domain`；
- 不拆票、不把同一 matched 狀態同時灌給多個 domain。

### 7.2 Multi-family historical prediction

同理，若：

```text
event_family = [A, B, C]
event_form_status = matched
```

不能知道是哪個 family 命中。

因此 family-specific scoring 只接受 normalization 後**恰好一個 event family**的 record。

多 family record 仍可在 domain 條件明確時支援 domain-level scoring，但不進 family-level scoring。

## 8. Domain Personalization Policy v1-exp

### 8.1 Domain evidence units

只使用 eligible high-activation record 的 `evaluation.domain_status`：

```text
matched     → +2
partial     → +1
missed      → -2
unscorable  → excluded
```

這是 ordinal evidence unit，不是命中率。

### 8.2 最低樣本門檻

單一 domain 至少需要：

```text
2 eligible historical records
```

才可以產生非零 modifier。

只有一筆 record：

```text
historical_modifier_scaled = 0
historical_support_class = insufficient
```

避免一個人生事件就永久改變命主模型。

### 8.3 Aggregate support → bounded modifier

對同一 domain 的 eligible records 加總 support units：

```text
support_units >= +3   → historical_modifier_scaled = +2
support_units +1..+2  → historical_modifier_scaled = +1
support_units == 0    → historical_modifier_scaled = 0
support_units -1..-2  → historical_modifier_scaled = -1
support_units <= -3   → historical_modifier_scaled = -2
```

Modifier cap 固定：

```text
-2 <= historical_modifier_scaled <= +2
```

這個 cap 刻意保持小於或等於 Phase 3 中一個 stable coarse modifier 的量級，不允許歷史資料蓋過 current target evidence。

### 8.4 Support class

對外 audit class 固定為：

```text
insufficient
contradicted
mixed
supported
strongly_supported
```

建議 mapping：

```text
eligible_count < 2       → insufficient
modifier == -2           → contradicted
modifier == -1 or 0      → mixed
modifier == +1           → supported
modifier == +2           → strongly_supported
```

`mixed` 不代表 50% 機率，只表示目前結構化歷史證據沒有形成明顯正向／反向排序修正。

### 8.5 Personalized ordering score

每個 base domain 計算：

```text
personalized_ordering_score_scaled
    = base_ordinal_score_scaled
    + historical_modifier_scaled
```

這個欄位：

- 只用來排序；
- 不回寫 `ordinal_score_scaled`；
- 不叫 probability；
- 不寫回 Phase 3 ranking。

排序 tie-break：

1. `personalized_ordering_score_scaled` descending；
2. `base_rank` ascending；
3. `primary_domain` lexical ascending。

因此 modifier 相同時，Phase 3 原排序仍具有優先權。

## 9. Event-family Personalization Policy v1-exp

### 9.1 Eligibility

Family-specific evidence 必須同時滿足：

1. record 已通過 general eligibility；
2. `role == high_activation`；
3. normalization 後恰好一個 domain；
4. normalization 後恰好一個 event family；
5. historical domain 與 current base domain exact identity 相同；
6. historical family 已存在於 current base domain 的 `event_families` candidate set；
7. `event_form_status != unscorable`。

### 9.2 Family evidence units

```text
matched     → +2
partial     → +1
missed      → -2
unscorable  → excluded
```

同樣至少 2 筆 eligible records 才形成 active family preference。

### 9.3 不新增、不刪除 candidate

Phase 4 v1 不改 base event-family set。

輸出保留：

```text
base_event_families
personalized_event_family_order
preferred_event_families
deprioritized_event_families
```

但：

```text
set(personalized_event_family_order)
== set(base_event_families)
```

不得從歷史事件新增 family，也不得永久刪除 base candidate。

Phase 5 可以優先使用 `preferred_event_families` 來組織文字，但仍受 Phase 3 specificity ceiling 約束。

## 10. Timing Calibration 在 Phase 4 v1 的角色

Historical Calibration 已提供：

```text
timing_status
offset_flow_years
boundary_ambiguity
```

Phase 4 v1 只把 timing 結果列入 audit summary，不用它：

- 把當期 signal 平移一年；
- 修改 target period；
- 修改 Calendar Resolver；
- 改流年／流月／流日歸屬；
- 生成 adjacent-year evidence。

原因：歷史 timing bias 若直接用來移動 current forecast context，就會越過 personalization 邊界，重新變成 evidence generation。

Timing-based prospective correction 必須等 Phase 6 有正式 outcome evaluation 後另立 spec。

## 11. Calibration Status Gate

Case 既有狀態：

```text
uncalibrated
basic
calibrated
```

Phase 4 v1 規則：

### uncalibrated

強制 no-op。

即使 Case 裡已有 1–2 筆 historical records，也只做 audit，不形成 modifier。

### basic

允許依本 spec 的最低樣本門檻套用 personalization。

### calibrated

使用相同 v1 policy；不因 state 名稱較高就提高 modifier cap 或 specificity。

`calibrated` 的未來多輪 qualification 規則不在 Phase 4 v1 自動升級。

```text
{
  "profile_version": "lin_tianji_historical_personalization_v1-exp",
  "base_policy_version": "lin_tianji_rank_v1-exp",
  "target_scope": "...",
  "base_ranking_digest": "...",
  "historical_source_digest": "...",
  "historical_calibration_status": "basic",
  "personalization_status": "applied | no_op",
  "no_op_reasons": [...],
  "eligible_record_count": N,
  "excluded_record_counts": {...},
  "control_audit": {...},
  "timing_audit": {...},
  "domains": [
    {
      "primary_domain": "career",
      "base_rank": 1,
      "base_ordinal_score_scaled": 8,
      "historical_modifier_scaled": 1,
      "personalized_ordering_score_scaled": 9,
      "personalized_rank": 1,
      "historical_support_class": "supported",
      "supporting_record_ids": [...],
      "base_event_families": [...],
      "personalized_event_family_order": [...],
      "preferred_event_families": [...],
      "deprioritized_event_families": [...],
      "allowed_specificity": "event_family"
    }
  ],
  "personalization_digest": "..."
}
```

### 12.1 Domain-set invariant

必須滿足：

```text
set(output.domains.primary_domain)
== set(base_ranking.domains.primary_domain)
```

### 12.2 Base field preservation

每個 output domain 的：

```text
base_rank
base_ordinal_score_scaled
allowed_specificity
base_event_families
```

必須可追溯回原 base ranking，不得被 personalization 改寫後冒充 base truth。

### 12.3 Digests

`historical_source_digest` 只對「Phase 4 正式使用／排除判斷所需的 machine-readable canonical subset」做 digest。

不得把以下自由文字放進 source digest：

- `actual_event`；
- hypothesis / interpretation text。

因此只改事件敘述措辭，不應改 personalization result 或 digest。

`personalization_digest` 對完整 personalization output（排除自身 digest 欄位）做 canonical SHA-256。

engine/distribution/forecast.py
engine/distribution/calibration.py

既有 modules 可以作資料來源或被 runtime orchestration 呼叫，但責任邊界不混合。

## 15. Runtime Integration

新增正式 action：

```text
personalize_ranking
```

目標 capability：

```text
distribution.historical_personalization
status = implemented
maturity = experimental
routing = on_demand
```

Runtime input 至少需要：

```text
base_ranking
historical_calibration_status
historical_records
```

其中 `historical_records` 必須是 `05_驗證事件紀錄.md` 中 finalized Historical Calibration record 的 canonical order。

Runtime 不接受：

```text
actual_event_text_as_training_input
verified_event_free_text
research_notes
```

如果呼叫端傳入完整 finalized record，core 必須明確忽略自由文字欄位，只抽取本 spec 定義的 machine-readable subset。

Generated portable distribution 必須與 modular runtime byte-semantically parity。

## 16. Error Handling / Fail-safe

### Fail closed

以下屬 contract corruption，應 error：

- base ranking digest mismatch；
- unsupported base ranking policy；
- malformed domain rows；
- duplicate `record_id`；
- invalid enum value；
- impossible finalized Historical Calibration shape。

### Fail safe to no-op / exclusion

以下不應讓整次 forecast 失敗：

- 沒有 05；
- calibration status uncalibrated；
- unmapped legacy domain；
- ambiguous multi-domain；
- ambiguous multi-family；
- contaminated record；
- cannot_recall；
- insufficient per-domain sample；
- historical domain 不在 current base domain set；
- historical family 不在 current base family set。

這些狀況應留下 audit reason，而不是猜測 mapping。

## 17. Determinism

相同：

```text
base_ranking
historical_calibration_status
ordered finalized historical records
profile version
```

必須產生完全相同：

- normalization；
- exclusion reasons；
- support units；
- modifiers；
- personalized order；
- event-family order；
- `historical_source_digest`；
- `personalization_digest`。

禁止把：

- dict insertion accident；
- current wall-clock time；
- AI wording；
- unordered set iteration

混入 output identity。

## 18. Test Strategy

Phase 4 新測試不得使用 Kai 2026 已知 outcome 作 expected answer。

只使用：

- synthetic finalized Historical Calibration records；
- 現有 public / deterministic contract fixtures；
- 現有 Historical Calibration test shape；
- outcome-free base rankings。

### 18.1 Policy tests

至少覆蓋：

- profile/version constants；
- +2/+1/-2 evidence units；
- minimum sample threshold；
- ±2 modifier cap；
- support-class boundaries；
- closed alias mapping。

### 18.2 No-history / identity tests

必須證明：

- `history=[]` → personalized order == base order；
- uncalibrated → no-op；
- all contaminated → no-op；
- all cannot_recall → no-op；
- single eligible sample → no-op modifier；
- base ranking digest 在所有情況都不變。

### 18.3 Authority isolation tests

必須證明：

- history domain 不在 base set → 不會新增 domain；
- history family 不在 base set → 不會新增 family；
- personalization 不改 base ordinal score；
- personalization 不改 allowed specificity；
- Phase 3 ranker 對相同 features 的 output 與 Phase 4 加入前 byte-equivalent。

### 18.4 Historical eligibility tests

必須覆蓋：

- contaminated excluded；
- cannot_recall excluded；
- unscorable excluded；
- control audit-only；
- duplicate reference year first-blind-wins；
- duplicate record_id fail closed；
- multi-domain ambiguity excluded；
- multi-family ambiguity excluded from family scoring。

### 18.5 Legacy compatibility tests

至少鎖定：

```text
工作／職責 → career
```

並證明：

- 未列入 registry 的 label 不會 fuzzy match；
- 舊 event-family 描述不會自由猜成 canonical family。

### 18.6 Domain modifier tests

至少：

- 2 matched records → positive bounded modifier；
- 2 missed records → negative bounded modifier；
- mixed matched/missed → conservative modifier；
- 100 synthetic matches 仍不得超過 +2；
- 100 synthetic misses 仍不得低於 -2。

### 18.7 Event-family tests

至少：

- 2 exact canonical family matches → preferred ordering；
- one sample → insufficient；
- family 不在 current base candidates → excluded；
- family order 改變時 set 完全相同。

### 18.8 Free-text isolation tests

對同一 machine-readable record：

- 改 `actual_event`；
- 改 hypothesis wording；

必須得到完全相同：

- historical source digest；
- modifiers；
- personalized order；
- personalization digest。

### 18.9 Runtime / Generated Parity

`personalize_ranking` 必須有：

- modular runtime test；
- generated single-file runtime test；
- identical output / digest parity test。

### 18.10 Full regression gate

Phase 4 final gate 必須包含：

- Historical Calibration existing suites；
- Phase 3 ranker suites；
- Phase 3.5 structural interpretation suites；
- Phase 4 focused suites；
- full repository regression；
- Python 3.9 compile；
- deterministic distribution build/check；
- strict clean tree。

## 20. Acceptance Criteria

Phase 4 完成時必須能證明：

### A. Cold-start 完全獨立

沒有 history 時，原 Phase 3.5 + Phase 3 output 不受影響。

### B. History 只做 personalization

History 可以：

- 有限重排 base domains；
- 標示 supported / contradicted；
- 在既有 candidate set 內排序 event families。

History 不可以：

- 開新 domain；
- 開新 family；
- 改 base ranking digest；
- 改 Phase 3 specificity ceiling；
- 改 current chart facts。

### C. 個人化可重現

每一個 modifier 都能追溯到：

```text
record_id
normalization result
eligibility decision
evidence unit
aggregate support
policy version
```

### D. 自由文字不影響演算法

只改歷史事件敘述文字，不得改 Phase 4 result。

### E. 舊資料相容但不猜

既有明確 legacy label 可用 versioned exact alias registry 相容；沒有正式 mapping 的字串必須 exclusion，而不是 fuzzy guess。

### F. Phase 5 可安全消費

Phase 5 可以同時取得：

```text
base ranking truth
personalized ordering
historical support provenance
unchanged specificity ceiling
```

因此可以清楚區分：

- 「盤面本來就有的訊號」；
- 「歷史校準後較值得前置／保守的部分」。

---

## 21. Final Boundary

Phase 4 的正式定位是：

> **歷史資料提供個人化證據，不提供當期命盤事實。**

換句話說：

```text
命盤決定可以談什麼
Phase 3 決定 base ordering 與能談多細
歷史校準只決定同一候選集合內，哪些更符合這位命主過去的落地型態
```

這個順序不得反轉。
