# Metaphysics Lab v1.6.0 Release Integration Design

## Goal

Publish Metaphysics Lab Core v1.6.0 without conflating software release with predictive-model promotion.

## Frozen product base

- Base authority: `eaf03116bf5e02b08b4b51caed2cb2c31f796686`.
- Historical Activation Selector default remains `historical-activation-bazi-v1 / 1.0-exp`.
- Distribution Interpretation Contract default remains `lin_tianji_interpretation_contract_v1-exp`.
- The failed v2 release-behavior gate remains authoritative evidence against a default switch.

## Y1 integration

Y1 yearly Ziwei transformations are included as an implemented Experimental Project-derived capability. Production/runtime blobs are copied byte-identically from qualified Y1 anchor `f20ec931bf868f152226bab831dfa011f905a4f2`:

- `engine/distribution/forecast.py`
- `engine/ziwei/yearly_cycle.py`
- `dist/ai/metaphysics_lab.py`

Qualification tests are carried with the release candidate. Retrospective benchmark/adjudication tooling and Y1 research-only workflows are not required on the formal release surface.

## Research boundary

The release does not alter the sealed prospective study:

- no outcome read;
- no oracle creation;
- no private scoring;
- no outcome-driven retuning;
- no claim that Y1 or the Candidate pipeline is prospectively superior;
- `promotion_allowed=false` remains true for research-model promotion.

Case A and Case B remain sealed and waiting for their registered outcome windows to close.

## Release semantics

Software release and model promotion are separate states.

v1.6.0 may formally publish:

- the v1.6 structured architecture already present in the frozen product base;
- qualified Y1 yearly Ziwei transformations as Experimental;
- backward-compatible v1 defaults;
- existing research/evaluation infrastructure that is already present in the product base, without making it default user routing.

v1.6.0 must not state or imply that prospective accuracy has been proven.

## Release gates

The release candidate must pass all of the following on the exact candidate SHA:

1. Y1 qualification tests and byte-identity provenance checks.
2. Existing Bazi flow-time, Ziwei flow-time and Ziwei month-boundary qualification checks.
3. Existing Lin Tianji prediction validation and release-surface checks.
4. v1.6 release-contract tests proving package/version/workflow/docs consistency and v1-default preservation.
5. Full repository regression.
6. Python 3.9 compile check.
7. Deterministic AI distribution rebuild/check and clean-tree verification.
8. Deterministic three-file v1.6.0 user package verification.
9. Fresh structured isolated-sandbox evidence bound to the exact v1.6.0 release candidate, using the existing fail-closed evidence model; PENDING/FAIL evidence cannot release.
10. Private/outcome contamination scan: no prospective outcome/oracle/scoring artifact may enter the release surface.

## Publication

Only after every gate is green:

1. merge the release-integration PR to `main`;
2. confirm the merged `main` SHA passes the release workflow;
3. create immutable tag `v1.6.0` targeting that merged release SHA;
4. publish the GitHub Release and deterministic three-file user package.

The release itself does not change capability maturity beyond the explicit Y1 `Experimental` designation and does not authorize Candidate/default promotion.
