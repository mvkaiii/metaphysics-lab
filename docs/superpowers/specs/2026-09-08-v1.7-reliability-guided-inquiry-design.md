# Metaphysics Lab v1.7｜Reliability + Guided Inquiry 設計規格

- 日期：2026-09-08
- 文件狀態：Design freeze candidate，待使用者書面覆核
- Base branch：`main`
- Base SHA：`675f45193649432a34c51829780f74f6f73abc60`
- 設計 branch：`design/v1.7-reliability-guided-inquiry`
- 版本定位：v1.7 reliability / usability release

## 1. 目標

v1.7 不以新增更多命理算法為主軸，而是把 Metaphysics Lab 的「資料可靠性、預測驗證、能力真相與使用導航」做成正式產品能力。

核心目標：

1. 使用者能知道目前 Case 是否乾淨、哪些檔案是 authority、是否存在 legacy / duplicate / conflict。
2. 預測能明確區分 clean prospective、conditional prospective、hidden existing reality 與 retrospective calibration，避免把已知安排算成乾淨預測命中。
3. runtime capability 的 implementation / maturity / routing / qualification 只有一個正式真相來源，文件不得各自猜測。
4. AI 主動提供 3～4 個有價值的建議詢問方向，讓一般使用者知道接下來可以問什麼，但不限制自由輸入。

一句話定位：

> **v1.7 = Case Integrity + Prediction Validation + Capability Truth + Guided Inquiry**

## 2. v1.6 現況與可重用基礎

v1.7 必須建立在現有架構上，不另起第二套平行系統。

### 2.1 Runtime / capability

目前 `runtime_info()` 已透過 `engine/distribution/manifest.py` 聚合：

- `birth/capabilities.py`
- `bazi/capabilities.py`
- `distribution/capabilities.py`
- `historical/capabilities.py`
- `natal/capabilities.py`
- `ziwei/capabilities.py`

因此 v1.7 的 Capability Manifest 必須**擴充既有 registry / manifest**，不得另外建立一份人工維護、可能漂移的第二真相來源。

### 2.2 Case

目前已存在：

- Case Schema 1.1
- subject-aware filename
- Progressive Case
- `validate_case`
- `migrate_case`
- `update_case_record`
- `subject.rename`
- `命主索引.md`
- canonical slot 00～08

因此 Case Doctor 的角色是**診斷、比對、提出安全 reconciliation plan**；不是重寫現有 Case storage。

### 2.3 Prospective governance

目前 `engine/distribution/prospective.py` 已有：

- query anchor
- knowledge cutoff
- prospective window
- immutable forecast lock
- `clean_prospective / known_before_lock / partially_known`
- `clean_scorable / excluded_from_clean_accuracy`

v1.7 應在此基礎上增加更清楚的 validation context，而不是破壞既有 v1.5/v1.6 forecast lock。

### 2.4 AI workflow

目前 `core/AI工作流程.md` 已要求：

- 先 resolve subject
- 檢查 Case materialization
- 需要 deterministic calculation 時先讀 `runtime_info`
- 正常內部步驟靜默
- 未知 capability 不得猜測

Guided Inquiry 應接在這個既有 orchestration 上，而不是建立另一套對話入口。

## 3. 全域設計原則

1. **Single source of truth**：capability、Case identity、forecast lock 各自只能有一個 authority。
2. **Fail closed**：無法確認 authority、context class 或 mutation safety 時，不自動升格／搬移／計分。
3. **Append-only where evidence matters**：已鎖定預測、Historical Blind Set、驗證結果不可被事後覆寫。
4. **No silent specificity inflation**：導航問題不得比目前證據允許的 specificity 更具體。
5. **No contamination by navigation**：Guided Inquiry 不得在第一階段盲判前讀取或洩漏已驗證事件。
6. **Free-form remains first-class**：建議問題是導航，不是強制選單。
7. **No Case Schema migration by default**：v1.7 目標維持 Case Schema 1.1；若實作證明必須 bump schema，需另開 migration spec，不可順手修改。
8. **v1 defaults remain protected**：Selector v2 / Interpretation v2 不因 v1.7 reliability work 自動 promotion。

## 4. Workstream A｜Capability Manifest 單一真相來源

### 4.1 設計決定

不新增獨立人工維護的 `capability_manifest.json` 作 authority。

正式 authority 仍是各 engine 的 `_CAPABILITIES` registry；`engine/distribution/manifest.py` 負責聚合，`runtime_info()` 負責對外暴露。

v1.7 新增 manifest-level metadata：

```text
capability_manifest_version = 1.0
```

並要求每個正式 capability 至少能表達：

```text
id
implementation
maturity
routing
rule_version
module
dependencies
output_classification
ranking_authority
qualification_status        # 若適用
supported_scopes            # 若適用
required_inputs             # 若適用
```

不是每個 capability 都必須使用所有 optional fields；但同一欄位語義不得在不同 registry 中改名。

### 4.2 文件同步

v1.7 建立 machine-checkable drift guard：

- `runtime_info()` 是 runtime truth。
- README / 核心規則可用人類語言摘要 capability，但不得宣稱與 manifest 相反的 implementation / maturity / routing。
- release validation 必須檢查已知 capability statements 與 manifest 不矛盾。

不要求所有文件逐字由程式生成；要求可被測試偵測明顯 drift。

### 4.3 不做的事

- 不因 capability 已 materialize 就提升 maturity。
- 不因正式 release 就自動變 Stable。
- 不把 research candidate 寫成 default。

## 5. Workstream B｜Case Doctor + Legacy Reconciliation

### 5.1 使用者問題

目前 Project 可能同時存在：

- canonical subject-aware Case，例如 `Kai_CDBF04_00_...`
- 早期 generic / legacy 檔，例如 `命盤核心摘要.md`
- 已匯入與未匯入的舊事件紀錄
- duplicate / conflicting metadata

一般使用者不應自行判斷哪些可刪、哪些已匯入、哪些會重複計算。

### 5.2 新 runtime action

新增：

```text
diagnose_case
plan_case_reconciliation
```

#### `diagnose_case`

輸入使用者 Project 中可讀的文字檔 mapping，以及目標 subject context；只讀，不 mutation。

輸出：

```json
{
  "health": "PASS|WARN|BLOCKED",
  "canonical_subject": {},
  "authoritative_files": [],
  "legacy_files": [],
  "findings": [
    {
      "code": "...",
      "severity": "INFO|WARN|BLOCKING",
      "files": [],
      "message": "..."
    }
  ],
  "safe_analysis_scopes": [],
  "recommended_next_action": "none|plan_reconciliation|user_resolution_required"
}
```

典型 finding codes 至少涵蓋：

```text
legacy_generic_file_detected
duplicate_subject_candidate
subject_id_conflict
canonical_filename_manifest_mismatch
record_duplicate_exact
record_possible_semantic_duplicate
legacy_record_missing_from_canonical
case_schema_incompatible
case_validation_failed
```

#### `plan_case_reconciliation`

只接受 `diagnose_case` 的 canonical diagnostic result + 原始 project files。

輸出 deterministic dry-run plan：

```json
{
  "status": "no_change|safe_plan|blocked",
  "actions": [],
  "requires_user_confirmation": true,
  "preserve_files": [],
  "do_not_delete_yet": [],
  "conflicts_requiring_user_choice": []
}
```

### 5.3 Mutation boundary

v1.7 MVP **不新增一個可以一鍵任意改寫所有 Case 的 `apply_reconciliation`**。

原因：legacy record 是否為 semantic duplicate 常需要使用者判斷；自動 apply 容易誤刪證據。

安全做法：

1. Doctor 診斷。
2. Planner 產生 dry-run。
3. AI 用白話請使用者確認。
4. 確定為 deterministic safe action 時，才使用既有 `migrate_case` / `update_case_record` / subject actions 執行。
5. 任何 semantic conflict 都要求使用者選擇，不猜。

### 5.4 刪除原則

Case Doctor 可以建議「legacy 已完全 reconciliation，可封存／移除」，但 runtime 不因診斷結果自行刪除使用者檔案。

## 6. Workstream C｜Prospective Validation 2.0

### 6.1 新的四種 validation context

v1.7 固定使用以下語義：

```text
clean_prospective
conditional_prospective
hidden_existing_reality
retrospective_calibration
```

#### clean_prospective

在 knowledge cutoff 前，預測目標本身與其必要事件安排都尚未被確知。

可進 clean prospective denominator。

#### conditional_prospective

已知某個未來安排／條件存在，但要預測的是該已知條件之後仍未知的結果。

例如：已知 4/15 有簡報；預測簡報是否出現資源條件爭議。

可追蹤，但**不得進 clean prospective denominator**；只能進 conditional denominator。

#### hidden_existing_reality

事件／安排在 lock 前已經存在，只是模型沒有被告知；預測聲稱的內容其實是在辨識被遮蔽的既有事實。

可作 blind hidden-context research，但不得算 clean prospective forecast hit。

#### retrospective_calibration

目標事件在 knowledge cutoff 前已發生。

不得走 prospective lock；應導向 Historical Calibration / retrospective validation。

### 6.2 Context 必須 claim-level 判定

同一個問題內，不同 claim 可以有不同 context。

例如已知簡報：

- 「4/15 會有簡報」→ hidden_existing_reality
- 「簡報是否出現預算爭議」→ conditional_prospective

因此 context 不可只存在 query-level。

### 6.3 新 classifier

新增 deterministic primitive：

```text
classify_validation_context
```

每個 claim 提供最少的 epistemic metadata：

```text
target_time_relation_to_cutoff
known_arrangement_before_lock
claim_describes_known_fact
claim_depends_on_known_arrangement
outcome_known_before_lock
```

runtime 只依輸入分類，不自行猜使用者其實知不知道某件事。

### 6.4 Forecast lock backward compatibility

現有 v1.5/v1.6 `lock_prospective_forecast` payload 與 digest 必須 byte-compatible。

v1.7 可以在同一 action 中加入**明確 versioned v2 claim contract**，但舊 payload：

```text
{anchor, claims}
```

必須走原 contract，輸出不變。

v2 claim lock 需保存：

```text
context_class
clean_accuracy_eligible
conditional_accuracy_eligible
knowledge_cutoff_at
forecast_window
matched_if
partial_if      # optional
not_matched_if
```

`retrospective_calibration` 不允許進 prospective lock。

### 6.5 評估 denominator

正式統計至少分開：

```text
clean prospective
conditional prospective
hidden-existing-reality research
historical calibration
```

不得用 aggregate accuracy 把四者混在一起。

## 7. Workstream D｜Guided Inquiry｜引導式問事導航

### 7.1 UX 決定

使用者已確認：

- **主動顯示**。
- 每次顯示 **3～4 個**建議問題。
- **預設 3 個**。
- 只有存在明確、互不重複且高價值的第四方向時才顯示 4 個。
- 使用者永遠可以忽略建議，直接自由輸入。

「主動顯示」指：在第一個符合條件的 assistant response 中主動附上建議；不是平台層無訊息觸發的 push notification。

### 7.2 顯示時機

#### Entry suggestions

成功完成 subject resolution、Case health 可判斷後，在該次 session 的第一個正常內容回覆中附上 3～4 個方向。

#### Post-answer suggestions

完成一個 substantive 命理分析／流年／決策回答後，附上 3～4 個自然衍生方向。

### 7.3 不顯示時機

以下情況 suppress Guided Inquiry：

- runtime / Case 發生 blocking error，當下主要任務是修復錯誤。
- 正在要求使用者補一個必要欄位。
- Historical Blind Set 已鎖定、正等待使用者揭露指定事件時。
- 正在要求使用者確認檔案 mutation / reconciliation action。
- 純下載／安裝／版本更新／檔案傳輸確認。
- 使用者明確說不要顯示建議問題。

### 7.4 建議類型

候選 suggestion intent：

```text
integrity       Case / 資料完整性處理
overview        年度／本命總覽
deep_dive       深挖剛才主題
time_refine     年→月→日等合法時間細化
decision        把趨勢轉成具體選項比較
validation      鎖定／追蹤可驗證預測
related_domain  有證據支持的鄰近領域
```

### 7.5 排序規則

Entry：

1. BLOCKING / WARN Case integrity 若存在且可處理，佔第一順位。
2. 使用者最近／目前最相關主題。
3. 目前 capability 可合法回答的高價值 overview / domain。
4. 若已有 pending forecast，提供 tracking / validation。
5. 第四題只有在與前三題明顯不同且高價值時才加入。

Post-answer：

1. `deep_dive`：把目前答案拆細，但不可超過 evidence specificity ceiling。
2. `decision`：若存在可操作現實選項，轉成行動決策。
3. `validation`：若結論可 falsify，建議 lock / tracking。
4. `related_domain` 或 `time_refine`：只有真的有證據與 capability 時作第四題。

### 7.6 Specificity hard gate

Guided Inquiry 不得把較寬的盤面訊號偷偷升格成具體故事。

例如目前只支持：

```text
工作角色／責任調整
```

不得推薦：

```text
要不要看你會不會升職？
```

可推薦：

```text
要不要進一步區分這次變化比較偏責任、專案角色、職稱還是雇主變動？
```

### 7.7 Blindness hard gate

第一階段盲判完成前：

- Guided Inquiry 不讀 `驗證事件紀錄` 產生建議。
- 不用歷史實際事件命名下一題。
- 不暗示 Historical Calibration 尚未揭露的答案。

### 7.8 Runtime / AI 分工

新增 structured guidance primitive：

```text
suggest_inquiries
```

runtime 負責：

- 建議數量 3 或 4
- suggestion type
- domain / scope
- max specificity
- capability eligibility
- reason code
- suppression

AI 負責把 structured intent 翻成自然、白話的繁體中文問題。

Guided Inquiry output **不是命盤證據，也不得寫入 Case 作為預測**。

建議 structured shape：

```json
{
  "suppressed": false,
  "suggestions": [
    {
      "type": "deep_dive",
      "domain": "career",
      "target_scope": "monthly",
      "max_specificity": "event_family",
      "reason_code": "continuation_of_current_answer"
    }
  ]
}
```

user-facing v1.7 MVP 不要求顯示 reason code；保持畫面輕量。

## 8. 整體資料流

### 8.1 Session entry

```text
Project Instructions
→ resolve subject
→ runtime_info / capability manifest
→ diagnose_case
→ safe analysis state
→ suggest_inquiries(entry)
→ AI 顯示 3～4 個建議方向
```

### 8.2 一般未來問事

```text
user question
→ resolve subject
→ Case / capability check
→ Stage 1 blind analysis
→ optional forecast lock
→ Stage 2 historical calibration（若流程需要）
→ final strategy
→ suggest_inquiries(post_answer)
```

### 8.3 已知未來安排

```text
known arrangement supplied
→ classify each forecast claim
→ hidden fact / conditional outcome 分開
→ lock only eligible prospective claims
→ separate denominator
→ answer
→ Guided Inquiry 可推薦 conditional follow-up，但不得稱 clean forecast
```

### 8.4 Case integrity issue

```text
diagnose_case
→ WARN/BLOCKED
→ plan_case_reconciliation
→ user review
→ existing safe mutation actions
→ re-run diagnose_case
→ PASS
→ normal analysis / Guided Inquiry
```

## 9. Versioning 提案

v1.7 reliability work 預計：

```text
Project Contract:          1.2

Case Schema:               1.1

```

若 implementation plan 發現 Runtime Schema 必須改 envelope，需先回到 spec 修訂；不得實作時偷偷 bump。

## 10. Non-goals

v1.7 本 cycle 不包含：

- 奇門遁甲 engine。
- Selector v2 default promotion。
- Interpretation v2 default promotion。
- 為 private outcomes 調參。
- 把 Ziwei daily/hourly 升為 Stable。
- 大規模重寫 Phase 3 evidence ranking。
- 自動刪除 legacy Case 檔案。
- Case Schema 1.2 migration。

Event-family / specificity ontology 與 Ziwei Monthly qualification 可作 v1.7 後續 research track，但不得阻塞本 reliability release 的 MVP。

## 11. 測試與 release hard gates

### 11.1 Capability

- manifest deterministic。
- duplicate capability id fail closed。
- docs known-claim drift tests PASS。
- v1.6 capability maturity / routing 不得被無意 promotion。

### 11.2 Case Doctor

至少 synthetic coverage：

- clean 1.1 Case → PASS。
- generic legacy + canonical duplicate → WARN。
- exact duplicate record → 可 deterministic 識別。
- semantic possible duplicate → 不自動 merge。
- subject_id conflict → BLOCKED。
- manifest filename mismatch → BLOCKED/WARN 依現行 validation authority。
- dry-run byte-identical。
- plan 不直接刪檔。

### 11.3 Prospective Validation 2.0

至少固定四個 synthetic cases：

1. 完全未知未來事件 → clean_prospective。
2. 已知會議存在、預測會議結果 → conditional_prospective。
3. 已知會議存在、模型猜到會議本身 → hidden_existing_reality。
4. 已發生事件 → retrospective_calibration，prospective lock rejected。

並要求：

- 舊 v1.5/v1.6 forecast lock fixtures byte-identical。
- clean denominator 不含 conditional / hidden / retrospective。
- conditional denominator 獨立。

### 11.4 Guided Inquiry

至少驗證：

- Entry 正常狀態 = 3 個。
- 有明確第四高價值方向 = 4 個。
- 不得 >4 或 <3（非 suppressed 狀態）。
- blocking interaction / event disclosure gate = suppressed。
- recommendation 不得超過 `max_specificity`。
- 未 materialized capability 不得被推薦。
- Stage 1 不得利用 verified-event input。
- suggestion order deterministic。
- user can ignore suggestions without改變 analysis path。

### 11.5 Regression

- full repository suite PASS。
- v1.6 release-contract / post-release docs regression PASS 或以 versioned successor 測試取代，不得直接刪 guard。
- Historical Calibration persistent-lock regression PASS。
- v1 forecast lock backward-compat PASS。
- AI distribution bundle parity PASS。
- Python 3.9 parse / compile PASS。
- User Package deterministic verification PASS。

## 12. Implementation decomposition

這份 spec 涵蓋四個互相合作、但可獨立 review 的 subsystem。implementation 不應做成一個巨型單 commit。

建議拆成五個 implementation plans／review gates：

1. **Plan 1｜Capability Manifest v1.0**
   - 先固定 capability truth 與 drift guard。
2. **Plan 2｜Case Doctor + Reconciliation Planner**
   - 建立 diagnosis / dry-run，不做任意 auto-apply。
3. **Plan 3｜Prospective Validation 2.0**
   - 建立 claim-level context classification 與 denominator separation。
4. **Plan 4｜Guided Inquiry**
   - 消費前 1～3 的 structured state，實作 entry / post-answer 3～4 題導航。
5. **Plan 5｜v1.7 Integration / Distribution / Release Gate**
   - Project Contract 1.2、runtime version、AI workflow、distribution regeneration、完整 regression、sandbox 與 release qualification。

依賴順序：

```text
Plan 1
├─ Plan 2
├─ Plan 3
└─ Plan 4 depends on Plan 1 + consumes Plan 2/3 outputs

Plan 1 + 2 + 3 + 4
→ Plan 5 release integration
```

## 13. Acceptance criteria

v1.7 MVP 完成時，一般使用者應能看到以下體驗：

1. 進入已有 Case 的正常對話後，AI 主動給 3 個建議問題；只有真的有第四個高價值方向時才給 4 個。
2. 建議題目不會偷偷把「工作變動」升格成「一定升職」。
3. Case 有 legacy / duplicate / conflict 時，AI 能先告知問題與安全處理方式，而不是自己猜哪份該刪。
4. 已知未來安排不會被計入 clean prospective accuracy；未知結果仍可作 conditional tracking。
5. `runtime_info` 與文件對 capability 的主要聲明不互相矛盾。
6. v1.6 已有 Case、forecast lock、Historical Calibration 與 v1 defaults 保持 backward compatible。

## 14. Release positioning

v1.7 發布說明應避免宣稱「命理更準」。

正確定位：

> v1.7 強化 Case integrity、預測驗證治理、能力狀態一致性與 Guided Inquiry 使用體驗；它提升的是可稽核性與使用可靠性，不等於已證明預測準確率提升。
