# 林氏天機 v1.5｜Phase 5 Interpretation Contract 設計

## 1. 目的

Phase 5 建立一個獨立、可稽核、deterministic 的 **Interpretation Contract Layer**，位於 Phase 3 base ranking 與 Phase 4 Historical Personalization 之後，負責把已確定的結構化結果整理成 AI 可安全使用的解讀邊界。

Phase 5 不重新排盤、不建立 EvidenceFeature、不重新 ranking、不產生新的 domain / event family，也不把歷史或現實背景轉成新的盤面訊號。它只回答四件事：

1. AI 應先談哪些已存在的候選。
2. 每個候選最多可以講到多具體。
3. 哪些資料只能當背景、時間窗、個人化順序或策略條件。
4. 一般使用者可以看到哪些判斷理由，哪些內部工程資訊不應直接外露。

Phase 5 profile identity 固定為：

```text
lin_tianji_interpretation_contract_v1-exp
```

本 Phase 不提升任何既有 capability maturity，不建立新的 base ranking authority。

---

## 2. 架構定位

正式資料流：

```text
Deterministic Forecast Context
  → Phase 3.5 Structural Interpretation
  → EvidenceFeature
  → Phase 3 Base Ranking
  → Phase 4 Historical Personalization
  → Phase 5 Interpretation Contract
  → AI Natural-language Interpretation / Strategy
```

### Authority 層級

- **Phase 3**：唯一 base ranking authority。
- **Phase 4**：bounded historical personalization metadata，`ranking_authority=false`。
- **Phase 5**：interpretation / disclosure / strategy boundary，`ranking_authority=false`。
- **AI**：依 contract 做自然語言解讀與策略，不得覆寫上游 deterministic truth。

Phase 5 必須把 Phase 3 與 Phase 4 明確分開。Phase 4 的 `personalized_rank`、preferred family order 只代表歷史校準後的呈現偏好，不等於新的盤面強度，也不得被 AI 表述成「盤面本身更強」。

---

## 3. 核心 invariants

Phase 5 必須遵守以下硬規則：

1. `base_ranking.ranking_digest` 必須驗證成功。
2. 若提供 personalization，`personalization.base_ranking_digest` 必須與 base ranking digest 完全一致。
3. Phase 5 不得新增 base ranking 中不存在的 domain。
4. Phase 5 不得新增或刪除任一 domain 原有的 event-family candidate set。
5. Phase 5 不得修改 Phase 3 ordinal score、base rank、EvidenceFeature、dependency relation 或 structural truth。
6. Phase 5 不得提高 `allowed_specificity`；只能原樣保留或因 local-window / UX / maturity 邊界而降低。
7. Phase 4 personalization 不得升高 specificity。
8. 現實背景不得改變 base ranking、personalization、local-window classification 或 forecast confidence。
9. cutoff 前已知事件不得被改寫為 prospective hit。
10. Stage 2 歷史校準不得回寫 Stage 1 blind forecast。
11. Phase 5 不輸出事件機率、命中率或 accuracy estimate。
12. 相同 canonical inputs 必須產生相同 `interpretation_contract_digest`。

任何輸入違反上述 authority relationship，Phase 5 必須 fail closed，不由 AI 猜測或自動修正。

## 4. Public Interface

建議公開函式：

```python
build_interpretation_contract(
    base_ranking,
    anchor,
    personalization=None,
    local_windows=None,
    claims=None,
) -> dict
```

### 必要輸入

#### `base_ranking`

Phase 3 `lin_tianji_rank_v1-exp` 的 immutable ranking snapshot。

Phase 5 需要驗證：

- policy version
- target scope
- domain rows
- event-family candidate sets
- allowed specificity
- ranking digest

Phase 5 不直接消費 raw EvidenceFeature 重新排名。

#### `anchor`

Phase 1 已 resolve 的 Query Anchor / prospective window。

至少綁定：

- `query_anchor_at`
- `knowledge_cutoff_at`
- `prospective_window_start`
- `prospective_window_end`
- `query_timezone`
- `question_reference`
- `status`

Query Anchor 只決定知識截止點與 prospective 時間窗，不影響命理 activation、rank 或 strength。

### 可選輸入

#### `personalization`

Phase 4 `lin_tianji_historical_personalization_v1-exp` output。

若不存在，Phase 5 正常產生 cold-start contract。

若存在，必須驗證：

- profile version
- `base_ranking_digest`
- target scope
- domain set equality
- base event-family candidate set equality
- allowed specificity 不高於 base
- personalization digest

Phase 5 只可使用：

- `personalization_status`
- `personalized_rank`
- `historical_support_class`
- `personalized_event_family_order`
- `preferred_event_families`
- `deprioritized_event_families`

Phase 5 不把 Phase 4 modifier 數值或歷史支持 class 翻譯成事件機率。

#### `local_windows`

只接受 Phase 3 `detect_local_spike()` 已產生的 structured rows。

Phase 5 不自行重新判定 local spike / active window。

若提供，至少驗證：

- parent / child scope relationship
- `parent_ranking_digest`
- `child_ranking_digest`
- supplied base ranking 是否對應 target-side digest
- source specificity
- capped allowed specificity
- window type

Local-window evidence 只能維持或降低 specificity，不能升級。

#### `claims`

只接受 Phase 1 已正式 locked 的 prospective claims 或其 immutable normalized representation。

Phase 5 不得修改：

- prediction
- forecast window
- matched_if
- not_matched_if
- knowledge cutoff
- contamination state
- method version

Claims 只用來告訴 AI 哪些說法已經正式鎖定，以及哪些內容不能因後續現實資料而改寫。

## 5. Output Contract

建議輸出固定包含：

```text
profile_version
target_scope
knowledge_cutoff_at
prospective_window_start
prospective_window_end

base_ranking_digest
personalization_digest
personalization_status

primary_domains
secondary_domains
domain_interpretation[]
local_windows[]

specificity_ceiling
reality_context_policy
forecast_strategy_policy
disclosure_policy
claim_boundaries[]

interpretation_contract_digest
```

### `domain_interpretation[]`

每個 base domain 至少包含：

```text
primary_domain
base_rank
presentation_rank
personalization_applied
base_allowed_specificity
effective_specificity
event_family_candidates
personalized_event_family_order
preferred_event_families
deprioritized_event_families
evidence_explanation_classes
```

#### `base_rank`

固定來自 Phase 3，不變。

#### `presentation_rank`

若 Phase 4 personalization `applied`，可使用 personalized order；否則等於 base order。

這只是 UX presentation order，不建立新的 ranking authority。

#### `event_family_candidates`

必須與 Phase 3 base candidate set 完全相同。

Phase 4 / Phase 5 都不能新增或刪除。

#### `personalized_event_family_order`

若 personalization 有效，可改順序，但集合必須與 base candidate set 完全相等。

## 6. Primary / Secondary Domain 規則

`primary_domains` / `secondary_domains` 是 **UX organization**，不是新的 scoring model。

Phase 5 不增加新的命理 threshold、不重新計分，也不使用隱藏的 probability cutoff。

建議 v1 規則：

- `domain_interpretation` 永遠保留所有 Phase 3 opened domains。
- `primary_domains` 依 presentation order 取固定展示上限。
- 其餘進 `secondary_domains`。
- 固定展示上限屬 UI / response organization policy，不得被描述為「只有前 N 名才有命理作用」。
- 即使 secondary domain 未在一般回答主動展開，仍保留在 contract 中供使用者追問。

Implementation plan 必須把展示上限定義為封閉、版本化的 UX 常數，並以測試證明它不影響 base ranking digest 或 domain eligibility。

---

## 7. Specificity Ceiling

Phase 5 的 effective specificity 規則固定為：

```text
effective_specificity = 最保守值(
    Phase 3 allowed_specificity,
    applicable local-window cap,
    interpretation UX / maturity cap
)
```

只允許降級，不允許升級。

### 範例

Phase 3：`concrete_event`

Daily local spike cap：`event_family`

Phase 5 effective specificity 必須是 `event_family`。

Phase 3：`event_family`

即使 Phase 4 歷史 repeated support 很強，也不能升成 `concrete_event`。

### 解讀語意

- `domain`：只能談領域或主題。
- `event_family`：可談事件類型或落地形式。
- `concrete_event`：允許較具體事件候選，但仍不是「一定發生」。

任何 Phase 5 contract 都不得把 specificity level 包裝成 probability。

---

## 8. Evidence Explanation Classes

Python 不直接生成最終自然語言回答，只產 deterministic explanation classes。

Phase 5 v1 建議至少支援：

```text
independent_convergence
single_system_support
target_with_background_modifier
background_modifier
local_spike
active_window
historically_supported_order
historically_mixed_order
historically_contradicted_order
experimental_only
```

### 語意

#### `independent_convergence`

多組相對獨立 evidence dependency 同時指向同一 domain / family。

對外可說：

> 這個主題不是只靠單一訊號，而是有多組相對獨立的盤面依據共同指向。

不得對外列 raw bonus / weight。

#### `single_system_support`

主要由單一體系或單一獨立來源支撐。

不得自動標成低可信；只說證據來源較集中。

#### `background_modifier`

較粗時間層只能當背景，不能單獨製造 target-period concrete event。

#### `local_spike`

較細時間層局部變強，但不改寫整體週期主軸。

#### `active_window`

父子時間層方向一致，表示既有主題進入較活躍時間窗。

#### `historically_supported_order`

歷史校準支持某種既有落地形式，因此呈現順序可優先。

不得說成「發生機率較高 X%」。

#### `historically_mixed_order`

歷史落地形式不一致，個人化只能弱化使用。

#### `historically_contradicted_order`

歷史結構化校準對某既有候選形成 bounded deprioritization；候選仍存在，不得刪除。

#### `experimental_only`

目前只有 experimental 層級支撐，AI 可作觀察，但不能單獨支撐高度具體事件。

## 9. Reality Context Policy

Phase 5 contract 不保存使用者現實背景自由文字，也不把自由文字納入 interpretation contract identity。

Contract 只輸出政策：

```text
reality_context_policy:
  may_adjust_strategy: true
  may_adjust_priority_of_advice: true
  may_adjust_feasibility: true

  may_change_base_ranking: false
  may_change_personalization: false
  may_open_domain: false
  may_add_event_family: false
  may_raise_specificity: false
  may_relabel_known_fact_as_prediction: false
```

### Known reality 定義

任何在 `knowledge_cutoff_at` 前已知的事實、安排或已進行事項都是 reality context，例如：

- 已開始工作或任務
- 已存在的合作
- 已知轉職／離職安排
- 已簽合約
- 已確定旅行
- 已知醫療狀況
- 使用者已明確提供的當前計畫

這些資訊可以讓策略更實際，但不能成為 prospective evidence，也不能計算為 prospective hit。

## 10. Forecast / Strategy Separation

Phase 5 必須明確區分：

```text
Forecast = 上游 deterministic ranking / windows / claims 所允許的前向判斷
Strategy = Forecast × Reality Context × Feasibility / Constraints
```

建議 contract：

```text
forecast_strategy_policy:
  forecast_specificity_authority: phase3
  strategy_specificity_authority: reality_context
  strategy_must_not_be_presented_as_forecast: true
  known_reality_must_not_be_scored_as_hit: true
  stage2_must_not_rewrite_stage1: true
```

### Strategy 可以比 forecast 更具體

若盤面只允許 `event_family`，forecast 不得越級講某個具體專案一定發生。

但如果使用者現實上已經有一個具體專案，策略可以針對該專案給非常具體的行動建議。

例如：

- Forecast：近期工作／責任與外部合作主題活躍。
- Reality：使用者已在執行 GA4 / GTM 類合作。
- Strategy：建議把一次性協助整理成需求表、事件命名規範、驗收清單與報價流程。

最後一段是策略，不是盤面直接預測。

---

## 11. Stage 1 / Stage 2 Interpretation Boundary

Phase 5 必須保留雙階段問事：

### Stage 1

```text
Phase 3 base ranking
+ anchor
+ local windows
→ cold-start interpretation contract
```

Stage 1 不讀 Historical Calibration outcome content 來改寫盤面。

### Stage 2

```text
同一份 immutable Phase 3 base ranking
+ Phase 4 personalization
+ 同一 anchor / claim boundary
→ calibrated interpretation contract
```

Stage 2 可以：

- 調整 presentation order
- 說明哪些既有 family 過去較符合這位命主的落地形式
- 提高或降低策略上的觀察優先度

Stage 2 不可以：

- 改寫 Stage 1 原文／prediction
- 新增 Phase 3 不存在的 candidate
- 把已知歷史事件包裝成 Stage 1 原本預測到
- 提高 allowed specificity

---

## 12. Strategy Context State

Phase 5 可提供簡單的策略背景完整度狀態：

```text
none
partial
sufficient
```

這不是命理 confidence，也不是 forecast strength。

### `none`

幾乎只有盤面與問題，策略只能提供較一般方向。

### `partial`

已有部分工作型態、既有合作、資源或限制資料，可提供較實際策略。

### `sufficient`

具體決策已有方案、成本、期限、風險與現實條件，可提供更具體的執行策略。

無論狀態為何，都不得反過來提高 forecast confidence / rank / specificity。

Phase 5 v1 的 Python public contract不需要吃自由文字 reality context 來自動分類此狀態；可把 policy schema 建好，實際 state 可由 AI / future structured context layer依明確資料判定。若 implementation plan 要讓 Python接收 state，必須使用 closed enum，不得 free-text semantic classification。

## 13. High-Risk Decision Boundary

醫療、法律、保險、稅務、房產、大額投資、高槓桿等領域，Phase 5 只能提供：

- 時間壓力
- 決策節奏
- 盤面傾向
- 心理／資源配置風險
- 防守／進攻條件
- 第二意見、降槓桿、延後、先確認條款等策略

不得把命理解讀替代醫師、律師、會計師、理財／房產專業意見。

此政策沿用現有 Project governance，不建立新的醫療／法律判定引擎。

## 14. Disclosure Policy

Phase 5 固定分三種 disclosure level：

```text
user_safe
technical_rationale
internal_only
```

### `user_safe`

一般命理對話預設層級。

可揭露：

- 哪些領域較活躍
- 單一或多組相對獨立訊號
- 全期主題或局部時間窗
- 歷史校準是否提供個人化順序參考
- 最多可以講到哪個 specificity 層級的白話意思
- 為什麼某判斷需要保守

不可直接暴露 raw runtime / schema / scoring field names。

### `technical_rationale`

使用者主動詢問方法、判斷原理、可稽核理由時可使用。

可說明：

- target-period ownership
- background modifier
- fine-time local window
- dependency de-dup 的高層原理
- independent convergence 的高層原理
- Historical Calibration 只能 narrowing / reordering existing candidates
- known reality 與 prospective forecast 分離

仍不預設公開精確 weight、threshold、feature vector 或 anti-gaming mechanics。

### `internal_only`

Repo 維護／技術稽核可用，一般使用者回答預設不直接曝光：

- exact numeric weights
- exact numeric thresholds
- raw ordinal contribution formula
- modifier cap calculation mechanics
- dependency de-dup implementation details
- raw feature vectors
- raw gate formula
- anti-gaming mechanics
- internal digest / field names（除非明確技術稽核）

### Contract schema

```text
disclosure_policy:
  user_facing_language: zh-Hant-TW
  default_explanation_level: user_safe

  allow_high_level_method_rationale: true
  allow_metaphysical_terms_when_relevant: true

  expose_numeric_weights: false
  expose_numeric_thresholds: false
  expose_internal_feature_vectors: false
  expose_raw_gate_formula: false

  expose_ranking_digest_to_ordinary_user: false
  expose_runtime_field_names_to_ordinary_user: false

  technical_audit_may_use_internal_terms: true
```

- 台灣繁體中文
- 自然完整中文句子

- 不必要的英文改成自然中文
- 不把工程欄位當命理結論

## 17. Historical Personalization ≠ Probability

Phase 4 support classes：

```text
insufficient
contradicted
mixed
supported
strongly_supported
```

Phase 5 不得翻譯為：

- 80% 機率
- 高機率發生
- 準確率上升多少
- 過去命中率

除非未來 Phase 6 有正式 prospective holdout 與獨立 evaluation contract，否則都不得建立 accuracy claim。

對外應使用：

> 過去的校準紀錄較支持這種落地方式。

而不是：

> 這件事發生機率比較高。

- domain

- contamination state
- evaluation eligibility
- method version
- immutable lock identity / digest reference

Phase 5 不重新 render 或修改 prediction text 作為 canonical claim。

## 19. Digest Identity

`interpretation_contract_digest` 以 canonical JSON SHA-256 計算。

Digest identity 應包含：

- Phase 5 profile version
- target scope
- anchor / cutoff structured fields
- base ranking digest
- personalization digest / status（若有）
- validated local-window structured rows
- deterministic domain interpretation rows
- specificity policy result
- policy blocks
- claim-boundary structured identities

Digest 不應包含：

- 使用者現實背景自由文字
- Historical Calibration actual-event free text
- AI 最終自然語言回答
- research notes
- transient UI copy

因此自由文字換句話說，不應改變 Phase 5 contract identity。

## 20. Fail-Closed Conditions

至少以下情況直接回傳 `DistributionError`：

1. base ranking policy 不支援。
2. base ranking digest mismatch。
3. anchor malformed / cutoff relationship invalid。
4. personalization profile 不支援。
5. personalization digest mismatch。
6. personalization base digest 不等於 supplied base ranking digest。
7. personalization domain set 與 base 不同。
8. personalization event-family set 與 base 不同。
9. personalization 提高 allowed specificity。
10. local-window parent / child digest 與 supplied ranking 不一致。
11. local-window 提高 source specificity。
12. claims digest / cutoff / method identity 不合法。
13. unknown authority override fields 出現在 runtime payload。
14. 非 deterministic / non-JSON material 被塞入 canonical contract input。

Fail closed 時 AI 不得自己跳過錯誤繼續稱已完成正式 Phase 5 contract。

## 24. Historical / Old-Data Test Protocol Boundary

使用者之後提供舊資料時，正式分類至少分成：

```text
development_contaminated
regression_only
holdout_unseen
prospective
```

### `development_contaminated`

已看過結果，可用於：

- bug reproduction
- compatibility
- fail-closed boundary
- wording / contamination test

不得用於調整 mapping / threshold 後再宣稱準確率提升。

### `regression_only`

鎖定既有行為，防止新版讀壞舊資料；不作 accuracy evidence。

### `holdout_unseen`

在 policy / threshold 定稿前沒有被拿來調參的資料，才可作較強的離線驗證。

### `prospective`

knowledge cutoff 後才發生的真正前向紀錄，交由 Phase 6 append-only evaluation。

Phase 5 不建立 accuracy denominator。

## 27. 與 2026-08-26 Roadmap 的差異

8/26 原始 Phase 5 roadmap 使用概念介面：

```text
build_interpretation_contract(ranking, anchor, claims=None)
```

Phase 3.5 與 Phase 4 完成後，正式架構已更清楚，因此新版改為：

```text
build_interpretation_contract(
    base_ranking,
    anchor,
    personalization=None,
    local_windows=None,
    claims=None,
)
```

這個修正的目的不是擴張 Phase 5，而是保留已建立的 authority boundary：

- `base_ranking` 永遠是 Phase 3 truth。
- `personalization` 是 Phase 4 bounded metadata，不能冒充 ranking truth。
- `local_windows` 是 Phase 3 已算好的 timing interpretation metadata，Phase 5 不重算。
- `claims` 是 Phase 1 locked boundary，Phase 5 不改寫。

因此 Phase 5 只負責「AI 可以怎麼解讀」，不重新決定「盤面到底是什麼」。
