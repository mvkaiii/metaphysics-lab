# v1.6 Yearly Ziwei Transformations Y1 Design

## Goal

Add a new research-only yearly Ziwei transformation materialization path so the forecast context can carry Project-derived yearly 四化 alongside yearly flowing stars, without modifying frozen EFA/C2/HCC/HOC semantics or any existing event-family mapping.

- Base authority: `eaf03116bf5e02b08b4b51caed2cb2c31f796686`.
- Work occurs only on `research/v1.6-yearly-ziwei-transformations-y1`.
- The frozen authority branch and frozen commit are not modified.
- This cycle is retrospective research only; `promotion_allowed=false` until a fresh prospective validation cycle.
- Historical outcomes must not be used to alter the transformation table, palace mapping, event-family mapping, ranking thresholds, EFA, C2, HCC, HOC, or paired evaluator.

## Problem statement

The frozen forecast pipeline already materializes yearly Ziwei flowing stars from the target lunar year, but `_yearly_scope()` does not materialize a yearly transformation layer. The Project transformation profile already supports all ten heavenly stems, `composition.build_cycle_layer()` explicitly supports `yearly`, and the Project chart already contains natal star locations required to resolve transformation targets.

As a result, formally available yearly 四化 semantics are absent from the frozen yearly structural-evidence path even though finer monthly/daily/hourly scopes already materialize transformation layers.

## Source-of-truth rule

The new yearly transformation layer is **Project 推導盤面**, not Astralium output.

Inputs are limited to:

1. the same deterministic yearly source already produced by `source_from_yearly()`;
2. frozen Project natal star locations reconstructed from normalized natal facts;
3. the existing `metaphysics-lab-common-v1` transformation table;
4. the existing flying-edge logic that resolves each transformation star to its natal palace.

The new path must not read verified events, historical outcomes, retrospective benchmark labels, or prose interpretations.

## Architecture

Create `engine/ziwei/yearly_cycle.py` as the yearly analogue of `fine_cycle.py`.

`build_yearly_cycle_layer(yearly_source, chart_identity, star_locations, transformation_profile_id=PROFILE_ID)` will:

1. validate that `yearly_source.scope == "yearly"` and its chart identity matches the supplied chart;
2. convert the yearly source into the existing neutral `CycleStemSource` using exactly the same scope, reference, heavenly stem and chart identity;
3. call the existing `get_transformation_set()` for that heavenly stem;
4. call the existing `fly_transformations()` against the natal star index;
5. build a `CycleTransformationLayer` with the same yearly reference and the yearly earthly branch;
6. preserve Project provenance from the yearly source.

`engine/distribution/forecast.py` will pass `star_locations` into `_yearly_scope()` and include the resulting layer as `transformation_layer` in the existing scope envelope. No other scope behavior changes.

## Required invariants

- Yearly flowing-star source and yearly transformation source use the same chart, scope, reference and heavenly stem.
- Four transformations and four flying edges are always produced for a qualified yearly source.
- The yearly transformation layer remains classified as Project-derived data.
- Existing monthly/daily/hourly behavior is unchanged.
- Existing decadal behavior is unchanged.
- Structural interpretation consumes the new yearly layer through the already-existing Ziwei transformation parser; no EFA code changes are required.
