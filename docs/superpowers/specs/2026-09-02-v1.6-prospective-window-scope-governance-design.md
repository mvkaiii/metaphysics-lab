# v1.6 Prospective Window → Structural Scope Governance Design

Status: DESIGN_ONLY / NOT_IMPLEMENTED / NOT_PROMOTION_AUTHORITY  
Profile: `lin_tianji_prospective_window_scope_v1`  
Base authority: `eaf03116bf5e02b08b4b51caed2cb2c31f796686`  
Promotion allowed: false

## 1. Purpose

This design closes one governance gap discovered during the first real private prospective intake: the prospective contract can lock an arbitrary civil-time window, while Phase 3 structural interpretation requires an explicit `target_scope` (`decadal`, `yearly`, `monthly`, `daily`, `hourly`). Frozen v1.6 does not define a deterministic bridge between those concepts.

The policy must decide structural scope without reading outcomes, verified events, oracle data, Legacy output, Candidate output, Q1/T1 output, or any other post-lock evidence.

The first supported use cases are:

- 2026 Q4: 2026-10-01 through 2026-12-31, work/finance.
- 2027 H2: 2027-07-01 through 2027-12-31, work/finance.

## 2. Non-goals

This change does not:

- modify EFA, C2, HCC, HOC, Q1, T1, paired evaluation, event-family mappings, or ranking thresholds;
- add `quarterly`, `half_yearly`, or generic `interval` to the structural scope hierarchy;
- permit monthly evidence to create a child claim when structural authority is yearly;
- change a case's prospective forecast/scoring window into a full-year window;
- read historical outcomes or verified-event ledgers;
- silently merge or promote the separate Y1 yearly-Ziwei-transformation research candidate;
- authorize merge, release, default-branch switch, or model promotion.

## 3. Existing authority preserved

Frozen structural scope order remains:

`decadal -> yearly -> monthly -> daily -> hourly`

Existing role semantics remain unchanged:

- same scope as target: `target_evidence`;
- coarser scope: `modifier`;
- finer scope: `timing_trigger`.

Therefore, when `target_scope=yearly`, monthly evidence may only be `timing_trigger`. It cannot independently open a domain or child event family under frozen Phase 3 / EFA semantics.

## 4. Decision

Version 1 supports only **calendar-aligned, same-year, multi-month windows**.

A supported window must satisfy all of the following:

1. start is strictly earlier than end;
2. timezone is explicit and valid;
3. start and end resolve into the same civil calendar year in that timezone;
4. start and end fall in different civil calendar months;
5. the local start date is the first day of its month;
6. the local end date is the last day of its month.

For every supported window:

- `claim_target_scope = yearly`
- `timing_scopes = [monthly]`
- `child_opening_scope = yearly`
- the original prospective window start/end are preserved unchanged
- monthly scopes may annotate timing or contribute timing triggers only
- the shared child universe is generated from the yearly EFA child inventory only

Any cross-year, partial-month, single-month, or sub-month window fails closed in v1.

This intentionally rejects cases such as 2026-01-31 → 2026-02-01 even though two month labels appear.

## 5. Why this approach

### 5.1 Recommended: yearly authority + monthly timing

This keeps the existing structural hierarchy intact and avoids making claim count proportional to the number of months in a case. Q4 and H2 therefore remain comparable case units even though one spans three months and the other six.

### 5.2 Rejected: run every month and union children

This would require new de-duplication, aggregation, and weighting rules. It would also give longer windows a mechanically larger opportunity to create claims.

### 5.3 Rejected: add quarterly / half-yearly / interval scopes

This would alter the frozen scope hierarchy and require broader changes to role routing, ranking, EFA, HCC/HOC, tests, and downstream research governance.

## 6. Policy input and output

The resolver consumes exactly three governance-only fields:

- `window_start`
- `window_end`
- `timezone`

Unknown fields are rejected. In particular, outcome-like, historical, oracle, Candidate, Legacy, Q1, and T1 fields are not accepted.

Normalized output:

```json
{
  "schema_version": "v1.6-prospective-window-scope-policy.v1",
  "policy_profile": "lin_tianji_prospective_window_scope_v1",
  "window_class": "calendar_aligned_same_year_multi_month",
  "window_start": "<normalized offset-aware ISO-8601>",
  "window_end": "<normalized offset-aware ISO-8601>",
  "timezone": "<IANA zone>",
  "claim_target_scope": "yearly",
  "timing_scopes": ["monthly"],
  "child_opening_scope": "yearly",
  "policy_digest": "<sha256 canonical payload without policy_digest>",
  "promotion_allowed": false
}
```

The policy profile/schema are implementation constants, not caller-selectable authority switches.

The policy digest is deterministic SHA-256 over canonical JSON with sorted keys, UTF-8, no NaN, and no whitespace-dependent representation.

## 7. Window classification rules

Classification is based only on civil calendar coordinates in the supplied timezone.

A window is `calendar_aligned_same_year_multi_month` when all rules in Section 4 hold. Version 1 does not infer scope from approximate duration in days, avoiding month-length and daylight-saving ambiguity.

The registered prospective cases classify as:

- 2026 Q4 -> `calendar_aligned_same_year_multi_month` -> yearly authority + monthly timing
- 2027 H2 -> `calendar_aligned_same_year_multi_month` -> yearly authority + monthly timing

## 8. Child-universe and claim identity authority

The scope policy does not create or rename claim IDs.

For an INCLUDE case:

1. resolve and lock the window-scope policy;
2. run the selected outcome-free structural candidate authority with `target_scope=yearly`;
3. run Phase 3 ranking and frozen EFA attribution;
4. use the complete frozen EFA `children[*].child_claim_id` inventory as the pre-arm shared child universe;
5. lock exactly those IDs in S1;
6. later Legacy and Candidate/HOC arms must preserve that same universe exactly; HOC may partition it into ordinary `children` and `audit_only_children`, but may not add or remove IDs;
7. do not suffix or rewrite child IDs with month, quarter, or half-year labels.

This ordering matters: the S1 shared universe is frozen **before** Legacy or Candidate render authority is inspected. It therefore cannot be defined by whichever children a downstream arm chose to render.

Monthly timing evidence cannot add a child ID absent from the yearly EFA inventory. In frozen EFA, timing triggers are attribution metadata while direct same-scope target evidence determines whether a child is opened.

## 9. Claim-authority provenance

S1 already requires `claim_authority_profile` and `claim_authority_digest`. The scope policy alone is not sufficient claim authority.

Before real claim-universe lock, the research cycle must create a small immutable **claim-authority manifest** containing at least:

- scope-policy profile + policy digest;
- structural candidate authority identifier/digest;
- mapping profile;
- Phase 3 policy/profile authority;
- EFA profile/version authority;
- resolved `target_scope=yearly`;
- `promotion_allowed=false`.

`claim_authority_digest` is the SHA-256 of that canonical manifest. `claim_authority_profile` identifies the manifest schema/profile, not the outcome or case.

For the current prospective validation of the separate Y1 research candidate, the exact Y1 semantic qualification authority must be recorded explicitly in this manifest. This design does not hardcode, merge, or promote that Y1 authority.

## 10. Forecast-window semantics

Structural authority and scoring window are separate concepts.

For a 2026 Q4 case:

- structural claim authority: yearly
- timing trigger granularity: monthly
- forecast/scoring window: 2026 Q4 only

A child supported by annual structural evidence is not automatically scored as a hit for an event outside the registered Q4 window. The original prospective window remains the only outcome-scoring interval for that case.

The same rule applies to 2027 H2.

## 11. S1 handoff

The existing private intake and S1 source manifest remain unchanged.

The ordering becomes:

`case intake -> private registry snapshot -> S1 source manifest -> window-scope policy lock -> claim-authority manifest -> outcome-free yearly structural/ranking/EFA child universe -> S1 claim-universe lock -> S1 frame/receipt -> freeze Legacy/Candidate arms -> wait for outcome -> oracle/adjudication`

The window-scope lock and claim-authority manifest are provenance authorities. They are not outcome oracle or scoring authority.

## 12. Error handling / fail-closed behavior

The resolver rejects:

- cross-year windows;
- partial-month windows;
- single-month or sub-month windows in v1;
- start >= end;
- missing or invalid timezone;
- timezone/offset mismatch;
- unknown input fields.

Failure prevents claim-universe lock for that case. No manual override may silently substitute `yearly` or `monthly`.

The S1 handoff additionally fails closed if:

- the claim-authority manifest is missing or digest-invalid;
- EFA target scope differs from the resolved scope-policy target;
- the S1 locked IDs do not exactly equal the EFA child inventory;
- a later Legacy/HOC universe differs from the locked S1 universe.

## 13. Testing requirements

Implementation must follow RED -> GREEN TDD.

Required tests:

1. 2026 Q4 resolves to yearly + monthly timing.
2. 2027 H2 resolves to yearly + monthly timing.
3. Cross-year window fails closed.
4. Single-month window fails closed in v1.
5. Partial-month cross-month window fails closed.
6. Same normalized input produces byte-identical output and digest on repeat runs.
7. Unknown/outcome/history/oracle/candidate fields are rejected.
8. Timezone offset mismatch is rejected.
9. Monthly timing evidence cannot open a child absent from the yearly EFA child inventory.
10. Existing manual `target_scope=yearly` Phase 3/EFA identity is unchanged when the policy selects yearly.
11. S1 locked child IDs must exactly equal the EFA child inventory.
12. Downstream Legacy and HOC universes must exact-match the S1 locked universe.
13. Claim-authority manifest digest changes if any semantic authority identifier/digest changes.
14. No frozen authority file outside the approved scope-policy / claim-authority integration surface changes.

## 14. Integration boundary

The minimal implementation should be isolated in new governance modules rather than changing structural mapping semantics.

Expected new responsibilities:

- window-scope resolver: civil window -> resolved structural/timing scope metadata;
- claim-authority manifest builder/validator: bind the scope-policy lock to exact structural/EFA semantic authorities;
- S1 integration validation: exact-match EFA child IDs with S1 locked IDs.

Existing structural interpreters, ranker, EFA, C2, HCC, HOC, Legacy Adapter, paired oracle, and paired evaluator remain semantic dependencies, not edit targets.

A runtime action may be added only if needed to expose the resolver deterministically. Any interface addition requires contract tests and remains research-only.

## 15. Relationship to Y1 yearly Ziwei transformation research

This scope policy is orthogonal to the separate Y1 yearly-Ziwei-transformation research cycle.

- Scope policy decides *which structural time scope is authoritative* for a civil-time prospective window.
- Y1 decides *which yearly Ziwei evidence is present* once yearly scope has been selected.

The scope policy can be developed and verified against frozen v1.6 independently. A prospective Candidate arm using Y1 must explicitly bind the exact Y1 semantic authority into the claim-authority manifest before the child universe is frozen.

This prevents the scope bridge from silently turning an unpromoted Y1 research result into base-v1.6 authority.

## 16. Governance and promotion

This is research infrastructure only.

- Work occurs on a dedicated research branch.
