# v1.6 Prospective Window → Structural Scope Governance Design

Status: DESIGN_ONLY / NOT_IMPLEMENTED / NOT_PROMOTION_AUTHORITY  
Profile: `lin_tianji_prospective_window_scope_v1`  
Base authority: `eaf03116bf5e02b08b4b51caed2cb2c31f796686`  
Promotion allowed: false

## 1. Purpose

This design closes one governance gap discovered during the first real private prospective intake: the prospective contract can lock an arbitrary civil-time window, while Phase 3 structural interpretation requires an explicit `target_scope` (`decadal`, `yearly`, `monthly`, `daily`, `hourly`). The frozen v1.6 code does not define a deterministic bridge between those two concepts.

The new policy must decide structural scope without reading outcome, verified events, oracle, Legacy output, Candidate output, Q1/T1 output, or any other post-lock evidence.

The first supported use cases are:

- 2026 Q4: 2026-10-01 through 2026-12-31, work/finance.
- 2027 H2: 2027-07-01 through 2027-12-31, work/finance.

## 2. Non-goals

This change does not:

- modify EFA, C2, HCC, HOC, Q1, T1, paired evaluation, or event-family mappings;
- add `quarterly`, `half_yearly`, or generic `interval` to the structural scope hierarchy;
- permit monthly evidence to create a new child claim when the structural authority is yearly;
- change a case's prospective forecast window into a full-year forecast;
- read historical outcomes or verified-event ledgers;
- authorize merge, release, default-branch switch, or model promotion.

## 3. Existing authority preserved

Frozen structural scope order remains:

`decadal -> yearly -> monthly -> daily -> hourly`

Existing role semantics remain unchanged:

- same scope as target: `target_evidence`;
- coarser scope: `modifier`;
- finer scope: `timing_trigger`.

Therefore, when `target_scope=yearly`, monthly evidence may only be a `timing_trigger`. It cannot independently open a domain or child event family under the frozen Phase 3 / EFA rules.

## 4. Decision

Version 1 supports only a narrow class of prospective windows:

1. the window spans at least two distinct civil calendar months;
2. the entire window is contained within one civil calendar year;
3. start is strictly earlier than end;
4. the timezone is explicit and valid.

For every supported window:

- `claim_target_scope = yearly`
- `timing_scopes = [monthly]`
- the original prospective window start/end are preserved unchanged
- monthly scopes may annotate timing or contribute timing triggers only
- the shared child universe is generated from the yearly target authority only

Any window that crosses a civil-year boundary fails closed in v1.

Any single-month or sub-month window also fails closed in v1 rather than being silently mapped to monthly. A later policy version may add that behavior after separate design and validation.

## 5. Why this approach

### 5.1 Recommended: yearly authority + monthly timing

This keeps the existing structural hierarchy intact and avoids making the number of claims proportional to the number of months in a case. Q4 and H2 therefore remain comparable case units even though one spans three months and the other six.

### 5.2 Rejected: run every month and union children

This would require new de-duplication, aggregation, and weighting rules. It would also give longer windows a mechanically larger opportunity to create claims.

### 5.3 Rejected: add quarterly / half-yearly / interval scopes

This would alter the frozen structural scope hierarchy and require broader changes to role routing, ranking, EFA, HCC/HOC, tests, and downstream research governance.

## 6. Policy input and output

The policy consumes governance-only input:

- `window_start`
- `window_end`
- `timezone`

It must reject unknown fields. In particular, outcome-like, historical, oracle, candidate, Legacy, Q1, and T1 fields are not accepted.

Normalized output:

```json
{
  "schema_version": "v1.6-prospective-window-scope-policy.v1",
  "policy_profile": "lin_tianji_prospective_window_scope_v1",
  "window_class": "same_year_multi_month",
  "window_start": "<normalized offset-aware ISO-8601>",
  "window_end": "<normalized offset-aware ISO-8601>",
  "timezone": "<IANA zone>",
  "claim_target_scope": "yearly",
  "timing_scopes": ["monthly"],
  "child_opening_scope": "yearly",
  "policy_digest": "<sha256 canonical payload without policy_digest>",
  "promotion_allowed": false
}
```

The policy digest is deterministic SHA-256 over canonical JSON with sorted keys, UTF-8, no NaN, and no whitespace-dependent representation.

## 7. Window classification rules

Classification is based only on civil calendar coordinates in the supplied timezone.

A window is `same_year_multi_month` when:

- start and end resolve into the same civil year; and
- `(start.year, start.month) != (end.year, end.month)`.

Version 1 does not infer scope from approximate duration in days. This avoids month-length and daylight-saving ambiguities.

The two registered prospective cases therefore classify as:

- 2026 Q4 -> `same_year_multi_month` -> yearly authority + monthly timing
- 2027 H2 -> `same_year_multi_month` -> yearly authority + monthly timing

## 8. Child-universe and claim identity rules

The scope policy does not create claim IDs.

For an INCLUDE case:

1. resolve the policy;
2. run the frozen structural pipeline with `target_scope=yearly`;
3. generate the frozen yearly EFA/C2/HCC/HOC child universe under the selected candidate authority;
4. lock exactly those outcome-free child IDs in S1;
5. do not suffix or rewrite child IDs with month, quarter, or half-year labels.

Monthly timing evidence cannot add a child ID that is absent from the yearly child universe.

Legacy and Candidate arms must consume the same locked child universe for paired evaluation.

## 9. Forecast-window semantics

Structural authority and scoring window are separate concepts.

For a 2026 Q4 case:

- structural claim authority: yearly
- timing trigger granularity: monthly
- forecast/scoring window: 2026 Q4 only

A child supported by annual structural evidence is not automatically scored as a hit for an event occurring outside the registered Q4 window. The original prospective window remains the only outcome-scoring interval for that case.

The same rule applies to 2027 H2.

## 10. S1 handoff

The existing private intake and S1 source manifest remain unchanged.

The new ordering is:

`case intake -> private registry snapshot -> S1 source manifest -> window-scope policy lock -> outcome-free yearly child universe -> S1 claim-universe lock -> S1 frame/receipt -> freeze Legacy/Candidate arms -> wait for outcome -> oracle/adjudication`

The window-scope lock becomes part of claim-authority provenance. It is not an outcome oracle and is not scoring authority.

## 11. Error handling / fail-closed behavior

The policy rejects:

- cross-year windows;
- single-month or sub-month windows in v1;
- start >= end;
- missing or invalid timezone;
- timezone/offset mismatch;
- unknown input fields;
- unsupported policy profile/version.

Failure must prevent claim-universe lock for that case. No manual override may silently substitute `yearly` or `monthly`.

## 12. Testing requirements

Implementation must follow RED -> GREEN TDD.

Required tests:

1. 2026 Q4 resolves to yearly + monthly timing.
2. 2027 H2 resolves to yearly + monthly timing.
3. Cross-year window fails closed.
4. Single-month window fails closed in v1.
5. Same normalized input produces byte-identical output and digest on repeat runs.
6. Unknown/outcome/history/oracle/candidate fields are rejected.
7. Timezone offset mismatch is rejected.
8. Monthly timing evidence cannot open a child absent from the yearly EFA child universe.
9. Existing manual `target_scope=yearly` EFA/C2/HCC/HOC identity is unchanged when the policy selects yearly.
10. No frozen authority file outside the approved scope-policy integration surface changes.

## 13. Integration boundary

The minimal implementation should be isolated in a new governance module rather than changing structural mapping semantics. Existing consumers should receive the selected `claim_target_scope` as an explicit resolved value.

The implementation may add a runtime action or a small orchestration hook only if needed to make the policy reusable and testable. Such an interface change must be covered by contract tests and remain outside frozen branch authority.

## 14. Relationship to Y1 yearly Ziwei transformation research

This policy is orthogonal to the separate Y1 yearly-Ziwei-transformation research cycle.

- The scope policy decides *which structural time scope is authoritative* for a civil-time prospective window.
- Y1 decides *which yearly Ziwei evidence is present* once yearly scope has been selected.

The scope-policy authority can therefore be developed and verified against the frozen v1.6 base independently. Any later prospective Candidate arm using Y1 must explicitly record both authorities/digests; this design does not silently merge or promote Y1.

## 15. Governance and promotion

This is research infrastructure only.

- Base frozen v1.6 authority remains immutable.
- New work occurs on a dedicated research branch.
- `promotion_allowed=false` at every stage.
- No merge/tag/release/default switch is authorized by this design.
- Real private cases may proceed to S1 claim-universe lock only after this policy implementation passes its full engineering/governance gate and the policy authority is frozen by digest.
