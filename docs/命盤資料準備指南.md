# 命盤資料準備指南

這份文件說明建立私人命理 Project 時可以提供哪些資料，以及資料不完整時系統應怎麼處理。

> **Precision must be earned by input.**
>
> 不知道的資料就保留未知；不得為了排出完整命盤而自行補出生時間、出生地、性別、四柱或其他缺值。

> 以下姓名、日期與識別碼皆為**虛構示例**。

## 一、三種準備方式

### 方式 A｜只有出生資料

提供：

- 性別
- 西元／Gregorian 出生日期
- 原始出生時間
- 出生地

資料足夠時，Metaphysics Lab 可以建立 **Project 原生盤面**，包括目前 runtime 可執行的八字與紫微本命資料。

### 方式 B｜出生資料 + Astralium

如果你有 Astralium 八字、Astralium 紫微，或其他第三方排盤，可以和出生資料一起提供。

這是**可選**的交叉校驗方式，不是使用 Metaphysics Lab 的必要條件。系統會把第三方資料保留為 External view，把自己計算的資料保留為 Project view，再做 reconciliation；兩邊不互相覆寫。

Astralium 資料若需要在私人 Project 中保留成獨立檔案，可另外建立：

```text
<filename_label>_<SUBJECT_SHORT_ID>_03-1_Astralium八字資料包.md
<filename_label>_<SUBJECT_SHORT_ID>_04-1_Astralium紫微資料包.md
```

這兩份是**非 canonical** 的**可選外部參考附件**，不取代 `03_八字結構化資料包.md`／`04_紫微基礎資料包.md`，也不改變 canonical 00～08 結構。沒有 Astralium 就不建立。

兩份補充檔必須屬於同一命主並統一使用 Case 的正式 `subject_display_name`。如果來源名稱只有**大小寫差異**，例如 `Amy` 與 `amy`，系統自動統一成 **Case 的正式命主稱呼**；如果名稱內容不同，例如 `Amy` 與 `Allie`，先視為命主不一致，在確認或修正前**不得生成** 03-1／04-1，也不得把兩人的資料混在一起。

### 方式 C｜只有第三方排盤

如果目前只有 Astralium、其他排盤網站、命理軟體或命理師提供的結構化八字／紫微資料，也可以先建立 External view。

但第三方資料存在，不代表 Project 原生盤面已經計算完成；系統不得把匯入資料冒充自己的計算結果。

## 二、先辨識命主

一個 Project 可以管理多位命主。Project-level 使用：

```text
命主索引.md
```

虛構範例：

```yaml
subject_id: subj_7f3a2c91d4e8
subject_display_name: Alex
subject_short_id: 7F3A2C
filename_label: Alex
```

- `subject_id` 是長期識別碼，不由姓名、生日、性別或出生地推導。
- `subject_display_name` 可以是真名、暱稱或私人標籤，也可以日後改名。
- 改名不得改掉 `subject_id`。
- 同名命主可以共存。
- 本人／配偶／合作夥伴／父母等，是當次問題角色，不是永久 Subject Identity。

Case Schema 1.1 的實際檔名格式為：

```text
<filename_label>_<SUBJECT_SHORT_ID>_<slot>_<canonical_title>.md
```

例如：

```text
Alex_7F3A2C_01_命盤核心摘要.md
```

這裡的 `01_命盤核心摘要.md` 是內部 **canonical slot**；真正私人 Project 會看到帶命主 label 與 short ID 的完整檔名。

## 三、完整出生資料

完整單一 Project 本命通常需要：

- 性別
- 出生日期
- 出生時間
- 出生地

建議另外保留：

- 出生時間來源，例如出生證明、戶籍資料或家人記憶
- 出生時間可信度
- 是否只有大概時段
- 第三方排盤是否使用真太陽時、特殊子時換日或其他時間設定

出生地解析後可能包含座標與 IANA timezone；時間口徑由既定規則處理，不能由 AI 自由補算。

目前真正可執行哪些能力、需要哪些輸入，技術上仍以 `runtime_info` 為準。本文件不硬寫容易過期的 capability 狀態表。

## 四、如果缺少出生時間

若使用者**缺少出生時間**，**不得自行補一個時辰**，也不得把區間中點當成真正出生時間。

如果只知道「大概晚上7、8點」、下午、早上，或例如 13:00～15:00，系統應保留這份不確定性。

當 `runtime_info` 顯示 `natal.candidate_envelope` 可執行，而且出生日期、出生地與 timezone 等必要 basis 足夠時，可以建立 **Candidate Envelope**，也就是 partial Project candidate set。

對 bounded / unknown time：

- Python 掃描使用者實際聲明的不確定時間範圍。
- 不使用 12:00、00:00 或其他 default time。
- 不使用 midpoint。
- 所有候選共同一致的欄位才當成 invariant facts。
- 有差異的欄位保留為 candidate-dependent facts。
- 不用多數決把不確定資料升格成確定資料。
- 不把任何候選盤冒充唯一完整 Project 本命。

因此可以建立 `partial` Base Case，但需要**唯一**出生時辰才能成立的時柱、紫微命宮／身宮、部分星曜、大限或 single-chart personalized forecast，仍可能保持 blocked。

如果連出生地／timezone 的可靠 basis 都不足，就不能假裝已建立 Project Candidate Envelope；可以先保存可信 External 資料或追問缺少資訊。

## 五、Astralium／第三方八字資料

若有 Astralium 或其他第三方八字資料，建議保留來源實際提供的：

- 年柱、月柱、日柱、時柱
- 日主
- 藏干
- 十神
- 八字大運
- 來源提供的流年資料
- 排盤系統名稱
- 產出日期／版本（若可取得）
- 子時換日口徑
- 真太陽時、時區或其他時間設定

來源若另外提供格局、身強弱、喜用神、五行統計、神煞或干支互動，也可以保存，但要清楚標示「來源提供」，不要把 AI 後續推論反寫成原始盤面事實。

若另存成 Astralium 八字補充檔，使用 `03-1_Astralium八字資料包.md` 的可選外部參考附件定位；內容仍只保存第三方實際提供的資料。

## 六、Astralium／第三方紫微資料

若有 Astralium 紫微或其他第三方紫微資料，建議保留來源實際提供的：

- 十二宮
- 各宮星曜
- 命宮
- 身宮
- 命主／身主（若來源有提供）
- 生年四化
- 自化／飛化（若來源有提供）
- 紫微大限
- 小限
- 流年命宮
- 流年四化／飛化（若來源有提供）
- 排盤系統與時間口徑

若另存成 Astralium 紫微補充檔，使用 `04-1_Astralium紫微資料包.md` 的可選外部參考附件定位。

Project 自己建立的本命計算屬於 **Project 原生盤面**；由本命、運限與目標時間再算出的流年、流月、流日、流時等時間層屬於 **Project 推導盤面**。兩者都不得冒充 Astralium 或其他第三方原始資料。

## 七、External / Project / Resolved 怎麼看

如果第三方資料與 Project 計算資料同時存在，先做 reconciliation，不要挑「比較符合人生事件」的版本直接使用。

固定保留三層：

```text
External / Project / Resolved
```

比較狀態：

```text
MATCH / EQUIVALENT / CONFLICT / NOT_COMPARABLE
```

簡單說：

- **External**：第三方來源原本提供什麼，就保存什麼。
- **Project**：Metaphysics Lab 自己按固定規則計算的結果。
- **Resolved**：經校驗後，明確記錄目前採用哪一個來源，以及是否仍有差異。

Resolved 不能把原本的 CONFLICT 改寫成 MATCH。

校驗結果可以進入該命主的 `02` slot，例如：

```text
Alex_7F3A2C_02_命盤資料校驗紀錄.md
```

## 八、第一次建立 Case

新 Case 採 Progressive Case：第一次有足夠 natal source 或合法 Candidate Envelope 時，先建立 Base Case。

虛構命主 Alex：

```text
Alex_7F3A2C_00_專案索引.md
Alex_7F3A2C_01_命盤核心摘要.md
Alex_7F3A2C_02_命盤資料校驗紀錄.md
Alex_7F3A2C_03_八字結構化資料包.md
Alex_7F3A2C_04_紫微基礎資料包.md
```

內部 canonical slot 仍是：

```text
00_專案索引.md
01_命盤核心摘要.md
02_命盤資料校驗紀錄.md
03_八字結構化資料包.md
04_紫微基礎資料包.md
```

若本次另外保留 Astralium，可再看到例如：

```text
Alex_7F3A2C_03-1_Astralium八字資料包.md
Alex_7F3A2C_04-1_Astralium紫微資料包.md
```

這兩份不屬於 canonical slot，不改變 Base Case 00～04 的正式結構。

如果是 `partial` natal，Case 必須把「已確定盤面」「候選依賴盤面」「目前不可唯一判定」分開，不能因 Case 已建立就把 blocked conclusion 當成解鎖。

## 九、05～08 需要時才建立

後續有實際內容時才建立：

```text
Alex_7F3A2C_05_驗證事件紀錄.md
Alex_7F3A2C_06_流年追蹤紀錄.md
Alex_7F3A2C_07_問事追蹤紀錄.md
Alex_7F3A2C_08_重大決策紀錄.md
```

- `05`：已驗證事件與 Historical Blind Calibration
- `06`：值得永久追蹤的流年／年度預測
- `07`：值得永久追蹤的一般問事
- `08`：重大決策紀錄

第一版 blind forecast 一旦正式記錄，不得事後覆寫；實際結果只能追加。

## 十、Historical Blind Calibration

過去 10 年的 Historical Blind Calibration 是**建議但非強制**的個人化校準步驟。完成後可以增加「同類盤面訊號在這位命主身上通常怎麼落地」的證據；使用者不做或稍後再做，也不會讓 Case 失效。

**未校準仍可直接進入**本命分析、個人化未來趨勢、流年、問事或重大決策。`Historical Calibration = uncalibrated` **不影響排盤本身的正確性**；差別是**個人化落地形式與信心校準會少一層證據**。回答時要明確說明這個限制，不得把未校準分析包裝成已完成事件驗證。

使用者選擇校準時，仍必須遵守 Historical Blind Calibration 的防污染順序：

```text
resolve subject
↓
先用 Base Case 完成 Stage 1 盲判並鎖定
↓
歷史盲測與使用者驗證
↓
寫入已確認事件
↓
Stage 2 事件校準
```

如果 Candidate Envelope 仍封鎖單一命盤個人化預測，不能為了進校準流程而偷偷選一個候選時辰。

`05` 內要分開：

- `blind_prediction`＝命理推論
- `user_confirmed_actual`＝**已驗證事件**
- `evaluation`＝**已校驗資料**

不得把盲測假說直接當成已驗證事件。

## 十一、Metaphysics Lab 的八種資料類型

所有資料永遠區分：

1. **原始盤面事實**：第三方來源直接提供的欄位。
2. **已校驗資料**：reconciliation、驗證結果、校準評價。
3. **Project 原生盤面**：由出生資料經固定 Natal Engine 建立的本命計算。
4. **Project 推導盤面**：由本命／運限／目標時間經固定算法建立的衍生時間層。
5. **已驗證事件**：使用者確認真正發生過的事件。
6. **命理推論**：AI 對盤面的事件、趨勢與策略解讀。
7. **研究假說**：尚未正式納入已校驗算法的研究想法。
8. **當次現實背景**：工作、財務、家庭、決策條件等現況。

資料越多不代表越好；來源與證據層級混在一起，反而會讓分析無法驗證。

## 十二、最低使用路徑

```text
metaphysics_lab.py
metaphysics_core.md
Project Instructions
↓
讀／建立 命主索引.md
↓
提供出生資料和／或 structured external chart
↓
完整時間 → 建立 Project natal
不確定時間 → natal.candidate_envelope / partial
只有第三方 → External view
↓
建立 Base Case
↓
可直接分析；視需要再做 Historical Blind Calibration
↓
依實際需要逐步建立追蹤紀錄
```

如果當次環境無法執行 Python，AI 必須明講，不能用文字模擬成「已排盤」「已展開候選」或「已驗證」。

私人 `命主索引.md`、出生資料、人生事件、Astralium raw chart、PDF 與截圖不應提交到公開／共用 GitHub repo。
