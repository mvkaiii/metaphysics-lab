# 命盤資料準備指南

這份文件說明建立私人命理專案時可以提供哪些資料，以及資料不完整時系統應怎麼處理。

> **精確度必須來自實際輸入資料（Precision must be earned by input）。**
>
> 不知道的資料就保留未知；不得為了排出完整命盤而自行補出生時間、出生地、性別、四柱或其他缺值。

> 以下姓名、日期與識別碼皆為**虛構示例**。

## 一、三種準備方式

### 方式 A｜只有出生資料

提供：

- 性別
- 西元（Gregorian）出生日期
- 原始出生時間
- 出生地

資料足夠時，Metaphysics Lab 可以建立**專案原生命盤**，也就是由系統根據出生資料與固定規則自行計算的八字與紫微本命資料。

### 方式 B｜出生資料 + Astralium

如果你有 Astralium 八字、Astralium 紫微，或其他第三方排盤，可以和出生資料一起提供。

這是**可選**的交叉校驗方式，不是使用 Metaphysics Lab 的必要條件。系統會把第三方資料保留為**第三方來源**，把自己計算的資料保留為**系統計算結果**，再做校驗；兩邊不互相覆寫。系統內部仍分別使用 `External` 與 `Project` 作為資料來源代碼。

Astralium 資料若需要在私人專案中保留成獨立檔案，可另外建立：

```text
<filename_label>_<SUBJECT_SHORT_ID>_03-1_Astralium八字資料包.md
<filename_label>_<SUBJECT_SHORT_ID>_04-1_Astralium紫微資料包.md
```

這兩份是**非正式主檔位**的**可選外部參考附件**，不取代 `03_八字結構化資料包.md`／`04_紫微基礎資料包.md`，也不改變正式 00～08 結構。沒有 Astralium 就不建立。

兩份補充檔必須屬於同一命主並統一使用個案資料中的正式 `subject_display_name`。如果來源名稱只有**大小寫差異**，例如 `Amy` 與 `amy`，系統自動統一成**個案資料中的正式命主稱呼**；如果名稱內容不同，例如 `Amy` 與 `Allie`，先視為命主不一致，在確認或修正前**不得生成** 03-1／04-1，也不得把兩人的資料混在一起。

### 方式 C｜只有第三方排盤

如果目前只有 Astralium、其他排盤網站、命理軟體或命理師提供的結構化八字／紫微資料，也可以先建立第三方來源資料。

但第三方資料存在，不代表專案原生命盤已經計算完成；系統不得把匯入資料冒充自己的計算結果。

## 二、先辨識命主

一個命理專案可以管理多位命主。專案層級使用：

```text
命主索引.md
```

虛構範例：

```yaml
subject_id: subj_7f3a2c91d4e8
subject_display_name: Alex
subject_short_id: 7F3A2C
filename_label: Alex
```

- `subject_id` 是長期識別碼，不由姓名、生日、性別或出生地推導。
- `subject_display_name` 可以是真名、暱稱或私人標籤，也可以日後改名。
- 改名不得改掉 `subject_id`。
- 同名命主可以共存。
- 本人／配偶／合作夥伴／父母等，是當次問題角色，不是永久命主識別資料。

個案資料格式（Case Schema）1.1 的實際檔名格式為：

```text
<filename_label>_<SUBJECT_SHORT_ID>_<slot>_<canonical_title>.md
```

例如：

```text
Alex_7F3A2C_01_命盤核心摘要.md
```

這裡的 `01_命盤核心摘要.md` 是內部**正式檔位**；真正私人專案會看到帶命主名稱與短識別碼的完整檔名。

## 三、完整出生資料

建立單一命主的完整本命通常需要：

- 性別
- 出生日期
- 出生時間
- 出生地

建議另外保留：

- 出生時間來源，例如出生證明、戶籍資料或家人記憶
- 出生時間可信度
- 是否只有大概時段
- 第三方排盤是否使用真太陽時、特殊子時換日或其他時間設定

出生地解析後可能包含座標與 IANA 時區；時間口徑由既定規則處理，不能由 AI 自由補算。

目前真正可執行哪些功能、需要哪些輸入，技術上仍以 `runtime_info` 為準。本文件不硬寫容易過期的功能狀態表。

## 四、如果缺少出生時間

若使用者**缺少出生時間**，**不得自行補一個時辰**，也不得把區間中點當成真正出生時間。

如果只知道「大概晚上7、8點」、下午、早上，或例如 13:00～15:00，系統應保留這份不確定性。

當 `runtime_info` 顯示 `natal.candidate_envelope` 可執行，而且出生日期、出生地與時區等必要依據足夠時，可以建立**候選盤面集合（Candidate Envelope）**，也就是保留多種可能狀態的部分專案資料。

對 `bounded`（有範圍）／`unknown_time`（時間未知）的情況：

- Python 掃描使用者實際聲明的不確定時間範圍。
- 不使用 12:00、00:00 或其他預設時間。
- 不使用區間中點。
- 只有所有候選共同一致的欄位，才視為確定事實。
- 有差異的欄位保留為候選狀態依賴資料。
- 不用多數決把不確定資料升格成確定資料。
- 不把任何候選盤冒充唯一完整本命。

因此可以建立 `partial` 的基礎個案資料，但需要**唯一**出生時辰才能成立的時柱、紫微命宮／身宮、部分星曜、大限或單一命盤個人化預測，仍可能保持未確定。

如果連出生地／時區的可靠依據都不足，就不能假裝已建立候選盤面集合；可以先保存可信的第三方來源資料，或追問缺少資訊。

## 五、Astralium／第三方八字資料

若有 Astralium 或其他第三方八字資料，建議保留來源實際提供的：

- 年柱、月柱、日柱、時柱
- 日主
- 藏干
- 十神
- 八字大運
- 來源提供的流年資料
- 排盤系統名稱
- 產出日期／版本（若可取得）
- 子時換日口徑
- 真太陽時、時區或其他時間設定

來源若另外提供格局、身強弱、喜用神、五行統計、神煞或干支互動，也可以保存，但要清楚標示「來源提供」，不要把 AI 後續推論反寫成原始盤面事實。

若另存成 Astralium 八字補充檔，使用 `03-1_Astralium八字資料包.md` 的可選外部參考附件定位；內容仍只保存第三方實際提供的資料。

## 六、Astralium／第三方紫微資料

若有 Astralium 紫微或其他第三方紫微資料，建議保留來源實際提供的：

- 十二宮
- 各宮星曜
- 命宮
- 身宮
- 命主／身主（若來源有提供）
- 生年四化
- 自化／飛化（若來源有提供）
- 紫微大限
- 小限
- 流年命宮
- 流年四化／飛化（若來源有提供）
- 排盤系統與時間口徑

若另存成 Astralium 紫微補充檔，使用 `04-1_Astralium紫微資料包.md` 的可選外部參考附件定位。

系統自己建立的本命計算屬於**專案原生命盤**；由本命、運限與目標時間再算出的流年、流月、流日、流時等時間層屬於**專案推導盤面**。兩者都不得冒充 Astralium 或其他第三方原始資料。

## 七、第三方來源／系統計算結果／已校驗採用結果怎麼看

如果第三方資料與系統計算結果同時存在，先做校驗，不要挑「比較符合人生事件」的版本直接使用。

固定保留三層；系統內部代碼如下：

```text
External / Project / Resolved
```

比較狀態：

```text
MATCH / EQUIVALENT / CONFLICT / NOT_COMPARABLE
```

簡單說：

- **第三方來源**：第三方原本提供什麼，就保存什麼。系統內部代碼為 `External`。
- **系統計算結果**：Metaphysics Lab 按固定規則自行計算的結果。系統內部代碼為 `Project`。
- **已校驗採用結果**：經校驗後，明確記錄目前採用哪一個來源，以及是否仍有差異。系統內部代碼為 `Resolved`。

已校驗採用結果不能把原本的 `CONFLICT`（衝突）改寫成 `MATCH`（一致）。

校驗結果可以進入該命主的 `02` 正式檔位，例如：

```text
Alex_7F3A2C_02_命盤資料校驗紀錄.md
```

## 八、第一次建立個案資料

新建個案資料採**漸進式個案結構（Progressive Case）**：第一次有足夠的本命資料來源或合法的候選盤面集合時，先建立基礎個案資料。

虛構命主 Alex：

```text
Alex_7F3A2C_00_專案索引.md
Alex_7F3A2C_01_命盤核心摘要.md
Alex_7F3A2C_02_命盤資料校驗紀錄.md
Alex_7F3A2C_03_八字結構化資料包.md
Alex_7F3A2C_04_紫微基礎資料包.md
```

內部正式檔位仍是：

```text
00_專案索引.md
01_命盤核心摘要.md
02_命盤資料校驗紀錄.md
03_八字結構化資料包.md
04_紫微基礎資料包.md
```

若本次另外保留 Astralium，可再看到例如：

```text
Alex_7F3A2C_03-1_Astralium八字資料包.md
Alex_7F3A2C_04-1_Astralium紫微資料包.md
```

這兩份不屬於正式檔位，不改變基礎個案資料 00～04 的正式結構。

如果是 `partial` 本命資料，個案資料必須把「已確定盤面」「候選依賴盤面」「目前不可唯一判定」分開，不能因個案資料已建立就把尚未確定的結論當成已解鎖。

## 九、05～08 需要時才建立

後續有實際內容時才建立：

```text
Alex_7F3A2C_05_驗證事件紀錄.md
Alex_7F3A2C_06_流年追蹤紀錄.md
Alex_7F3A2C_07_問事追蹤紀錄.md
Alex_7F3A2C_08_重大決策紀錄.md
```

- `05`：已驗證事件與歷史盲測校準
- `06`：值得永久追蹤的流年／年度預測
- `07`：值得永久追蹤的一般問事
- `08`：重大決策紀錄

第一版盲判一旦正式記錄並鎖定，不得事後覆寫；實際結果只能追加。

## 十、歷史盲測校準

過去 10 年的**歷史盲測校準（Historical Blind Calibration）**是**建議但非強制**的個人化校準步驟。完成後可以增加「同類盤面訊號在這位命主身上通常怎麼落地」的證據；使用者不做或稍後再做，也不會讓個案資料失效。

**未校準仍可直接進入**本命分析、個人化未來趨勢、流年、問事或重大決策。系統內部若顯示 `Historical Calibration = uncalibrated`，**不影響排盤本身的正確性**；差別是**個人化落地形式與信心校準會少一層證據**。回答時要明確說明這個限制，不得把未校準分析包裝成已完成事件驗證。

使用者選擇校準時，仍必須遵守歷史盲測校準的防污染順序：

```text
resolve subject
↓
先用基礎個案資料完成第一階段盲判並鎖定
↓
歷史盲測與使用者驗證
↓
寫入已確認事件
↓
第二階段事件校準
```

如果候選盤面集合仍無法支持單一命盤個人化預測，不能為了進校準流程而偷偷選一個候選時辰。

`05` 內要分開：

- `blind_prediction`＝命理推論
- `user_confirmed_actual`＝**已驗證事件**
- `evaluation`＝**已校驗資料**

不得把盲測假說直接當成已驗證事件。

## 十一、Metaphysics Lab 的八種資料類型

所有資料永遠區分：

1. **原始盤面事實**：第三方來源直接提供的欄位。
2. **已校驗資料**：校驗結果、驗證結果、校準評價。
3. **專案原生命盤**：由出生資料經固定本命計算引擎建立的本命計算。系統內部分類值仍為 `Project 原生盤面`。
4. **專案推導盤面**：由本命／運限／目標時間經固定算法建立的衍生時間層。系統內部分類值仍為 `Project 推導盤面`。
5. **已驗證事件**：使用者確認真正發生過的事件。
6. **命理推論**：AI 對盤面的事件、趨勢與策略解讀。
7. **研究假說**：尚未正式納入已校驗算法的研究想法。
8. **當次現實背景**：工作、財務、家庭、決策條件等現況。

資料越多不代表越好；來源與證據層級混在一起，反而會讓分析無法驗證。

## 十二、最低使用路徑

```text
metaphysics_lab.py
metaphysics_core.md
Project Instructions
↓
讀／建立 命主索引.md
↓
提供出生資料和／或結構化第三方命盤
↓
完整時間 → 建立專案原生命盤
不確定時間 → `natal.candidate_envelope`／`partial`
只有第三方 → 建立第三方來源資料
↓
建立基礎個案資料
↓
可直接分析；視需要再做歷史盲測校準
↓
依實際需要逐步建立追蹤紀錄
```

如果當次環境無法執行 Python，AI 必須明講，不能用文字模擬成「已排盤」「已展開候選」或「已驗證」。

私人 `命主索引.md`、出生資料、人生事件、Astralium 原始命盤資料、PDF 與截圖不應提交到公開／共用 GitHub 儲存庫。
