# 命盤資料準備指南

本文件說明建立新的 Metaphysics Lab 私人 Case 時，應準備哪些資料、哪些資料不足時必須降級，以及 Case 會在什麼時候建立各類紀錄。

固定原則：

> **Precision must be earned by input.**
>
> 不知道的資料就保留未知；不得為了排出完整命盤而自行補出生時間、出生地、性別、四柱或其他缺值。

目前 capability implementation、maturity、routing、required inputs 與 rule version 一律以 `runtime_info` 為執行真相；本文件不另外維護容易過期的能力快照。

---

## 一、完整 Project 本命需要哪些出生資料

目前 runtime 要建立單一完整 Project 本命，通常需要：

- 性別
- Gregorian／西元出生日期
- 原始出生時間
- 出生地

出生地解析後還會保留座標、IANA timezone 與 provenance；真太陽時、子時換日等時間口徑由正式 time profile 處理，不由 AI 自由補算。

建議另外保留：

- 出生時間來源，例如出生證明、戶籍資料或家人記憶
- 出生時間可信度
- 是否只有大概時段，例如清晨、上午、下午、晚上
- 第三方排盤是否使用真太陽時或其他特殊時間口徑

### 如果缺少出生時間

若使用者缺少出生時間，**不得自行補一個時辰**。

目前 runtime 的 `bazi_static`、`bazi_natal`、`ziwei_natal` 與完整 natal 路徑仍要求可唯一解析的出生時間，因此只知道日期與出生地時，**不能建立單一完整 Project 本命**；時間範圍跨越多個可能時辰時，也不能偷偷取中間值。

這不代表所有資料都完全不能用：

- 若使用者已有可信第三方八字／紫微結構化資料，可以只匯入來源實際提供的欄位，建立 External view；不得把來源缺少的欄位補齊。
- 若已知四柱，可建立 Bazi external/imported view；不得反推成唯一 civil 出生時間，也不得因此重建完整 Ziwei natal。
- 若只有出生日期、地點與大概時段，可以先保留候選範圍與不確定性，做不依賴未知時辰的資料整理；目前不得把這類結果冒充完整 Project 原生盤面。
- 歷史事件未來可以用來比較候選時間的適配度，但那屬於校準／候選判別，不得把事件反推結果改寫成「原始出生時間事實」。

換句話說，目前產品可以誠實保留「部分已知、部分未知」，但還沒有一個正式的 partial natal runtime action 可以把未知時辰自動展開成候選命盤集合。

## 二、第三方八字資料

若使用 Astralium、其他排盤網站、命理軟體或命理師資料，建議至少保留來源實際提供的：

- 年柱、月柱、日柱、時柱
- 日主
- 藏干
- 十神
- 八字大運
- 來源提供的流年資料
- 排盤系統名稱
- 產出日期／版本（若可取得）
- 子時換日口徑
- 真太陽時、時區或其他時間設定

來源若另外提供格局、身強弱、喜用神、五行統計、神煞或干支互動，也可以完整保留，但要維持來源原貌。

不要把 AI 後續推論的格局、喜用或事件解讀反寫成原始排盤欄位。

第三方直接提供的欄位屬於 **原始盤面事實**；如果 Project 依出生資料另外重算，兩者要保留為 External / Project 分離的 raw views，再經 reconciliation 形成 Resolved view。

## 三、第三方紫微資料

建議保留來源實際提供的：

- 十二宮
- 各宮星曜
- 命宮
- 身宮
- 命主／身主（若來源有提供）
- 生年四化
- 自化／飛化（若來源有提供）
- 紫微大限
- 小限
- 流年命宮
- 流年四化／飛化（若來源有提供）
- 排盤系統與時間口徑

不要依固定文件猜「目前 Project 會不會算某一層紫微流月／流日／流時／四化／飛化／流曜」。需要建立 deterministic 時間層時，先讀 `runtime_info`，只使用當次 runtime 宣告可執行、required inputs 也完整的 capability。

Project 自己算出的本命 deterministic facts 是 **Project 原生盤面**；由本命、運限與目標時間再建立的細時間層才是 **Project 推導盤面**。兩者都不得冒充第三方原始資料。

## 四、命盤校驗與 External / Project / Resolved

如果第三方資料與 Project 重算資料同時存在，先做 reconciliation，不要挑「比較符合人生事件」的版本直接使用。

固定保留：

```text
External / Project / Resolved
```

比較狀態：

```text
MATCH / EQUIVALENT / CONFLICT / NOT_COMPARABLE
```

嚴重度：

```text
INFO / CAUTION / BLOCKING
```

常見需要核對的項目包括：

- 出生資料與時間口徑
- 四柱
- 真太陽時是否造成實質盤面差異
- 紫微命宮／身宮
- 八字大運／紫微大限
- 查詢年份與運限層級

校驗結果進入 `02_命盤資料校驗紀錄.md`。Resolved 只是可追溯的 authority selection，不能把原本的 CONFLICT 改寫成 MATCH。

## 五、第一次建立 Case：只建立 00～04

新 Case 採 Progressive Case。第一次有足夠 natal source 可以建立 Case 時，只 materialize Base Case：

```text
00_專案索引.md
01_命盤核心摘要.md
02_命盤資料校驗紀錄.md
03_八字結構化資料包.md
04_紫微基礎資料包.md
```

`00_專案索引.md` 是 manifest，記錄目前已存在的 Case files 與 Historical Calibration 狀態。

本命分析可以在 Base Case 建立後先使用；不需要為了「看起來完整」預先建立空白 05～08。

## 六、05：驗證事件與 Historical Blind Calibration

`05_驗證事件紀錄.md` 不在新 Case 初始化時先建立。

它在第一次真的有可保存的已驗證事件／Historical Blind Calibration 結果時才 materialize。

對第一次個人化未來趨勢、流年或重大決策，在 Historical Calibration 尚未完成時，流程固定為：

```text
Base Case 00～04
↓
先鎖定這次未來問題的 Stage 1 盲判
↓
Historical Blind Calibration
↓
使用者驗證／訂正
↓
首次 materialize 05
↓
Stage 2 事件校準
```

因此，新使用者可以先建立命盤與做本命分析，但不能因為「還沒有自己整理過歷史事件」就跳過第一次未來問事前的 Historical Blind Calibration gate。

05 內若保存 Historical Calibration ledger，必須分開：

- `blind_prediction`＝命理推論
- `user_confirmed_actual`＝已驗證事件
- `evaluation`＝已校驗資料

不得把盲測假說直接寫成已驗證事件。

## 七、06～08：需要時才建立

以下都屬 Progressive Records：

```text
06_流年追蹤紀錄.md
07_問事追蹤紀錄.md
08_重大決策紀錄.md
```

- `06`：第一次有值得永久追蹤的年度／半年／月份預測時建立。
- `07`：第一次有值得永久追蹤的一般問事時建立；普通聊天不必每題都存。
- `08`：第一次有重大決策紀錄時建立。單一重大決策通常優先記 08，不為了湊檔案而同時複製到 07。

第一版 blind forecast 一旦寫入追蹤紀錄，不得事後覆寫；實際結果只能追加。

## 八、Metaphysics Lab 的八種資料類型

所有資料永遠區分：

1. **原始盤面事實**：第三方來源直接提供的原始欄位。
2. **已校驗資料**：reconciliation、驗證結果、校準評價等已完成校驗的資料。
3. **Project 原生盤面**：由出生資料經目前 runtime 固定 Natal Engine 建立的本命 deterministic facts。
4. **Project 推導盤面**：由本命／運限／目標時間經固定算法建立的衍生時間層與 Historical Activation selection。
5. **已驗證事件**：使用者確認真正發生過的事件。
6. **命理推論**：AI 對盤面的事件、趨勢與策略解讀。
7. **研究假說**：尚未正式納入已校驗算法或盤面事實的研究性想法。
8. **當次現實背景**：使用者這次提供的工作、財務、家庭、決策條件等現況。

這個分類比「資料越多越好」更重要。資料來源與證據層級混在一起，後面的分析就無法可靠驗證。

## 九、最低使用路徑

一般新使用者不需要手工複製全部 template。標準流程是：

```text
metaphysics_lab.py
METAPHYSICS_CORE.md
Project Instructions
↓
提供可用出生資料／structured external chart
↓
runtime 建立或校驗 natal
↓
建立 Base Case 00～04
↓
本命分析可先使用
↓
第一次未來／流年／重大決策前完成 Historical Blind Calibration
↓
05～08 依真實使用情境逐步 materialize
```

如果當次環境無法執行 Python，AI 必須明講，不能用文字模擬成「已排盤」或「已驗證」。

## 十、長期保存原則

長期使用時，私人 Project 可逐步保留：

```text
00_專案索引.md
01_命盤核心摘要.md
02_命盤資料校驗紀錄.md
03_八字結構化資料包.md
04_紫微基礎資料包.md
05_驗證事件紀錄.md（若已 materialize）
06_流年追蹤紀錄.md（若已 materialize）
07_問事追蹤紀錄.md（若已 materialize）
08_重大決策紀錄.md（若已 materialize）
第三方原始／結構化資料
必要的研究筆記
```

私人出生資料與人生事件不應提交到公開／共用 GitHub repo。共用 repository 只保存規則、引擎、測試、qualification 與非私人模板。
