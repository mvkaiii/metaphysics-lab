# 中文使用者文件語言規範

## 目的

本規範用來避免中文使用者文件出現不必要的中英夾雜，也就是常說的「晶晶體」。

原則不是禁止英文，而是區分：

- **正式識別字**：應保留，避免翻譯後失去技術精度。
- **一般敘述**：若有自然、清楚、不失真的台灣繁體中文，就應使用中文。

## 適用範圍

以下內容視為使用者文件，應遵守本規範：

- `README.md`
- `docs/快速開始.md`
- `docs/安裝到ChatGPT-Project.md`
- `docs/更新與版本同步.md`
- 最新正式版本的 `docs/發布說明-vX.Y.Z.md`
- 其他直接提供給一般使用者閱讀的說明
- 對一般使用者輸出的版本摘要、升級說明與操作指引

歷史工程紀錄、測試資料、研究紀錄、API說明、程式碼與精確技術稽核文件可以保留必要英文，不要求為了表面中文化而破壞正式名稱或可追溯性。

## 可以保留英文的情況

以下內容可以保留原文：

1. 程式識別字、函式名稱、欄位名稱、狀態值與命令，例如 `runtime_info`、`natal_revision_id`。
2. 檔名、路徑、版本號、雜湊值與命令列內容。
3. 正式規格或功能名稱，例如 Project Contract、Case Schema、Candidate Envelope v2。
4. 品牌、產品或平台名稱，例如 GitHub、Python。
5. 沒有自然中文替代，或翻譯後反而會造成歧義的專有術語。

正式名稱第一次出現時，優先採「中文名稱（英文正式名稱）」；後續敘述以中文為主。

## 不應保留英文的情況

一般名詞、動詞、形容詞或流程描述，只要有自然中文說法，就應翻成中文。

例如：

| 不建議 | 建議 |
|---|---|
| 流程 authority | 流程的正式依據／判定依據 |
| release 本身 | 版本發布本身 |
| Stable promotion | 成熟度升級為 `stable` |
| capability maturity | 功能成熟度 |
| routing | 啟用方式／路由方式 |
| material state | 實際盤面狀態 |
| revision identity | 修訂版本識別 |
| revision lineage | 修訂版本沿革 |
| prospective lock | 前瞻預測鎖定紀錄 |
| blind lock | 盲判鎖定紀錄 |
| readable | 仍可讀取 |
| deterministic SVG | 依固定規則產生的 SVG |
| schema migration | 資料結構移轉 |
| clean tree | 工作目錄乾淨狀態 |
| regression | 回歸測試 |
| smoke test | 基本啟動驗證 |

## 撰寫規則

1. 中文句子以台灣繁體中文完整表達，不把英文普通詞直接當中文文法成分。
2. 技術識別字優先放在反引號中，正文先說明它的中文意義。
3. 不因內部PR、spec、測試名稱使用英文，就直接把相同字串搬進使用者文件。
4. 不為了「看起來專業」保留可自然翻譯的英文。
5. 不要求把正式API、欄位、狀態值或版本識別硬翻成中文。
6. 發布說明送出前必須做一次「自然中文檢查」：確認一般敘述中沒有仍可自然翻譯的英文詞。

## 自動檢查

測試會對**最新正式版本的發布說明**做基本檢查：

- 忽略程式碼區塊與反引號中的正式識別字。
- 允許已知正式名稱。
- 對常見晶晶體詞組與未核准的一般英文詞提出失敗。

自動檢查只是一道底線，不取代人工審閱。若新的正式名稱需要保留英文，應明確加入允許清單；不要直接放寬整個規則。
