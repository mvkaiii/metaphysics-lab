# 資料治理

Metaphysics Lab 把共用系統規則與私人 Case 資料分開管理。所有分析資料都必須保留來源、證據層級、命主 identity 與可追溯性；不得為了讓命理解讀看起來一致而混用不同資料類型或不同命主。

> 以下姓名與識別碼皆為虛構示例。

## 系統核心與私人資料分離

本儲存庫只保存共用規則、引擎、測試、qualification 與非私人模板。

私人 `命主索引.md`、Case、出生資料與人生事件不應提交到本儲存庫。

## Project-level Subject Registry

`命主索引.md` 是 Project-level **Subject Registry**，用途只限命主 discovery / display。Registry 的正式資料最小化原則是只保存 **discovery/display metadata**，例如：

- opaque `subject_id`
- `subject_short_id`
- `subject_display_name`
- `filename_label`

Registry **不保存出生資料**，也**不保存人生事件**、Historical Calibration 回答、命盤內容、健康／財務／家庭紀錄。

`subject_id` 必須由 opaque random identity 建立，不得由姓名、生日、出生地或其他 PII derive。同名命主可以共存，靠不同 `subject_id` 區分；rename 不改 `subject_id` / `subject_short_id`。

如果某位命主已有 Case，rename 必須一次同步 registry、該 subject 的所有 materialized filenames、front matter、00 manifest 與 old → new mapping；不能只改 `命主索引.md`。

## Case identity 與 filename

Case 內部仍以00～08的 **canonical slot** 識別 record type，例如 `01_命盤核心摘要.md`。Case Schema 1.1 實際 persisted filename 固定是：

```text
<filename_label>_<SUBJECT_SHORT_ID>_<slot>_<canonical_title>.md
```

虛構範例：

```text
Alex_7F3A2C_01_命盤核心摘要.md
```

canonical slot 與 persisted filename 必須分開。這讓多人 Case 可以放在同一個 Project，又不污染 runtime 內部 schema。

## 不應提交的私人資料

- 真實 `命主索引.md`
- 真實姓名與可識別資料
- 真實出生年月日時與出生地
- 個人八字、紫微原始資料包
- Candidate Envelope / partial Case 個案結果
- Historical Blind Calibration 的私人回答
- 醫療事件
- 家庭事件
- 工作與收入事件
- 資產與投資事件
- 感情與婚姻事件
- 真實問事紀錄
- 重大決策紀錄

私人 qualification 若需要留證據，只能保存規範允許的 aggregate counts、status、digest 等去識別化結果，不提交 raw Case payload。

## 八種資料類型

Metaphysics Lab 固定區分：

1. **原始盤面事實**
2. **已校驗資料**
3. **Project 原生盤面**
4. **Project 推導盤面**
5. **已驗證事件**
6. **命理推論**
7. **研究假說**
8. **當次現實背景**

### 原始盤面事實

Astralium、其他排盤系統、PDF、結構化資料包等第三方來源直接提供的欄位屬於原始盤面事實。

保留來源原貌與 provenance；不得把後續 AI 解讀反寫成來源欄位。

### 已校驗資料

資料校驗、External / Project reconciliation、Historical Calibration evaluation，以及其他已完成驗證／比較的結果屬於已校驗資料。

已校驗資料描述「資料之間如何比對、校準結果如何」，不是第三方原始輸出，也不是人生事件本身。

### Project 原生盤面

由使用者出生資料經目前 runtime 固定 Natal Engine 建立的本命 deterministic facts 稱為 Project 原生盤面。

Candidate Envelope 也是 Project deterministic natal foundation 的候選集合，但在 `bounded` / `unknown_time` 狀態下不能把任何候選冒充唯一盤。

### Project 推導盤面

由本命、運限與目標時間經目前 runtime 固定算法產生的衍生時間層稱為 Project 推導盤面。

例如正式 runtime 輸出的流年／流月／流日／流時 context、Historical Activation evidence / canonical selection 等。實際可使用哪些能力一律以 `runtime_info` 為目前執行真相。

### 已驗證事件

只有真正已發生、並由使用者或可信紀錄確認的事情，才可稱為已驗證事件。

未來計畫、命理推論、盲測假說與預測不得提前寫成已驗證事件。

### 命理推論

AI 對盤面做出的趨勢、事件類型、策略與風險解讀屬於命理推論。

命理推論即使事後吻合，也不能反向改寫成原始盤面事實。

### 研究假說

尚未納入正式、已校驗 deterministic contract 的研究性規則或觀察屬於研究假說。

不得因單一案例吻合就升格為 Project 原生盤面或 Project 推導盤面。

### 當次現實背景

使用者當次提供的工作、財務、家庭、合作、時間、資源與決策條件屬於當次現實背景。

重大決策時，現實背景具有最高實務權重；命盤與推導盤面提供趨勢與風險參考，不取代現實條件。

## Candidate Envelope 的不確定性治理

出生時間未知或只有範圍時，`natal.candidate_envelope` 必須保存「不知道」本身，不得用假精度消除不確定性。

固定治理規則：

- 不使用 midpoint 或 default time。
- 逐分鐘 evaluate uncertainty interval，再將相鄰且 deterministic discrete chart structure 相同的分鐘壓成 material state。
- 只有**所有** candidates 都一致的 nested fact 可標為 invariant。
- 任何不一致的 nested fact 都保留為 candidate-dependent；不用 majority voting。
- Bazi 起運 datetime 等連續量保存 range。
- `bounded` / `unknown_time` 即使只有1個material state，仍不得自動解鎖 unique birth time、unique hour pillar、unique Ziwei natal、single-chart personalized forecast 等 blocked scopes。

Candidate Envelope 建立的 Base Case 必須標為 `partial`，不得輸出成唯一 `NormalizedNatalChart`。

## External / Project / Resolved 不互相覆寫

第三方 external chart 與 Project deterministic chart 必須分開保存：

```text
External / Project / Resolved
```

Resolved 是 authority policy 下的可追溯選擇，不是新的原始來源。

即使 Resolved 選擇其中一邊，原本的 MATCH / EQUIVALENT / CONFLICT / NOT_COMPARABLE 與 INFO / CAUTION / BLOCKING 都應保留；不得把 CONFLICT 改寫成 MATCH。

## Historical Blind Calibration 的資料分層

Historical Blind Calibration 的一筆 ledger record 內至少要維持三種不同語意：

- `blind_prediction`＝**命理推論**
- `user_confirmed_actual`＝**已驗證事件**
- `evaluation`＝**已校驗資料**

原始 blind prediction 一旦鎖定不得事後覆寫。使用者訂正的實際事件應追加保存，而不是拿來重寫原假說。

`cannot_recall` 屬 unscorable，不得被寫成事件不存在，也不能為了完成評分逼使用者猜日期。

Stage 1 source allowlist 以 canonical slot 判斷，只能是該 subject 的00～04；實際 key 可例如：

```text
Alex_7F3A2C_01_命盤核心摘要.md
```

05～08不得混入 blind Stage 1。

## Progressive Case 的資料生命週期

新 Case schema 1.1 初始化只 materialize Base5：

```text
Alex_7F3A2C_00_專案索引.md
Alex_7F3A2C_01_命盤核心摘要.md
Alex_7F3A2C_02_命盤資料校驗紀錄.md
Alex_7F3A2C_03_八字結構化資料包.md
Alex_7F3A2C_04_紫微基礎資料包.md
```

Progressive4：05～08只有第一次真正有對應內容時才建立。

不要為了讓 Case 看起來完整而預先建立空白 lifecycle records，也不要因 schema 升版刪除 Legacy Case 1.0 已存在的合法檔案。Legacy bare filename 九檔仍可讀；1.1 不要求 destructive rename 才能使用。

## 多人資料隔離

每個命主必須有自己的 `subject_id` 與 Case。多人／合盤時先 resolve 每位 subject，再分別讀取個別盤面與事件，最後才分析互動。

不得混用不同人的：

- 四柱
- 紫微宮位
- 八字大運
- 紫微大限
- Project 原生／推導盤面
- Candidate Envelope
- 驗證事件與追蹤紀錄

## 核心原則

> 來源要保留，命主要隔離，分類要分開，不確定性要保留，推論不能冒充事實，歷史紀錄不能事後改寫。

若文件對某個 capability 的「目前是否可用」與 runtime 狀態不同，以 `runtime_info` 為目前執行真相；固定文件負責治理原則，不保存容易過期的 capability 快照。
