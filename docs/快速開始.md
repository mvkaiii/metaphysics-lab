# 快速開始

這份文件給第一次使用 Metaphysics Lab 的人。正式 release identity 目前仍為 v1.2.0；以下同時說明 **Unreleased Phase 2C0｜Natal Chart Foundation** 的使用方式。

建議搭配：

- [安裝到 ChatGPT Project](安裝到ChatGPT-Project.md)
- [命盤資料準備指南](命盤資料準備指南.md)
- [Astralium 資料取得指南](Astralium資料取得指南.md)
- [更新與版本同步](更新與版本同步.md)

---

## 1. 最簡單的建立命盤方式｜Mode A

直接提供：

- 性別
- Gregorian 出生日期
- 出生時間
- 出生地

例如：

> 男，1984年3月13日19:20，台北市出生

Phase 2C0 可以由出生資料建立 Project 原生八字與 Project 原生紫微，不要求使用者一定先去 Astralium 排盤。

目前 `bazi.natal_chart` 與 `ziwei.natal_chart` 都是 **implemented / Experimental / on_demand**，因此可以執行，但仍需保留 profile、validation 與 qualification 狀態；不要把 Experimental 說成 Stable。

### 只追問缺少欄位

若使用者說：

> 1990年5月6日，高雄出生

已知出生日期與出生地，就只追問缺少的：

- 性別
- 出生時間

不要要求對方重新輸入整份資料。

固定原則：

> **Precision must be earned by input.**

輸入不足時，只能追問、保留候選或降級分析，不得自行補值。

### 模糊時間

若使用者說：

> 大概晚上7、8點

不得自行取 19:30 或其他中點。如果候選範圍跨越會改變時辰／日柱／命宮等核心盤面的邊界，保留候選盤或追問；若所有候選在目前 profile 下產生相同核心盤面，可在該精度下繼續並保留 provenance。

## 2. 已知四柱｜Mode B

若使用者只有已知四柱，可建立 Bazi imported/external natal view，用於八字本命與可由四柱直接支持的分析。

不能因為知道四柱，就反推出唯一的 civil 出生年月日時，也不能可靠重建完整 Ziwei natal。需要完整紫微本命時，仍應提供實際出生日期、出生時間、出生地與性別。

---

## 3. 有 Astralium 或其他第三方資料｜Mode C

Astralium 為可選 external qualification source，不是建立 Project 命盤的必要 runtime dependency。

若同時有出生資料與 Astralium structured chart：

1. External view 保留 Astralium／第三方欄位。
2. Project view 由 Metaphysics Lab deterministic engine 獨立計算。
3. 兩者做 field-level reconciliation。
4. Resolved view 依 authority policy 選擇供下游使用的值。

固定三層：

`External / Project / Resolved`

固定比較狀態：

`MATCH / EQUIVALENT / CONFLICT / NOT_COMPARABLE`

External / Project raw views 不互相覆寫。

---

## 4. 出生時間與真太陽時

一般使用者只要輸入出生地名稱，不需要自己找經緯度或 IANA timezone。

Location Resolver 解析地點；Calendar Resolver 建立 neutral civil/calendar context。Calendar Resolver 不負責真太陽時。

Phase 2C0 至少保留：

```text
reported_civil_time
normalized_civil_time
bazi_effective_time
ziwei_effective_time
```

Ziwei Natal ordinary UX 使用 Project default true-solar profile；使用者不必自行選「是否真太陽時」。原始 civil time 一定保留。

只有時間校正真的跨越會改盤的時辰／日期邊界時，才需要明確提示「排盤差異需要確認」。若只是分鐘差且核心盤面相同，可標為 EQUIVALENT。

---

## 5. Project 原生盤面 vs Project 推導盤面

- 出生資料 → Project deterministic Natal Engine → **Project 原生盤面**。
- 本命／運限＋未來目標時間 → 流年／流月／流日／流時等 → **Project 推導盤面**。
- 對兩者的解讀 → **命理推論**。

不得把 Project 原生盤面或 Project 推導盤面說成 Astralium 的直接輸出。

---

## 6. Canonical Markdown export

Phase 2C0 的 Markdown exporter 只輸出 structured facts，不會重新排盤，也不會偷偷加入命理解讀。

可輸出本命摘要、Bazi facts、Ziwei facts、External/Project/Resolved reconciliation、time basis、profile、validation 與 provenance。

相同 structured input + 相同 generated date 必須產生 byte-identical Markdown。

## 8. 第一次分析建議順序

1. 確認 `命理分析作業規範.md` 可讀。
2. 確認出生資料與 Input Resolution 狀態。
3. 建立／匯入 External 與 Project natal views。
4. 查看 reconciliation 是否有 BLOCKING conflict。
5. 再建立 `命盤核心摘要.md`。
6. 本命分析完成後，再進流年／問事。
7. 未來問題採先盲判、後事件校準。

如果本命仍有 BLOCKING 時間／四柱／命宮衝突，不應直接把高精度細運當成確定基礎。

## 9. Python 與 ChatGPT Project

把 `.py` 放進 Project 代表保存正式算法來源，不代表每個 ChatGPT 對話都會自動執行 Python。

若當次環境能執行，才可宣稱程式已計算；不能執行時，只能讀規則／程式，不得假裝已跑過。

---

## 10. 私人資料

個人出生資料、Astralium raw chart、PDF、截圖與私人事件不要提交回共用 GitHub repo。

Qualification 只應提交 public/synthetic cases、aggregate counts、digest、版本與 status。私人 Astralium evidence 只保留 aggregate summary；raw payload 不進 repo。
