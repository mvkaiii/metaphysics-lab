# 架構說明

Metaphysics Lab v1.2.0 將命理分析拆成七種資料類型：

1. 原始盤面事實
2. 已校驗資料
3. Project 推導盤面
4. 已驗證事件
5. 命理推論
6. 研究假說
7. 當次現實背景

這七層不能互相冒充。尤其 Project 自己算出的流月、流日、流時、四化或飛化結果，不得包裝成 Astralium 或其他第三方原始輸出。

---

## 資料流

```text
原始盤面 → 資料校驗 → 本命模型 ───────────────┐
                                               ↓
使用者問題 → Input Resolution / Precision Gate → 必要時 Calendar Resolver
                                               ↓
                                  CalendarContext / 各體系 adapter
                                               ↓
                                  固定算法建立時間層級
                                               ↓
                                       第一階段盲判
                                               ↓
                                       鎖定原始預測
                                               ↓
                                    第二階段事件校準
                                               ↓
                                      現實策略與底線
                                               ↓
                                      事後結果驗證
```

Input Resolution / Precision Gate 先判斷 target capability 所需最低時間精度。輸入不足或不唯一時只能追問、保留候選或降級，不得為了讓下游 API 能跑而補假日期、假時間或假 timezone。

---

## Capability 三軸模型

```text
implementation = planned / implemented
maturity       = experimental / stable
routing        = default / on_demand
```

三個欄位分開解讀：

- `implemented`：程式能力存在。
- `stable`：已達既定 promotion gate。
- `experimental`：可執行，但證據權重較低。
- `default`：一般符合條件時可預設執行。
- `on_demand`：只有問題需要更高解析度或明確指定時才執行。

`on_demand` 不等於「不存在」，`implemented` 也不等於「每次都要跑」。

## Calendar Resolver v1

Calendar Resolver 是 system-neutral 的民用時間／曆法 context 層，不屬於八字或紫微本身。

正式模組：

```text
engine/calendar/precision.py
engine/calendar/models.py
engine/calendar/timezone.py
engine/calendar/lunar.py
engine/calendar/resolver.py
```

責任：

- structured local civil datetime + IANA timezone 正規化
- DST nonexistent / ambiguous local time contract
- Gregorian civil date
- Gregorian → Lunar
- hour branch
- provider provenance 與 validation metadata
- 產出 `CalendarContext`

固定 runtime：

```text
lunar-python==1.4.8
tzdata==2026.3
IANA 2026c
```

固定 qualification / validation：

```text
HKO exhaustive validated range = 1901-01-01..2100-12-31
2057-09-28..2057-10-27 = boundary_conflict
2089-09-04 / 2097-08-07 = boundary_caution
```

Resolver civil date 只在 `00:00` 換日；23:00 已屬子時，但 `metaphysics_day_boundary_applied = false`。八字 early-Zi 規則仍由八字引擎負責；紫微 23:00 命理日界尚未固定。

Resolver 不負責：

- 自然語言日期解析
- timezone 猜測
- 真太陽時
- 八字換日 policy
- 紫微 23:00 school policy
- Qimen

## 八字與紫微分工

### 八字

正式模組：

```text
engine/bazi/calendar.py
```

主要責任：

- 本命底層結構
- 八字大運／流年

- 十神

八字流月採節氣月。

### 紫微

主要責任：

- 十二宮與星曜
- 生年四化
- 本命宮干飛化
- 大限／流年
- 流月／流日／流時宮位定位
- 已達 stable gate 的 Transformation / Flying Core

紫微流月採農曆月，初一換月；閏月採初一至十五歸原月、十六起歸下一月。

八字與紫微的月界不同是正常設計，不是 bug。

## Ziwei Transformation & Flying Core v1

### Transformation Core

```text
heavenly_stem + profile_id
→ TransformationSet
```

第一版 profile：

```text
metaphysics-lab-common-v1
```

Transformation Core 不知道某個天干屬於生年、大限、流年、流月、流日或流時；它只回答該天干對應哪四個祿／權／科／忌。

### Natal basis

```text
StarLocationRecord[] → StarLocationIndex
PalaceStemRecord[]    → PalaceStemIndex
```

builder 採 record-first 驗證，duplicate / conflict 在 materialization 前 fail closed，避免 Python dict last-write-wins 吃掉矛盾資料。

### Flying Core

```text
TransformationSet
+ StarLocationIndex
+ explicit source
→ FlyingEdge[]
```

第一版 target basis 只允許 `natal_star_location`，不重新安星。

Palace source 的底層 geometry：

```text
same_palace
opposite_palace_incoming
normal
```

Astralium-compatible presentation：

```text
same_palace              → ↓ / 離心自化
opposite_palace_incoming → ↑ / 向心自化
```

`↑/↓` 是 presentation，不是 core primitive。

### NatalFlyingGraph

十二宮宮干各產生四條 edge，因此本命 graph 固定：

```text
12 × 4 = 48 edges
```

### Composition

```text
NatalContext
├─ birth_year_layer
└─ natal flying graph

ZiweiLayerStack
└─ cycles
   ├─ decadal
   └─ yearly
```

不同 scope 同時存在但不互相覆寫。同一 layer identity 或 component 不一致時 fail closed。

Composition 不提供：

- `final_transformation`
- `resonance_score`
- `transformation_score`
- 自動吉凶排序
- AI interpretation
