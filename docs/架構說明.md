# 架構說明

Metaphysics Lab 將命理分析拆成七層：

1. 原始盤面事實
2. 已校驗資料
3. Project 推導盤面
4. 已驗證事件
5. 命理推論
6. 研究假說
7. 當次現實背景

## 資料流

```text
原始盤面
  ↓
資料校驗
  ↓
本命模型
  ↓
固定算法建立時間層級
  ↓
第一階段盲判
  ↓
鎖定原始預測
  ↓
第二階段事件校準
  ↓
現實策略與底線
  ↓
事後結果驗證
```

## 八字與紫微分工

八字主要負責底層結構與時間骨架；紫微主要負責十二宮、星曜、四化、飛化、大限、小限、流年與時間領域定位。

目前八字年月日時可由 Project 固定算法推導。紫微目前分成兩個成熟度層級：

- 流月定位：`implemented / stable / default`，包含斗君、流月命宮與流月十二宮。
- 流日定位：`implemented / experimental / on_demand`，包含流日命宮與流日十二宮；一般年度／月份問事不預設執行。

紫微流時、細部四化、流曜、細層飛化與 Cross-System Validation 正式引擎目前仍未實作。

月份邊界必須分開：八字流月採節氣月；紫微流月採農曆月，初一換月，閏月拆半。兩者不同步不是 bug。

## Capability 三軸模型

v1.2 將紫微細部能力拆成三個互相獨立的狀態：

```text
implementation = planned / implemented
maturity       = experimental / stable
routing        = default / on_demand
```

因此「預設不跑」不等於「沒有能力」。例如紫微流日已可由 Python 執行，但因目前成熟度為 Experimental，分析時必須降權，而且只在指定日期、日期比較或需要提高解析度時按需調用。

## Python 引擎模組

v1.2 將八字與紫微正式實作分開：

```text
engine/
├── bazi/
│   ├── __init__.py
│   └── calendar.py
├── ziwei/
│   ├── __init__.py
│   ├── common.py
│   ├── capabilities.py
│   ├── month.py
│   └── day.py
├── project_bazi_calendar.py
├── project_ziwei_month.py
└── project_ziwei_day.py
```

`engine/bazi/calendar.py` 負責八字流年、流月、流日、流時與天干十神等既有正式算法。

紫微部分：

- `engine/ziwei/common.py`：共用地支索引、十二宮名稱、輸入驗證與宮位重排 helper。
- `engine/ziwei/capabilities.py`：記錄 implementation / maturity / routing / rule version / dependency。
- `engine/ziwei/month.py`：Stable 流月定位。
- `engine/ziwei/day.py`：Experimental / On-demand 流日定位。

`engine/project_bazi_calendar.py`、`engine/project_ziwei_month.py` 與 `engine/project_ziwei_day.py` 保留作 compatibility wrapper（相容入口名稱），但 wrapper 不是獨立單檔引擎；若要實際執行，必須同時具備對應 package 依賴並保持同版。

後續紫微流時、細部四化、流曜、細層飛化與 Cross-System Validation 仍依「固定算法 → Python 實作 → 自動測試 → 外部校驗 → Experimental / Stable」流程逐項加入，不建立會讓人誤認為已實作的空殼功能。
