# 架構說明

Metaphysics Lab 將命理分析拆成七層：

1. 原始盤面事實
2. 已校驗資料
3. Project 推導盤面
4. 已驗證事件
5. 命理推論
6. 研究假說
7. 當次現實背景

## 資料流

```text
原始盤面 → 資料校驗 → 本命模型 ───────────────┐
                                               ↓
使用者問題 → Input Resolution / Precision Gate → 必要時 Calendar Resolver
                                               ↓
                                  CalendarContext / 各體系 adapter
                                               ↓
                                  固定算法建立時間層級
                                               ↓
                                       第一階段盲判
                                               ↓
                                       鎖定原始預測
                                               ↓
                                    第二階段事件校準
                                               ↓
                                      現實策略與底線
                                               ↓
                                      事後結果驗證
```

Input Resolution / Precision Gate 是時間輸入的上游 pure policy，不取代原始盤面、資料校驗或本命模型。它先判斷 target capability 的最低時間精度；精度不足時只能追問、保留候選或降級，不得為下游 API 補假日期／假時間。只有需要完整 civil datetime 的路徑才進 Calendar Resolver；自然語言解析在 Resolver 外。

## Calendar Resolver v1

Calendar Resolver v1 已在 v1.2 開發線實作，是 system-neutral 的民用時間／曆法 context 層。第一版責任只有：

- structured local civil datetime + IANA timezone 正規化；
- DST nonexistent / ambiguous local time contract；
- Gregorian civil date；
- Gregorian → Lunar provider；
- 時辰地支；
- provider provenance 與 validation metadata；
- 產出 `CalendarContext`。

第一版 `civil_datetime` 必須明確包含 local time，格式為 `YYYY-MM-DDTHH:MM[:SS[.ffffff]]`；date-only 輸入不合法，不得自動補成 `00:00`。若使用者只有 civil date，應由上游依 target capability 決定是否停在日級分析、追問時間或走其他較粗路徑，而不是為了呼叫 Resolver 補假時間。

固定 provenance / validation：

```text
runtime lunar = lunar-python 1.4.8
source revision = 000c8a3d74eed098d6256a28fdd51b869324c559
HKO exhaustive validated range = 1901-01-01..2100-12-31
2057-09-28..2057-10-27 = boundary_conflict
2089-09-04 / 2097-08-07 = boundary_caution
timezone = tzdata 2026.3 / IANA 2026c
timezone source revision = a44279419071b7aa41ebe7eca301ebb2e759571a
```

Resolver 的 civil date 只在 00:00 換日；23:00 已屬子時，但不改 civil date。`metaphysics_day_boundary_applied = false`。命理日界仍由各體系自己負責：八字既有 23:00 early-Zi 規則留在八字引擎；紫微不自動沿用八字規則；Qimen 未來另定。

第一版不負責自然語言解析、timezone 猜測、真太陽時、紫微 23:00 學派選擇、Bazi refactor 或 Qimen。

## 八字與紫微分工

八字主要負責底層結構與時間骨架；紫微主要負責十二宮、星曜、四化、飛化、大限、小限、流年與時間領域定位。

目前八字年月日時可由既有 Project 固定算法推導；本次 Calendar Resolver v1 **沒有 refactor Bazi**。紫微 timing capability：

- 流月定位：`implemented / stable / default`。
- 流日定位：`implemented / experimental / on_demand`。
- 流時定位：`implemented / experimental / on_demand`。
- Ziwei Calendar Adapter：`implemented`，以成功的 `CalendarContext` 原樣傳遞 lunar month/day/leap 與 hour branch 給既有 core。
- 十干四化核心：`implemented / stable / on_demand`；只處理天干→祿／權／科／忌，不自行解析細運天干。
- 飛化核心：`implemented / stable / on_demand`；使用已校驗 natal star location 建立 cycle edges 與 48-edge `NatalFlyingGraph`。
- 流月／流日／流時四化與細層飛化：`planned / on_demand`。
- 流曜：`planned / on_demand`。
- 十天干四化核心：`implemented / stable / on_demand`，profile `metaphysics-lab-common-v1`。
- 本命宮干／生年／大限／流年飛化核心：`implemented / stable / on_demand`；只使用已校驗本命星曜位置。
- 流月／流日／流時細運四化與飛化：`planned / on_demand`；Phase 2A 不建立細運天干。
- 流曜（moving stars）：`planned / on_demand`。

`boundary_conflict` 的 CalendarContext 不會被 Ziwei adapter 靜默當作正常可信日期；adapter 會拒絕執行。

月份邊界仍分開：八字流月採節氣月；紫微流月採農曆月，初一換月，閏月拆半。兩者不同步不是 bug。

## Capability 三軸模型

```text
implementation = planned / implemented
maturity       = experimental / stable
routing        = default / on_demand
```

「預設不跑」不等於「沒有能力」。Experimental 可以執行與累積驗證，但分析時必須降權。

`engine/bazi/calendar.py` 仍負責八字流年、流月、流日、流時與天干十神等既有正式算法，本次沒有 refactor。

紫微部分：

- `engine/ziwei/common.py`：共用地支索引、十二宮名稱、輸入驗證與宮位重排 helper。
- `engine/ziwei/capabilities.py`：記錄 implementation / maturity / routing / rule version / dependency。
- `engine/ziwei/errors.py` / `models.py`：Phase 2A stable error contract 與 immutable typed models。
- `engine/ziwei/basis.py`：由 records 驗證並建立 duplicate-safe natal star / palace-stem indexes。
- `engine/ziwei/transformation_profiles.py` / `transformations.py`：版本化十天干四化規則與純 transformation core。
- `engine/ziwei/flying.py`：四化星落宮、12×4 natal flying graph、宮位幾何 relation；`↑/↓` 僅在 presentation 層映射。
- `engine/ziwei/composition.py`：保留 birth-year／decadal／yearly layers，不覆寫、不評分；同 layer 衝突 fail closed。
- `engine/ziwei/month.py`：Stable / Default 流月定位。
- `engine/ziwei/day.py`：Experimental / On-demand 流日定位。
- `engine/ziwei/hour.py`：Experimental / On-demand 流時定位，只處理已解析農曆日期＋時辰地支。
- `engine/ziwei/calendar_adapter.py`：把可用 `CalendarContext` 原樣傳入既有 Ziwei core；不重算日期或套用命理日界。

`engine/project_bazi_calendar.py`、`engine/project_ziwei_month.py`、`engine/project_ziwei_day.py` 與 `engine/project_ziwei_hour.py` 繼續保留作 compatibility wrapper；若要實際執行，仍必須同時具備對應 package 依賴並保持同版。

Calendar Resolver runtime 需要 exact `lunar-python==1.4.8` 與 `tzdata==2026.3`。缺少 exact dependencies 時，不得宣稱 Resolver 可執行。
