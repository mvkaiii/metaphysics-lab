# 架構說明

Metaphysics Lab 目前正式版本為 **v1.5.0｜2026-08-29**。本文件保留架構與技術歷史；動態 capability implementation / maturity / routing 仍以 `runtime_info` 為權威來源。正式 release 不會自動提升任何 experimental capability maturity。

> 以下姓名與識別碼皆為虛構示例。

核心分工：

> **Python 算盤，AI 讀盤。**

Python 負責可重現的 calculation / validation / serialization / identity / selection；AI 負責工作流、證據分層、命理解讀、盲判、事件校準與現實策略。

## 一、八種資料類型

1. 原始盤面事實
2. 已校驗資料
3. Project 原生盤面
4. Project 推導盤面
5. 已驗證事件
6. 命理推論
7. 研究假說
8. 當次現實背景

這八層不能互相冒充。Project 由出生資料建立的 deterministic natal facts 屬 **Project 原生盤面**；Project 由本命／運限／目標時間建立的細時間層與 Historical Activation Selector 屬 **Project 推導盤面**。

`Project 推導盤面` 是資料分類，不是 capability prefix。

## 三、Subject Identity 與 Subject Registry

多人 Project 的 identity authority 是 `subject_id`，不是檔名或顯示名稱。

### 3.1 Identity fields

```text
subject_id
subject_short_id
subject_display_name
filename_label
```

- `subject_id`：opaque random identifier；不得由姓名、生日、出生地等 PII derive。
- `subject_short_id`：從 opaque `subject_id` 衍生，預設至少6個 hex chars；Project registry 內碰撞時 deterministic 延長。
- `subject_display_name`：人類可讀名稱。
- `filename_label`：display name 的 deterministic normalized filename label。

同名命主可以共存；rename 不改 `subject_id` / `subject_short_id`。

### 3.2 Project-level Subject Registry

`命主索引.md` 是 Project-level **Subject Registry**。它只保存 discovery/display metadata，不保存出生資料或人生事件。

核心 runtime actions：

```text
subject.create_identity
subject.registry_validate
subject.rename
```

AI 在讀 Case 前先 resolve subject。多人／合盤時每人有自己的 `subject_id` 與 Case，先做個別分析再做互動；不得混用不同人的四柱、宮位、八字大運、紫微大限、Project 原生／推導盤面或驗證事件。

### 3.3 Rename atomicity

已有 Case 的 subject rename 不是單純改 registry。一次操作必須回傳／更新：

- Subject Registry
- 所有該 subject materialized Case filenames
- 所有 front matter 的 display / filename metadata
- 該 subject 的00 manifest
- old → new rename mapping
- removed old filenames

新 display name 只改可見識別，opaque identity不變。

## 四、Case identity：canonical slot 與 persisted filename

Runtime 內部持續使用00～08 **canonical slot**：

```text
00_專案索引.md
01_命盤核心摘要.md
02_命盤資料校驗紀錄.md
03_八字結構化資料包.md
04_紫微基礎資料包.md
05_驗證事件紀錄.md
06_流年追蹤紀錄.md
07_問事追蹤紀錄.md
08_重大決策紀錄.md
```

Case Schema 1.1 實際 persisted filename 固定為：

```text
<filename_label>_<SUBJECT_SHORT_ID>_<slot>_<canonical_title>.md
```

虛構範例：

```text
Alex_7F3A2C_01_命盤核心摘要.md
```

因此：

```text
internal canonical slot ≠ persisted filename
```

Parser 從右側 canonical suffix 解析，因為 filename label 本身可能包含 `_`。

## 五、Birth / Location / Calendar Foundation

完整 Mode A 最低輸入：sex、Gregorian birth date、birth time、birth place。自然語言層只解析使用者已提供資料並回報 missing fields，不生成假值。

Known Four Pillars Mode B 只允許建立 Bazi imported/external view，不反推唯一 civil birth identity，也不建立完整 Ziwei natal。

Location Resolver 提供 canonical label、latitude、longitude、IANA timezone 與 provenance；零候選或多個 material candidates 時 fail closed。

Calendar Resolver v1 接受 structured local civil datetime + IANA timezone + optional offset hint，負責 timezone/DST、Gregorian normalization、Gregorian→Lunar、neutral civil hour branch 與 validation。

**Calendar Resolver 不負責真太陽時，也不套八字／紫微命理日界。** civil date 只在00:00換日；23:00已屬子時，但 neutral calendar context 不自行前進 metaphysical effective date。

## 六、Birth Time Views 與 Candidate Envelope

至少保存：

```text
reported_civil_time
normalized_civil_time
bazi_effective_time
ziwei_effective_time
```

另外可保存 versioned true-solar record、adjustment minutes、calculation basis、profile id、rule version、provenance。

真太陽時由 downstream time profile 決定，不是 Calendar Resolver 的全域行為。八字與紫微 profile 獨立；原始 civil time 永遠保留。

### 6.1 Candidate Envelope

`natal.candidate_envelope` 用於出生時間為 `bounded` 或 `unknown_time` 時。設計目的不是找一個「最可能時間」，而是保存所有 materially distinct 的合法候選。

核心流程：

1. Python逐分鐘 evaluate uncertainty interval。
2. 取得每分鐘的 deterministic discrete Bazi / Ziwei structure。
3. 相鄰分鐘若 discrete structure 完全相同，合併成一個 **material state**。
4. Bazi 起運 datetime 等連續變數保存 range，不因分鐘級微調製造1440張假不同盤。
5. 對 candidate facts做遞迴 nested-path分類。

固定不確定性契約：

- **不使用 midpoint**，也不使用 default time。
- **不用多數決**；2/3候選相同仍不是 invariant。
- 只有所有 candidates 都一致且該 path 都存在的值才標 **invariant**。
- 任何不一致 nested path 都保持 **candidate-dependent**。
- `bounded` / `unknown_time` 的 unresolved status 不因壓縮後只有1個material state就消失。

### 6.2 Partial Case 與 blocked scopes

Candidate Envelope 可以建立 schema 1.1 `partial` Base Case，但不得轉成假的唯一 `NormalizedNatalChart`。

Partial Case必須明確列出：

- invariant facts
- candidate-dependent facts
- unresolved birth-time uncertainty
- **blocked scopes**

至少以下scope在 `bounded` / `unknown_time` 時保持 blocked：

```text
unique_birth_time_claim
unique_hour_pillar_conclusion
unique_ziwei_natal_conclusion
single_chart_personalized_forecast
```

因此「已經有五個Case檔」不等於「唯一盤成立」。

## 七、Normalized Natal Model

Cross-system model 固定：

```text
External / Project / Resolved
```

固定 status：

```text
MATCH / EQUIVALENT / CONFLICT / NOT_COMPARABLE
```

固定 severity：

```text
INFO / CAUTION / BLOCKING
```

External / Project raw values 不得覆寫。Resolved source selection 只是 authority policy 的可追溯選擇，不得改寫原 status / severity。

Astralium 為可選 external qualification source，不是 runtime dependency。

## 八、Natal Builders 與時間能力

Bazi Natal 與 Ziwei Natal 輸出 deterministic natal facts；主觀格局／喜用神／事件解讀不由 Python 自動補值。

Ziwei Transformation / Flying、Fine Cycle、Flowing Stars 各自維持獨立 capability、profile 與 maturity。Calendar、Bazi、Ziwei 的時間 boundary responsibility 不混用。

### 8.1 Phase 2C Ziwei Flowing Stars

Phase 2C 採 **Pure Placement Core + Scope Source Adapters + Independent FlowingStarLayer + Optional Materialized View**，profile：

```text
ziwei-flowing-stars-common-v1
```

`FlowingStarLayer` 與 `CycleTransformationLayer` 語意分離，不互相覆寫。動態 join key：

```text
chart_id + scope + reference
```

Canonical flowing-star location 保存 Earthly Branch；宮名只在 materialized view 解析。當前 capability 狀態由 `runtime_info` 決定，架構文件不把 maturity promotion 寫死。

## 九、Progressive Case Schema 1.1

完整 Case canonical slot 仍為00～08，但新 Case 不在第一天建立九個實體檔案。

**Base5**：

```text
00_專案索引.md
01_命盤核心摘要.md
02_命盤資料校驗紀錄.md
03_八字結構化資料包.md
04_紫微基礎資料包.md
```

**Progressive4**：

```text
05_驗證事件紀錄.md
06_流年追蹤紀錄.md
07_問事追蹤紀錄.md
08_重大決策紀錄.md
```

實際 schema 1.1 filename 都帶 subject prefix，例如：

```text
Alex_7F3A2C_00_專案索引.md
Alex_7F3A2C_01_命盤核心摘要.md
Alex_7F3A2C_05_驗證事件紀錄.md
```

該 subject 的實際00是 manifest，追蹤 materialized files 與 Historical Calibration status。

Case mutation分成兩種：

- 首次materialize新檔：套用canonical template。
- rename／migration／後續append：重寫front matter＋既有body，不再重新包一次template。

這使 mutation保持idempotent，不會每次append都累積template wrapper。

### 9.1 Legacy Case 1.0

Legacy schema 1.0 是bare filename＋完整九檔。新版runtime保持readable；不因1.1的subject-aware filename或Progressive model強制 destructive rename，也不刪除既有05～08。

正式migration才會建立subject identity並產生prefixed filenames與rename mapping。

## 十、Historical Activation Selector v1

```text
capability      = historical.activation_selector
profile         = historical-activation-bazi-v1
classification  = Project 推導盤面
ranking_basis   = bazi_only
```

Selector 接受 canonical normalized natal + `as_of_datetime` + timezone。禁止 history-based ranking hints，例如 known event years、preferred years 或 manual ranking override。

### 10.1 Window

最近10個**已完整結束**的 Bazi flow-year periods，以立春交接時刻為界。當前尚未走完的流年不進 calibration window。

### 10.2 Evidence

固定三級：

```text
Tier 1 = 核心強訊號
Tier 2 = 中度支持訊號
Tier 3 = 輔助訊號
```

Relation tables version-control 於 `engine/historical/relations.py`；suppression / dedup 防止同一結構重複灌水。

### 10.3 Ranking

不用黑箱分數。每年建立 lexicographic rank vector，排序後 canonical selection 永遠是：

```text
Top 4    = High Years
Bottom 1 = Control
```

conversation contamination、已知事件與AI偏好都不能改選。Supplemental blind points也必須來自同一selector最近10年 `ranked_periods`，不得與canonical Top4 + Bottom1重複，supplemental之間不得重複，且不改canonical `selection_digest`。

## 十一、Ziwei Historical Support：support-only

Historical selector v1 先完整產生 Bazi canonical selection + `selection_digest`，之後才附 Ziwei yearly context。

```text
ziwei_support.role              = support_only
ziwei_support.ranking_authority = false
```

Ziwei support 缺失／部分失敗時，Bazi selector仍正常輸出。無論support如何變動，都不得改：

- `high_years`
- `control_year`
- `selection_digest`

若未來要讓 Ziwei 共同 ranking，必須另開新的 cross-system profile與qualification，不能靜默修改v1。

## 十二、Historical Blind Calibration

Historical Calibration 是 AI workflow + deterministic runtime 的組合，不是單一命理演算法。

1. Python先選 canonical 4 High + 1 Control。
2. AI在不知道答案的情況下對每個年份提出明確「年份＋主要領域／事件形式」假說。
3. Blind set鎖定並產生digest。
4. 使用者逐題回答 matched / partial / not_matched / cannot_recall，並可直接訂正真正年份與事件。
5. Blind prediction不可覆寫；使用者確認事件另存為已驗證事件，評價另存為已校驗資料。
6. `cannot_recall` 是 unscorable，不算失準。
7. actual date優先依Li-Chun flow-year interval評價；Gregorian year只是友善label。

若 canonical point 已在 conversation 中曝光，標 `contaminated`；仍保留 canonical selection，但不計作完整 blind evidence。

### 12.1 Subject-aware Stage 1

實際Case key可以是：

```text
Alex_7F3A2C_01_命盤核心摘要.md
```

但安全allowlist先canonicalize，再要求恰好等於完整00～04。05～08不得混入blind Stage 1。

第一次未來問事且 Case 尚未校準時：

```text
resolve subject
↓
subject canonical 00-04 + reality
↓
Stage 1 future blind forecast LOCK
↓
Historical Blind Calibration
↓
materialize subject actual 05 + update subject actual 00
↓
Stage 2 event calibration
```

這避免先知道歷史答案後污染第一版未來盲判。

## 十三、Capability 三軸模型

```text
implementation = planned / implemented
maturity       = experimental / stable
routing        = default / on_demand
```

三軸分開。implemented 不等於 Stable，也不等於每次預設執行。當前 capability truth 一律從 `runtime_info` 取得。

`natal.candidate_envelope` 的設計狀態是 `implemented / experimental / on_demand / 1.0-exp`；本階段不得因實作完成自行promotion為Stable。

## 十四、AI Distribution build authority

Generated distribution 不直接手改：

```text
metaphysics_lab.py
metaphysics_core.md
project_instructions.txt
```

Source authority：

```text
project_instructions.txt <- core/核心提示詞.md
metaphysics_core.md      <- core/AI工作流程.md + core/命理分析作業規範.md
```

由：

```text
tools/build_ai_distribution.py
```

重建與檢查。Repo不存在 `core/project_instructions.txt` 這個source contract。

## 十五、Qualification 與 Privacy

公開 qualification 可提交 public/synthetic vectors、versions、aggregate status、counts 與 digest。

私人 `命主索引.md`、Astralium或使用者命盤不得提交 raw birth input、raw chart、full address、Candidate Envelope個案、Historical Calibration答案或 external raw payload；private qualification 只允許 aggregate counts/digest/status。

Infrastructure outage 與 algorithm mismatch 必須分開報告，不能把 provider failure 重命名成 PASS 或產品 FAIL。

## 十六、分析責任

Deterministic layer只提供identity、chart facts、source classification、validation、reconciliation、candidate state、forecast context、historical selection與canonical export。命理 interpretation、使用者對話與現實策略仍在AI分析層執行。

因此：

- Project 原生盤面 ≠ 命理推論。
- Candidate Envelope ≠ 唯一出生時間。
- 已校驗資料 ≠ 已驗證事件。
- Historical activation高 ≠ 某事件必然發生。
- runtime可以算 ≠ AI可以忽略precision gate。
- 有Case檔案 ≠ 唯一盤已解鎖。

最終策略仍以使用者當次現實條件為最高實務權重。
