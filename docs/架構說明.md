# 架構說明

Metaphysics Lab 正式 release identity 目前為 **v1.3.0｜2026-08-23**。本文件同時記錄尚未正式發版的 **Progressive Case + Historical Blind Calibration** 架構；動態 capability implementation / maturity / routing 仍以 `runtime_info` 為權威來源。

核心分工：

> **Python 算盤，AI 讀盤。**

Python 負責可重現的 calculation / validation / serialization / selection；AI 負責工作流、證據分層、命理解讀、盲判、事件校準與現實策略。

## 八種資料類型

1. 原始盤面事實
2. 已校驗資料
3. Project 原生盤面
4. Project 推導盤面
5. 已驗證事件
6. 命理推論
7. 研究假說
8. 當次現實背景

這八層不能互相冒充。Project 由出生資料建立的本命屬於 **Project 原生盤面**；Project 由本命／運限／目標時間建立的細時間層與 Historical Activation Selector 屬於 **Project 推導盤面**。

`Project 推導盤面` 是資料分類，不是 capability prefix。

# 二、Birth / Location / Calendar Foundation

完整 Mode A 最低輸入：sex、Gregorian birth date、birth time、birth place。自然語言層只解析使用者已提供資料並回報 missing fields，不生成假值。

Known Four Pillars Mode B 只允許建立 Bazi imported/external view，不反推唯一 civil birth identity，也不建立完整 Ziwei natal。

Location Resolver 提供 canonical label、latitude、longitude、IANA timezone 與 provenance；零候選或多個 material candidates 時 fail closed。

Calendar Resolver v1 接受 structured local civil datetime + IANA timezone + optional offset hint，負責 timezone/DST、Gregorian normalization、Gregorian→Lunar、neutral civil hour branch 與 validation。

**Calendar Resolver 不負責真太陽時，也不套八字／紫微命理日界。** civil date 只在00:00換日；23:00已屬子時，但 neutral calendar context 不自行前進 metaphysical effective date。

# 三、Birth Time Views

至少保存：

```text
reported_civil_time
normalized_civil_time
bazi_effective_time
ziwei_effective_time
```

另外可保存 versioned true-solar record、adjustment minutes、calculation basis、profile id、rule version、provenance。

真太陽時由 downstream time profile 決定，不是 Calendar Resolver 的全域行為。八字與紫微 profile 獨立；原始 civil time 永遠保留。

只有會改變日柱、時柱、命宮、身宮或其他核心依賴欄位的差異才升級為 material conflict。

# 五、Natal Builders 與時間能力

# 六、Progressive Case Schema 1.1

完整 Case record type 仍為00～08，但**新 Case 第一次不建立九個實體檔案**。

Base Case：

```text
00_專案索引.md
01_命盤核心摘要.md
02_命盤資料校驗紀錄.md
03_八字結構化資料包.md
04_紫微基礎資料包.md
```

Progressive records：

```text
05_驗證事件紀錄.md    ← 第一次有 verified historical event / calibration record
06_流年追蹤紀錄.md    ← 第一次永久追蹤流年／年度預測
07_問事追蹤紀錄.md    ← 第一次永久追蹤一般問事
08_重大決策紀錄.md    ← 第一次永久追蹤重大決策
```

`00_專案索引.md` 是 manifest，追蹤 materialized files 與 Historical Calibration status。

Case Schema 1.0 的既有九檔 Case 是合法 legacy data；1.1 runtime 必須可讀，不因 progressive model 刪除舊檔。

# 七、Historical Activation Selector v1

```text
capability = historical.activation_selector
profile    = historical-activation-bazi-v1
classification = Project 推導盤面
ranking_basis  = bazi_only
```

Selector 接受 canonical normalized natal + `as_of_datetime` + timezone。禁止 history-based ranking hints，例如 known event years、preferred years 或 manual ranking override。

## 7.1 Window

最近10個**已完整結束**的 Bazi flow-year periods，以立春交接時刻為界。當前尚未走完的流年不進 calibration window。

## 7.2 Evidence

固定三級：

```text
Tier 1 = 核心強訊號
Tier 2 = 中度支持訊號
Tier 3 = 輔助訊號
```

Tier 1 包含大運交界、歲運並臨、完整本命柱伏吟、流年支沖本命／大運、補成完整三合／三會／三刑。

Tier 2 包含六合、partial三合／三會、pair/self punishment、單支伏吟、天干五合。

Tier 3 包含六害、六破、天干同干。

Relation tables version-control 於 `engine/historical/relations.py`；suppression / dedup 防止同一結構重複灌水。

## 7.3 Ranking

不用黑箱分數。每年建立 lexicographic rank vector：

```text
tier1_family_count
tier1_evidence_count
cross_layer_tier1
tier2_family_count
tier2_evidence_count
tier3_family_count
tier3_evidence_count
label_year
```

排序後 canonical selection 永遠是：

```text
Top 4    = High Years
Bottom 1 = Control
```

連續年份、單一大運、conversation contamination、已知事件都不能改選。最後 `label_year` 只作完全同 evidence 時的 deterministic tie-break。

Control quality 分 `strong_control / acceptable_control / relative_low`；relative_low 不得稱真正穩定年。

# 八、Ziwei Historical Support：Support-only

Historical selector v1 先完整產生 Bazi canonical selection + `selection_digest`，之後才附 Ziwei yearly context。

```text
ziwei_support.role              = support_only
ziwei_support.ranking_authority = false
```

對 canonical 5 年各取該 Bazi flow-year period 的 deterministic midpoint，呼叫既有 Ziwei yearly context。這層給 AI 作事件領域交叉參考，不參與 Bazi selection。

Ziwei support 缺失／部分失敗時，Bazi selector仍正常輸出，support只標 `partial` 或 `unavailable`。無論 Ziwei內容如何變動，都不得改：

- `high_years`
- `control_year`
- `selection_digest`

若未來要讓 Ziwei 共同 ranking，必須另開新的 cross-system profile與qualification，不能靜默修改v1。

# 九、Historical Blind Calibration

Historical Calibration 是 AI workflow + deterministic runtime 的組合，不是單一命理演算法。

1. Python先選 canonical 4 High + 1 Control。
2. AI在不知道答案的情況下對每個年份提出明確「年份＋主要領域／事件形式」假說。
3. Blind set鎖定並產生digest。
4. 使用者逐題回答 matched / partial / not_matched / cannot_recall，並可直接訂正真正年份與事件。
5. Blind prediction不可覆寫；使用者確認事件另存為已驗證事件，評價另存為已校驗資料。
6. `cannot_recall` 是 unscorable，不算失準。
7. actual date優先依Li-Chun flow-year interval評價；Gregorian year只是友善label。

若 canonical point 已在 conversation 中曝光，標 `contaminated`；仍保留 canonical selection，但不計作完整 blind evidence。

第一次未來問事且 Case 尚未校準時，順序固定：

```text
00-04 + reality
↓
Stage 1 future blind forecast LOCK
↓
Historical Blind Calibration
↓
materialize 05
↓
Stage 2 event calibration
```

這避免先知道歷史答案後污染第一版未來盲判。

# 十、Capability 三軸模型

```text
implementation = planned / implemented
maturity       = experimental / stable
routing        = default / on_demand
```

三軸分開。implemented 不等於 Stable，也不等於每次預設執行。當前 capability truth 一律從 `runtime_info` 取得。

---

# 十一、Qualification 與 Privacy

公開 qualification 可提交 public/synthetic vectors、versions、aggregate status、counts 與 digest。

私人 Astralium 或使用者命盤不得提交 raw birth input、raw chart、full address、Historical Calibration 答案或 external raw payload；private qualification 只允許 aggregate counts/digest/status。

Infrastructure outage 與 algorithm mismatch 必須分開報告，不能把 provider failure 重命名成 PASS 或產品 FAIL。

---

# 十二、分析責任

Deterministic layer 只提供 chart facts、source classification、validation、reconciliation、forecast context、historical selection 與 canonical export。命理 interpretation、使用者對話與現實策略仍在 AI 分析層執行。

因此：

- Project 原生盤面 ≠ 命理推論
- Project 推導盤面 ≠ 命理推論
- Historical activation high ≠ 一定發生壞事
- qualification match ≠ 命理預測正確
- capability implemented ≠ maturity Stable
- Historical blind hit ≠ 可以事後改寫原始盲讀
