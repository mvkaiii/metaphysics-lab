# 更新與版本同步

一般使用者先記住一件事：**大多數只更新執行程式的版本，只要替換 `metaphysics_lab.py`，不需要重建整個命理專案。** 但如果正式發布說明明確變更專案規格（Project Contract），就要同步核心規則與 Project Instructions。

目前最新正式版本為 **v1.9.0｜2026-10-03**。既有命主資料與個案紀錄可以沿用；Project Contract升為1.3，但Case Schema仍維持1.1，不要求破壞性schema migration。v1.9.0新增出生時間不確定性流程、Case Revision Integrity、Lock Provenance v2、Guided Natal Build與Candidate Envelope摘要視覺化。

> 以下姓名與識別碼皆為虛構示例。

## 一、三種更新層級

### 專案規格（Project Contract）

負責 AI 的固定治理與工作方式，主要對應：

```text
project_instructions.txt
metaphysics_core.md
```

如果正式發布說明明確寫專案規格（Project Contract）改版，這兩份要一起同步。

### 執行程式（Runtime）

負責可重現計算與結構化操作：

```text
metaphysics_lab.py
```

一般演算法修正、新增功能、相依元件檢查或打包修正，通常都屬於執行程式更新。

### 個案資料格式（Case Schema）

負責私人個案資料 Markdown 的識別資料、欄位、檔案建立與修改規則。個案資料格式（Case Schema）1.1 的正式檔位仍是 00～08；實際保存檔名為：

```text
<filename_label>_<SUBJECT_SHORT_ID>_<slot>_<canonical_title>.md
```

虛構範例：

```text
Alex_7F3A2C_01_命盤核心摘要.md
```

個案資料格式 1.1 同時採漸進式個案結構（Progressive Case）：**Base5** = 00～04；**Progressive4** = 05～08，只有真正有內容時才建立檔案。

## 二、最常見更新｜只換執行程式

如果正式發布說明只說執行程式更新：

1. 下載新版 `metaphysics_lab.py`。
2. 在自己的 ChatGPT Project／Claude Project **只替換 `metaphysics_lab.py`**。
3. 保留原本的 `metaphysics_core.md`、Project Instructions、`命主索引.md` 與私人個案資料。
4. 讓 AI 執行 `runtime_info`，確認目前程式版本、可執行能力與相依元件狀態。

如果專案規格與個案資料格式都沒變，到這裡就完成。不要因執行程式更新而重新建立本命、清空驗證事件、重建 `subject_id` 或覆寫第一版盲判。

## 三、v1.3.0 → v1.4.0

v1.4.0 明確包含專案規格（Project Contract）／個案資料格式（Case Schema）1.1，因此不是「只換執行程式」：替換執行程式與核心規則，並以當時的 `project_instructions.md` 重新貼 Project Instructions，保留既有 `命主索引.md` 與私人個案資料。若舊版個案資料真的需要結構移轉，再依正式 `validate_case` / `migrate_case` 回傳處理；沒有移轉要求就不做破壞性重建。

## 四、v1.4.0 → v1.5.0

v1.5.0 的一般使用者發行面改成三檔使用者安裝包（User Package），個案資料格式仍維持 1.1，不要求重建私人個案資料。

1. 下載 `Metaphysics-Lab-v1.5.0-User-Package.zip`。
2. 替換 `metaphysics_lab.py` 與 `metaphysics_core.md`。
3. 打開 `project_instructions.txt`，把全文重新貼到 Project Instructions。
4. 保留既有 `命主索引.md`、命盤資料與 05～08 追蹤紀錄。
5. 更新後執行 `runtime_info`。

Project Instructions 的發行副檔名改成 `.txt` 是為了手機／電腦開啟與複製方便；這不是個案資料格式（Case Schema）的結構移轉，也不代表要重新排盤。

## 五、v1.5.0 → v1.6.0

v1.6.0 的使用者安裝包仍是同一個三檔安裝面，建議三個檔案一起同步；個案資料格式仍維持 1.1，不要求重建私人個案資料。

1. 下載 `Metaphysics-Lab-v1.6.0-User-Package.zip`。
2. 替換 ChatGPT Project／Claude Project 中的 `metaphysics_lab.py`。
3. 替換 `metaphysics_core.md`。
4. 打開新版 `project_instructions.txt`，把全文重新貼到 Project Instructions。
5. **保留**既有 `命主索引.md`、出生盤、驗證事件、流年／問事／重大決策紀錄與已鎖定的第一版預測。
6. 更新後執行 `runtime_info`。

v1.6.0 的 Y1 年度紫微四化**專案推導能力**仍屬實驗性；正式納入軟體不等於已證明比舊方法更準，也不代表 selector v2 / interpretation v2 已改成預設版本。

## 六、v1.6.0 → v1.7.0

v1.7.0 是可靠性與易用性更新。專案規格（Project Contract）從 1.1 升到 1.2，但個案資料格式（Case Schema）仍維持 1.1；因此這次三個發行檔案要一起同步，私人個案資料則原樣保留。

更新方式：

1. 下載 `Metaphysics-Lab-v1.7.0-User-Package.zip`。
2. 替換 ChatGPT Project／Claude Project 中的 `metaphysics_lab.py`。
3. 替換 `metaphysics_core.md`。
4. 打開新版 `project_instructions.txt`，把全文重新貼到 Project Instructions。
5. **三個檔案一起**完成後，保留既有 `命主索引.md`、本命資料、第三方原始命盤資料、驗證事件、流年／問事／重大決策紀錄與所有已鎖定預測。
6. 執行 `runtime_info`，確認專案規格 1.2、執行資料格式 1.1、個案資料格式 1.1，以及目前的功能清單與執行程式狀態。

本次不需要重建個案資料、重新產生 `subject_id`、清空 05～08，或把舊預測重新鎖定。**個案資料檢查（Case Doctor）**可以找出舊版資料、重複資料與內容衝突，並先提出不會直接修改檔案的校驗預演；它**不會自動刪除**檔案。若真的需要修改資料，仍要遵守既有確認與正式更新流程。

**前瞻驗證 2.0（Prospective Validation 2.0）**會把 `clean_prospective`、`conditional_prospective`、`hidden_existing_reality`、`retrospective_calibration` 分開。已知安排或鎖定前已存在但當時未知的事實，不得計入乾淨前瞻預測的命中率母體。

**引導式追問（Guided Inquiry）**會主動提供 3～4 個後續詢問方向，預設 3 個；這些只是導航，不是新命理證據，也不會提高結論的具體程度或信心。

## 七、v1.7.0 → v1.7.1

v1.7.1 是**只調整執行程式版本資訊的修正版**。它的目的，是讓 `runtime_info` 明確同時回報：

```text
Release Version            1.7.1
AI Distribution Runtime    1.2-exp
Project Contract            1.2
Runtime Schema              1.1
Case Schema                 1.1
```

這兩個版本層級不要混在一起：`v1.7.1` 是整體 Metaphysics Lab 發布版本；`1.2-exp` 是內部 AI 執行環境版本（AI Distribution Runtime）。

如果目前已經是 **v1.7.0**：

1. 從 v1.7.1 正式發布頁下載新版 `metaphysics_lab.py`，或下載 `Metaphysics-Lab-v1.7.1-User-Package.zip` 後只取出該檔。
2. **只替換 `metaphysics_lab.py`**。
3. `metaphysics_core.md` 不需要替換；Project Instructions 也不需要重貼。
4. 保留 `命主索引.md`、所有私人個案資料、命盤、驗證事件、追蹤紀錄與已鎖定預測。
5. 執行 `runtime_info`，確認 `release_version = 1.7.1`、`distribution_runtime_version = 1.2-exp`。

舊版個案資料裡的 `project_contract_version: 1.1` 或 `runtime_version_if_applicable: 1.1-exp` 可能是建立當時留下的來源與版本紀錄；v1.7.1 **不要求批次覆寫這些欄位**。只要個案資料格式 1.1 可以被新版執行程式正常驗證，就不是升級失敗。

## 八、v1.7.1 → v1.8.0

v1.8.0 雖維持專案規格 1.2／個案資料格式 1.1，但固定核心規則與 Project Instructions 有使用者呈現更新，因此請**三檔一起同步**：

1. 下載 `Metaphysics-Lab-v1.8.0-User-Package.zip`。
2. 替換 `metaphysics_lab.py`。
3. 替換 `metaphysics_core.md`。
4. 把新版 `project_instructions.txt` 全文重新貼到 Project Instructions。
5. 保留 `命主索引.md`、所有私人個案資料、驗證事件、追蹤紀錄與已鎖定預測。
6. 執行 `runtime_info`，確認正式發布版本 1.8.0、AI 執行環境版本 1.4-exp、專案規格 1.2、執行資料格式 1.1、個案資料格式 1.1。

本版的八字曆法引擎與大運時間來源已有實質工程修正。若既有個案資料已產生相關八字長週期資料，不得直接覆寫；需要使用新版執行程式重新計算時，應採明確的重新計算與校驗流程，並保留舊版資料的來源與版本紀錄。

## 九、v1.8.0 → v1.9.0

v1.9.0 將專案規格（Project Contract）從1.2升到1.3，但個案資料格式（Case Schema）仍維持1.1，因此請**三檔一起同步**，私人Case與歷史紀錄則保留。

1. 下載 `Metaphysics-Lab-v1.9.0-User-Package.zip`。
2. 替換 `metaphysics_lab.py`。
3. 替換 `metaphysics_core.md`。
4. 把新版 `project_instructions.txt` 全文重新貼到 Project Instructions。
5. 保留 `命主索引.md`、既有Case、驗證事件、流年／問事／重大決策紀錄與所有已鎖定預測。
6. 執行 `runtime_info`，確認正式發布版本1.9.0、AI Distribution Runtime 1.5-exp、Project Contract 1.3、Runtime Schema 1.1、Case Schema 1.1。

既有Project Contract 1.2 Case仍可讀，不要求批次覆寫。只有本命基礎資料真的改變、或新流程明確要求revision-bound Base Case時，才使用 `case.replace_natal_base` 等正式路徑。舊lock保持不可變：不回填provenance、不重簽、不重算digest。

## 十、專案規格更新

只有正式發布說明明確寫專案規格（Project Contract）改版時，才同步新的 `metaphysics_core.md` 與 `project_instructions.txt`。更新後保留 `命主索引.md` 與私人個案資料，再讓 AI 確認命主、讀取個案索引，並檢查結構相容性。

專案規格更新不代表一定要重新排盤；是否重算由正式發布說明與資料移轉要求決定。v1.7 的專案規格 1.2 **不伴隨個案資料格式的結構移轉**。

## 十一、個案資料格式更新

只有正式發布說明明確寫出**結構移轉（schema migration）**時，才處理私人個案資料。正式流程先呼叫 `validate_case` / `migrate_case`，並遵守：

- 同一結構版本且相容 → `no_change`
- 結構移轉只改真正需要改的檔案
- 不捏造事件、預測或決策
- 第一版已鎖定盲判不可覆寫
- 命主識別資料不可混用
- 不為了 Progressive Case 而刪除既有合法紀錄

### 舊版個案資料 1.0

舊版個案資料 1.0 是完整九檔、使用不帶命主前綴檔名的合法歷史格式。新版執行程式必須繼續可讀；升級到 1.1 不強制先做結構移轉，也不要求破壞性改名。只有使用者明確執行正式移轉流程時，執行程式才建立命主識別資料、更新檔案前置資訊與清單，並回傳舊檔名 → 新檔名的對照。

### 新版個案資料 1.1

新建個案資料使用 Base5（00～04）＋ Progressive4（05～08 按需求建立），實體檔名維持 `<filename_label>_<SUBJECT_SHORT_ID>_<slot>_<canonical_title>.md`。如果執行程式尚未提供某條正式移轉路徑，就不要自行猜欄位轉換方式。

## 十二、命主識別資料更新規則

`命主索引.md` 是專案層級的命主索引。命主改名時，`subject_id` / `subject_short_id` 不變，`subject_display_name` / `filename_label` 可以改；已存在的個案資料必須一致更新索引、已建立的檔名、檔案前置資訊、00 專案清單與改名對照。不能只改索引而留下識別資料不一致。

## 十三、候選盤面集合與部分個案資料

出生時間仍是 `bounded` 或 `unknown_time` 的個案資料屬於 `partial`。即使候選盤面集合（Candidate Envelope）整理後只剩一種盤面狀態，也不能因執行程式升級就自動宣稱出生時間已唯一確定。需要唯一出生時間才能成立的結論仍保持未確定，除非真的有新證據解除不確定性。

## 十四、能力狀態不要從固定文件猜

固定 Markdown 不維護容易快速過期的功能狀態表。更新後讓 AI 呼叫：

```text
runtime_info
```

以執行程式回傳的實作狀態、成熟度、路由方式、版本與相依元件狀態為目前技術執行依據。任何仍在實驗階段的功能都**不會因 v1.9 發布而自動升級**，也不會因文件整理或合併到 `main` 就自動變成穩定狀態（Stable）。

## 十五、什麼情況需要重新計算？

建議重新計算的情況包括：正式發布說明明確指出本命／曆法／時間口徑算法有實質變更；候選盤面集合的狀態計算方式有實質變更且命主仍是部分資料狀態；規則版本有實質變更；原個案資料有阻斷性衝突而新版專門修正該問題；使用者提供更精確的出生資料；或新的第三方交叉校驗改變目前採用的校驗依據。

單純文件、命令列工具、打包方式、相依元件檢查、個案資料匯出或驗證證據補強，不應自動重算本命。已完成並鎖定的歷史盲測校準，也不應因小版本執行程式更新而自動覆寫。

## 十六、更新後快速檢查

讓 AI 執行 `runtime_info`，至少確認：專案規格、執行資料格式／執行程式版本、個案資料格式、支援的操作、各功能的實作／成熟度／路由狀態，以及外部相依元件。若系統回報不相容或需要資料移轉，再依正式發布說明處理。
