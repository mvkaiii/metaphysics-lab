# 更新與版本同步

本文件說明 GitHub 的 Metaphysics Lab 更新後，如何安全同步到自己的 ChatGPT Project，而不覆蓋私人 Case。

核心原則：

> GitHub 是系統核心的正式版本來源；私人 Project 是實際個案資料與分析環境。

兩者更新方向不同。

---

## 一、先看版本與變更紀錄

每次更新前先查看：

```text
VERSION.md
CHANGELOG.md
```

`VERSION.md` 告訴你目前正式組合；`CHANGELOG.md` 告訴你這一版新增、修改、停用或固定了哪些規則。

不要只看 Python 檔案是否有變化。規則文件與 Project Instructions 也可能影響分析行為。

---

## 二、哪些屬於「共用核心」

通常需要從 GitHub 同步到 Project 的是：

```text
core/核心提示詞.md
core/命理分析作業規範.md
core/命理推導計算規則.md
core/紫微流月推導規則.md
engine/project_bazi_calendar.py
engine/project_ziwei_month.py
```

若測試基準有更新，也建議同步：

```text
tests/命理推導測試案例.md
tests/紫微流月推導測試案例.md
```

v1.2 重構後，GitHub 內部正式實作另外位於：

```text
engine/bazi/__init__.py
engine/bazi/calendar.py
engine/ziwei/__init__.py
engine/ziwei/common.py
engine/ziwei/month.py
```

一般 ChatGPT Project 可以繼續保留兩支 `project_*.py` 作相容入口名稱；但如果環境要**實際執行**這些 wrapper，就必須連同對應 package 一起同步。wrapper 不是獨立單檔引擎。

---

## 三、核心提示詞的更新方式

`core/核心提示詞.md` 最重要的用途是更新 ChatGPT Project Instructions。

因此 GitHub 的核心提示詞有變更時：

1. 開啟最新 `core/核心提示詞.md`。
2. 更新 Project Instructions。
3. 不要只把新檔上傳，卻保留舊的 Instructions。

如果 Project Instructions 與上傳的規則檔互相矛盾，容易出現「文件說已啟用，但 AI 還是認為未啟用」的狀況。

---

## 四、Python 引擎需要同步嗎

需要。

如果 GitHub 的引擎版本更新，Project 中的 `.py` 也要替換成同版。

目前一般 Project 的正式相容入口為：

```text
engine/project_bazi_calendar.py
engine/project_ziwei_month.py
```

尤其從 v1.0 升到 v1.1 的 Project，如果沒有加入 `project_ziwei_month.py`，就不算完成紫微流月功能同步。

v1.2 內部模組化後，兩支舊檔仍保留作 compatibility wrapper，所以**既有呼叫名稱不需要因內部重構立即改掉**。

但要注意兩件事：

1. wrapper 執行時會 import `engine.bazi` / `engine.ziwei` 的正式模組，因此 wrapper 與 package 必須同版；只替換 wrapper 而不帶 package，實際執行會失敗。
2. `.py` 放在 Project 中代表保存正式算法，不代表每次對話都自動執行 Python。

AI 若沒有實際執行證據，不得宣稱程式已跑過。

---

## 五、哪些私人檔案絕對不要被更新覆蓋

不要用 GitHub 的模板或共用檔案覆蓋自己的：

```text
命盤核心摘要.md
命盤資料校驗紀錄.md
驗證事件紀錄.md
流年追蹤紀錄.md
問事追蹤紀錄.md
重大決策紀錄.md
八字原始資料
紫微原始資料
個人命盤 PDF／截圖
```

`templates/` 只用來「建立新檔」，不是日後更新私人 Case 的來源。

---

## 六、建議同步流程

### Step 1｜查看版本

先確認 GitHub 的 `VERSION.md`。

### Step 2｜閱讀 CHANGELOG

找出跟自己目前版本相比改了什麼。

### Step 3｜更新規則文件

替換 Project 中對應的 `core/` 規則檔。

### Step 4｜更新 Python 引擎

如果 Project 只把 Python 當知識來源，可以保留 `project_*.py` 相容入口作索引；如果環境要實際執行，請同步 wrapper **以及**其 package 依賴：

```text
engine/project_bazi_calendar.py
engine/bazi/__init__.py
engine/bazi/calendar.py

engine/project_ziwei_month.py
engine/ziwei/__init__.py
engine/ziwei/common.py
engine/ziwei/month.py
```

完整 Python 環境可直接使用 `engine.bazi` 與 `engine.ziwei` package。

### Step 5｜更新 Project Instructions

若 `core/核心提示詞.md` 有改，重新同步 Instructions。

### Step 6｜保留私人 Case

不要更動自己的命盤摘要、事件紀錄與追蹤資料。

### Step 7｜做版本確認

可以在 Project 裡問：

> 請只根據目前上傳的核心檔案，列出 Metaphysics Lab Core、八字引擎、紫微流月引擎與推導規則版本，並指出目前已啟用與未啟用的細運層級。

如果回答版本與 GitHub `VERSION.md` 不一致，表示 Project 還有舊檔或舊 Instructions 未替換。

---

## 七、v1.0 → v1.1 的特別升級項目

從沒有紫微流月的舊 Project 升到 v1.1，至少需要：

```text
更新 core/核心提示詞.md → 同步到 Project Instructions
更新 core/命理分析作業規範.md
更新 core/命理推導計算規則.md
新增 core/紫微流月推導規則.md
新增 engine/project_ziwei_month.py
```

建議再加入：

```text
tests/紫微流月推導測試案例.md
```

完成後，Project 應知道：

- 紫微流月已啟用。
- 只做到斗君、流月命宮、流月十二宮。
- 紫微流日／流時仍未啟用。
- 流月四化／流曜／細層飛化仍未啟用。
- 紫微流月採農曆月，八字流月採節氣月；兩者不同步不是 bug。

若要在 v1.2 模組化後的 Python 環境執行相容入口，還必須補齊對應 `engine/ziwei/` package。

---

## 八、v1.2 引擎重構的特別說明

v1.2 的第一階段只做模組拆分：

```text
八字正式實作 → engine/bazi/calendar.py
紫微共用基礎 → engine/ziwei/common.py
紫微流月實作 → engine/ziwei/month.py
```

舊入口繼續存在，因此既有程式可以保留原本的 wrapper 呼叫名稱；**但 wrapper 執行需要 package 依賴，不再是單檔可執行。**

這次內部重構**不等於**：

- 紫微流日已啟用
- 紫微流時已啟用
- Cross-System Validation 已啟用

這三項會在各自算法、測試與版本規則完成後另行公告。

---

## 九、如果更新後回答變怪，先檢查什麼

依序檢查：

1. Project Instructions 是否仍是舊版。
2. `命理分析作業規範.md` 是否已替換。
3. `命理推導計算規則.md` 是否已替換。
4. `紫微流月推導規則.md` 是否存在。
5. wrapper 與 `engine/bazi/`、`engine/ziwei/` 是否為同一版本且依賴齊全。
6. 是否同時保留了多個舊版同名／近似檔案，造成 AI 讀到不同版本。
7. `VERSION.md` 與實際 Project 檔案是否一致。

不要先修改命盤或私人事件來「配合」新版系統。

---

## 十、GitHub 與 Project 不會自動同步

目前應把兩者視為兩套環境：

- GitHub：正式核心版本庫
- ChatGPT Project：實際使用副本

GitHub 更新後，Project 端仍需要手動替換／上傳新版檔案與更新 Instructions，除非未來另外建立自動部署流程。

因此每次重要版本更新，都應在 CHANGELOG 明確列出「Project 需要同步哪些檔案」。
