# 更新與版本同步

本文件說明 GitHub 的 Metaphysics Lab 更新後，如何安全同步到自己的 ChatGPT Project，而不覆蓋私人 Case。

核心原則：

> GitHub 是系統核心的正式版本來源；私人 Project 是實際個案資料與分析環境。

兩者更新方向不同。

目前正式版本：**v1.2.0｜2026-08-21**。

---

## 一、先看三份版本文件

每次更新前先查看：

```text
VERSION.md
CHANGELOG.md
docs/更新與版本同步.md
```

三者分工：

- `VERSION.md`：目前正式有效版本與 capability 狀態。
- `CHANGELOG.md`：每個 release 改了什麼、qualification / regression 到哪裡。
- `更新與版本同步.md`：從舊版升級時實際要替換哪些檔案。

不要只看 Python 檔案是否有變化。規則文件、Project Instructions、requirements 與 capability metadata 都可能影響行為。

---

## 二、版本治理

以下變更必須留下版本歷程：

- 會改變命盤計算結果的規則
- 日期／時間邊界
- rule profile
- schema / data contract
- capability implementation / maturity / routing
- qualification source 或 promotion gate

建議版本語意：

- patch：不改演算法語意的修正、文件錯誤、測試補強
- minor：新增正式 capability、啟用新的可執行規則層
- major：破壞性 schema／API／核心規則相容性變更

Git tag / GitHub Release 應在 release 文件 merge、main regression 完成後建立，不提前鎖在中間狀態。

## 五、v1.2.0 Capability 狀態

```text
紫微流月 = implemented / stable / default
紫微流日 = implemented / experimental / on_demand
紫微流時 = implemented / experimental / on_demand
Calendar Resolver v1 = implemented / stable infrastructure
Ziwei Calendar Adapter = implemented
Ziwei Transformation Core = implemented / stable / on_demand
Ziwei Flying Core = implemented / stable / on_demand
流月／流日／流時四化與飛化 = planned / on_demand
流曜 = planned / on_demand
Cross-System Validation = planned
```

因此：

- `implemented`：Python 能力存在。
- `stable`：已達既定 promotion gate。
- `experimental`：可執行，但分析時降權。
- `on_demand`：平常不預設跑。
- `planned`：尚不能執行。

不要再用 `enabled = false` 推論能力不存在，也不要因 core 已 stable 就推論細運四化已完成。

## 七、Calendar Resolver 更新注意事項

Calendar Resolver civil date 只在 00:00 換日；23:00 已屬子時，但 `metaphysics_day_boundary_applied = false`。

八字 23:00 early-Zi 仍由八字引擎負責。v1.2.0 release baseline 尚未固定紫微 23:00 細運日界；Unreleased Phase 2B 已由 `late_zi_forward-v1` fine-cycle profile 固定，Calendar Resolver 本身仍不套用。

不能因 Resolver 已 implemented 就推論：

- 自然語言解析已解決
- 真太陽時已解決
- 八字／紫微共用同一換日規則
- 若使用 v1.2.0 release baseline，紫微 Fine Cycle Stem Resolver 並不包含在該 release；若使用 Unreleased Phase 2B，則已實作為 Experimental / On-demand

## 八、Ziwei Transformation / Flying 更新注意事項

v1.2.0 已 stable 的是：

- 十天干四化 core
- 本命十二宮宮干飛化
- 生年四化
- 大限四化／飛化
- 流年四化／飛化
- layer composition / conflict validation

v1.2.0 release baseline 的細運四化／飛化仍是 planned；目前 Unreleased Phase 2B 已將流月／流日／流時 stem、四化與飛化 promotion 為 Experimental / On-demand。流曜仍 planned。

若後續修改 fine-cycle stem policy，必須重新確認 VERSION / CHANGELOG / capability registry 與 qualification evidence 是否同版。

## 十、建議同步流程

### Step 1｜確認版本

看 `VERSION.md` 與 `CHANGELOG.md`。

### Step 2｜確認 Project 需要哪些 capability

只用月份分析，不需要每次自動跑流日／流時；要指定日期或時辰，再同步相對應 capability。

### Step 3｜更新規則與 Instructions

替換 `core/` 檔案，並把最新版 `core/核心提示詞.md` 同步到 Project Instructions。

### Step 4｜更新 Python modules

wrapper 與 package 必須同版；Calendar Resolver 另需 exact requirements。

### Step 5｜保留私人 Case

不要更動自己的命盤、事件與追蹤資料。

### Step 6｜做版本確認

可在 Project 中要求：

> 請只根據目前上傳的核心檔案，列出 Metaphysics Lab Core 版本、Calendar Resolver runtime、八字與紫微 capability 的 implementation / maturity / routing，並指出哪些能力 Stable、哪些 Experimental、哪些 Planned，以及 Ziwei Transformation / Flying Core 可以處理哪些 scope。

若回答與 GitHub `VERSION.md` 或 `engine/ziwei/capabilities.py` 不一致，表示 Project 仍混有舊檔或舊 Instructions。

## 十一、更新後回答變怪時的檢查順序

1. Project Instructions 是否仍是舊版。
2. `命理分析作業規範.md` 是否最新版。
3. `命理推導計算規則.md` 是否最新版。
4. 紫微流月／流日／流時規則是否同版。
5. wrappers 與 package modules 是否版本一致。
6. `capabilities.py` 是否最新版。
7. Calendar Resolver modules 與 requirements 是否同版。
8. Ziwei Transformation / Flying modules 是否全部同步。
9. 是否同時保留多個舊版同名／近似檔案。
10. 私人命盤資料是否被 GitHub 模板誤覆蓋。

---

## 十二、GitHub 與 ChatGPT Project 不會自動同步

GitHub 更新後，Project 端仍需要手動替換／上傳新版檔案與更新 Instructions，除非未來另外建立自動部署流程。

因此每次重要 release 都應在 `CHANGELOG.md` 明確留下版本歷程，並在本文件維護 migration 清單。
