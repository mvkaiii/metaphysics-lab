# 更新與版本同步

Metaphysics Lab 的更新分成三個彼此獨立的層級：**Project Contract、Runtime、Case Schema**。先判斷變更屬於哪一層，再決定要替換什麼；不要每次更新都重建整個 Project。

目前正式 release identity 仍為 **v1.3.0｜2026-08-23**。本文件所在的 Progressive Case + Historical Blind Calibration 變更仍屬 **Unreleased**；在正式 release 前，不因此修改既有 Git tag 或把 feature branch 當正式版本。

## 一、三種版本邊界

### Project Contract

負責 AI 的固定治理與工作方式，主要對應：

```text
PROJECT_INSTRUCTIONS.md
METAPHYSICS_CORE.md
```

若只是 deterministic runtime 修正，Project Contract 不一定需要變。

Progressive Case + Historical Blind Calibration 會改變 AI 初始化／未來問事工作流，因此屬 Project Contract 變更。

### Runtime

負責可重現計算與 structured actions：

```text
metaphysics_lab.py
```

一般演算法修正、新 capability、dependency doctor 或 bundle 修正，通常只屬 Runtime 更新。

Historical Activation Selector 由 Python deterministic 計算，因此 runtime 也必須同步更新。

### Case Schema

負責私人 Case Markdown 的欄位、metadata、materialization 與 mutation 規則。

Case record type 仍是：

```text
00_專案索引.md
01_命盤核心摘要.md
02_命盤資料校驗紀錄.md
03_八字結構化資料包.md
04_紫微基礎資料包.md
05_驗證事件紀錄.md
06_流年追蹤紀錄.md
07_問事追蹤紀錄.md
08_重大決策紀錄.md
```

但 schema 1.1 起採 Progressive Case：新 Case 初始化只 materialize 00～04；05～08 在第一次真正有內容時才建立。Runtime 更新不應默認重寫私人 Case。

## 二、一般更新｜只換 Runtime

最常見的更新方式：

1. 下載新版 `metaphysics_lab.py`。
2. 在自己的 Project **只替換 `metaphysics_lab.py`**。
3. 保留原本的 `METAPHYSICS_CORE.md`、Project Instructions 與已存在的私人 Case 檔案。
4. 讓 AI 執行 `runtime_info`，確認 runtime version、capability 與 dependency 狀態。

若 Project Contract 與 Case Schema 都沒變，就到這裡為止。

不要因 runtime 更新而重新建立本命、清空驗證事件或覆寫第一版盲判。

## 三、Project Contract 更新

只有 release notes 明確說 Project Contract 改版時，才同步：

- 新的 `METAPHYSICS_CORE.md`
- 新的 `PROJECT_INSTRUCTIONS.md`

更新方式：

1. 替換 Project 中的 `METAPHYSICS_CORE.md`。
2. 把新版 `PROJECT_INSTRUCTIONS.md` 全文重新貼到 Project Instructions。
3. 保留私人 Case。
4. 重新開一個對話，讓 AI 先讀 Case index 並確認 schema compatibility。

Project Contract 更新不代表一定要重新排盤；是否重算由 release notes 與 runtime migration 要求決定。

Progressive Case + Historical Blind Calibration 這類工作流改版，正式發布時應同時更新 Runtime、`METAPHYSICS_CORE.md` 與 Project Instructions；不能只換 Python 卻讓 AI 繼續按照舊的「初始化九檔」流程工作。

## 四、Case Schema 更新

只有 release notes 明確寫出 **schema migration** 時才處理私人 Case。

AI 應先呼叫 `validate_case` / `migrate_case`，並遵守這些原則：

- same-schema compatible → `no_change`
- migration 只改需要改的檔案
- 不捏造事件、預測或決策
- 已記錄的第一版 blind forecast 不可覆寫
- subject identity 不可混用
- 不為了符合新 Progressive Case 規則而刪除舊 Case 已存在的 05～08

### Legacy Case 1.0

既有 Case schema 1.0 的九檔資料屬合法歷史資料。新版 runtime 必須能辨識／讀取 legacy 1.0；不得因 schema 1.1 改為 progressive materialization 就要求使用者刪掉空白或既有追蹤檔。

### 新 Case 1.1

新建 Case 使用 schema 1.1：

```text
初始：00～04
後續：05～08 按需求 materialize
```

`00_專案索引.md` 是 manifest；新增 05～08 時應同步更新 index 的 materialized file 狀態與相關 calibration metadata。

如果 runtime 尚未提供某一條 migration path，就不要自行猜欄位轉換方式。

## 五、能力狀態不要從固定文件猜

固定 Markdown 不再維護會快速過期的 capability matrix。

更新後讓 AI 呼叫：

```text
runtime_info
```

以 runtime 回傳的 implementation、maturity、routing、版本與 dependency status 為目前執行狀態。

`README.md`、歷史 CHANGELOG 或舊 release snapshot 可以說明某一時間點發生過什麼，但不能覆蓋 runtime 的自我描述。

## 六、什麼情況要重新計算

不是每次更新都要重算。

建議重新計算的情況：

- release notes 明確標示 natal / calendar / time-profile algorithm 有 material change
- Historical Activation Selector profile version 發生 material rule change，且使用者要重新建立 calibration baseline
- 原本 Case 有 BLOCKING conflict，且新版專門修正該問題
- 使用者提供更精確出生資料，跨越原本 precision gate
- external cross-check 新增足以改變 Resolved basis 的可信資料

單純文件、CLI、bundle、dependency doctor 或 Case export 修正，不應自動重算本命。

已經完成並鎖定的 Historical Blind Calibration 不應因小版本 runtime 更新自動覆寫；若未來 profile 升版需要重測，應建立新的 calibration id，保留舊紀錄。

## 七、更新後快速檢查

讓 AI 先做：

```text
runtime_info
```

至少確認：

- Project Contract version
- Runtime schema / runtime version
- Case Schema version
- supported actions
- capability implementation / maturity / routing
- external dependencies

若已有 Case，再跑 `validate_case`。兩者都可用後再進分析。

若 Case 尚未校準且使用者要問未來，應依目前 contract 先鎖 Stage 1，再執行 Historical Blind Calibration；不要因為 Case 是舊版本就跳過 anti-contamination 流程。

## 八、AI 環境不能執行 Runtime

若 Project 當次無法執行 Python，AI 必須明講，不能用「已更新」或「已驗證」暗示程式真的跑過。

本機可用：

```bash
python metaphysics_lab.py runtime-info --pretty
python metaphysics_lab.py request --input request.json --pretty
```

把輸出交回 AI 後再繼續。

## 九、私人資料永遠不被共用更新覆蓋

以下都屬使用者私人 Case／來源，不是 distribution update target：

```text
00_專案索引.md
01_命盤核心摘要.md
02_命盤資料校驗紀錄.md
03_八字結構化資料包.md
04_紫微基礎資料包.md
05_驗證事件紀錄.md（若已 materialize）
06_流年追蹤紀錄.md（若已 materialize）
07_問事追蹤紀錄.md（若已 materialize）
08_重大決策紀錄.md（若已 materialize）
Astralium raw chart
個人 PDF／截圖
私人事件資料
Historical Calibration 回答
```

共用 distribution 不應包含上述私人資料。

## 十、版本文件的責任

- `VERSION.md`：正式 release identity。
- `CHANGELOG.md`：Release / Unreleased 歷史與 migration 通知。
- `runtime_info`：目前 runtime 真正能做什麼。
- 本文件：告訴使用者該替換哪些檔案。

這四者回答的是不同問題，不應互相複製一份容易過期的 capability snapshot。
