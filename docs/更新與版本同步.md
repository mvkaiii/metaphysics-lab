# 更新與版本同步

一般使用者先記住一件事：**大多數程式更新只要替換 `metaphysics_lab.py`，不需要重建整個命理 Project。**

如果 Release 說明明確提到 Project Contract 或 Case Schema 改版，再依下面的進階規則處理。

目前正式版本為 **v1.4.0｜2026-08-26**。Project Contract 1.1、Case Schema 1.1、Runtime Schema 1.1 與 AI Distribution Runtime 1.1-exp 已納入本次正式 Release；v1.3.0 tag 與歷史 Release snapshot 不回頭改寫。

> 以下姓名與識別碼皆為虛構示例。

## 一、三種更新層級

Metaphysics Lab 的更新分成三層：

### Project Contract

負責 AI 的固定治理與工作方式，主要對應：

```text
project_instructions.md
metaphysics_core.md
```

如果 Release 說明明確寫 Project Contract 改版，這兩份才需要一起同步。

### Runtime

負責可重現計算與 structured actions：

```text
metaphysics_lab.py
```

一般演算法修正、新 capability、dependency doctor 或 bundle 修正通常屬 Runtime 更新。

### Case Schema

負責私人 Case Markdown 的 identity metadata、欄位、materialization 與 mutation 規則。

內部 record type / **canonical slot** 仍是：

```text
00_專案索引.md
01_命盤核心摘要.md
02_命盤資料校驗紀錄.md
03_八字結構化資料包.md
04_紫微基礎資料包.md
05_驗證事件紀錄.md
06_流年追蹤紀錄.md
07_問事追蹤紀錄.md
08_重大決策紀錄.md
```

Case Schema 1.1 的實際 persisted filename 為：

```text
<filename_label>_<SUBJECT_SHORT_ID>_<slot>_<canonical_title>.md
```

虛構範例：

```text
Alex_7F3A2C_01_命盤核心摘要.md
```

也就是 `01_命盤核心摘要.md` 是 canonical slot，而 `Alex_7F3A2C_01_命盤核心摘要.md` 才是實際檔名。

schema 1.1 同時採 Progressive Case：**Base5** = 00～04；**Progressive4** = 05～08 有真正內容時才 materialize。

## 二、最常見更新｜只換 Runtime

如果 Release 說明只說 Runtime 更新：

1. 下載新版 `metaphysics_lab.py`。
2. 在自己的 Project **只替換 `metaphysics_lab.py`**。
3. 保留原本的 `metaphysics_core.md`、Project Instructions、`命主索引.md` 與私人 Case。
4. 讓 AI 執行 `runtime_info`，確認目前程式版本、能力與 dependency 狀態。

如果 Project Contract 與 Case Schema 都沒變，到這裡就完成。

不要因 Runtime 更新而重新建立本命、清空驗證事件、重建 `subject_id` 或覆寫第一版盲判。

## 三、v1.3.0 → v1.4.0

v1.4.0 明確包含 Project Contract / Case Schema 1.1，因此這次不是「只換 Runtime」：

1. 替換 Project 中的 `metaphysics_lab.py`。
2. 替換 `metaphysics_core.md`。
3. 把新版 `project_instructions.md` 全文重新貼到 Project Instructions。
4. **保留**既有 `命主索引.md` 與私人 Case；不要自行清空事件、流年、問事或重大決策紀錄。
5. 更新後執行 `runtime_info`。
6. 若舊 Case 需要 schema migration，再依正式 `validate_case` / `migrate_case` 回傳結果處理；沒有 migration 要求就不做破壞性重建。

這次同步 Project Contract 是因為固定治理與 user-facing language boundary 有正式變更；同步 Case Schema 是為了多人 subject identity / Progressive Case 契約一致。**不代表要重新排本命。**

## 四、Project Contract 更新

只有 Release 說明明確寫 Project Contract 改版時，才同步：

- 新的 `metaphysics_core.md`
- 新的 `project_instructions.md`

更新方式：

1. 替換 Project 中的 `metaphysics_core.md`。
2. 把新版 `project_instructions.md` 全文重新貼到 Project Instructions。
3. 保留 `命主索引.md` 與私人 Case。
4. 重新開一個對話，讓 AI 先 resolve subject、讀 Case index 並確認 schema compatibility。

Project Contract 更新不代表一定要重新排盤；是否重算由 Release 說明與 migration 要求決定。

## 五、Case Schema 更新

只有 Release 說明明確寫出 **schema migration** 時，才處理私人 Case。

正式流程應先呼叫 `validate_case` / `migrate_case`，並遵守：

- same-schema compatible → `no_change`
- migration 只改真正需要改的檔案
- 不捏造事件、預測或決策
- 第一版 blind forecast 不可覆寫
- subject identity 不可混用
- 不為了符合 Progressive Case 而刪除既有合法紀錄

### Legacy Case 1.0

**Legacy Case 1.0** 是完整九檔、使用 **bare filename** 的合法歷史格式，例如：

```text
00_專案索引.md
01_命盤核心摘要.md
...
08_重大決策紀錄.md
```

新版 runtime 必須繼續 readable。升級到 1.1 **不強制**先 migration，也不要求做 destructive rename 才能讀舊 Case。

因此：

- legacy 1.0 九檔可以原樣留存並驗證／讀取。
- 不因 1.1 的 Base5 + Progressive4 就刪除 legacy 已存在的 05～08。
- 不因新 filename contract 就直接批次改舊檔名。
- 只有使用者明確執行正式 migration path 時，runtime 才建立 subject identity、更新 front matter / manifest，並回傳 old → new rename mapping。

### 新 Case 1.1

新建 Case 使用：

```text
Base5：00～04
Progressive4：05～08 按需求 materialize
```

實體檔名一律為：

```text
<filename_label>_<SUBJECT_SHORT_ID>_<slot>_<canonical_title>.md
```

虛構範例：

```text
Alex_7F3A2C_00_專案索引.md
Alex_7F3A2C_01_命盤核心摘要.md
```

該 subject 的實際 `00` 是 manifest；新增 05～08 時同步更新 `00` 的 materialized file 狀態與 calibration metadata。

如果 runtime 尚未提供某條 migration path，就不要自行猜欄位轉換方式。

## 六、Subject Identity 更新規則

`命主索引.md` 是 Project-level Subject Registry。rename 命主時：

- `subject_id` 不變。
- `subject_short_id` 不變。
- `subject_display_name` / `filename_label` 可變。
- 已存在 Case 必須一次更新 registry、該 subject 全部 materialized filenames、front matter、00 manifest 與 old → new rename mapping。
- 不能只改 registry，留下 Case 名稱與 metadata 不一致。

同名命主依不同 opaque `subject_id` 共存；不得以姓名、生日或出生地重新 derive identity。

## 七、Candidate Envelope 與 partial Case

出生時間仍是 `bounded` 或 `unknown_time` 的 Case 屬 `partial`。即使 Candidate Envelope 壓縮後只剩一個 material state，也不能因 runtime 升級就自動宣稱出生時間唯一確定。

至少以下 blocked scopes 要保留到真的有新證據解除不確定性：

- unique birth time claim
- unique hour pillar conclusion
- unique Ziwei natal conclusion
- single-chart personalized forecast

演算法更新若改變 candidate material-state grouping，可依 Release 說明重算，但不得用 majority voting、midpoint 或舊候選的「最常見值」覆蓋不確定性。

## 八、能力狀態不要從固定文件猜

固定 Markdown 不維護會快速過期的 capability matrix。更新後讓 AI 呼叫：

```text
runtime_info
```

以 runtime 回傳的 implementation、maturity、routing、版本與 dependency status 為目前技術執行狀態。

README、CHANGELOG 或歷史 Release snapshot 可以記錄某一時間點發生過什麼，但不能覆蓋 runtime 的自我描述。

## 九、什麼情況需要重新計算？

建議重新計算的情況：

- Release 說明明確標示 natal / calendar / time-profile algorithm 有 material change
- Candidate Envelope material-state algorithm 有 material change，而且該 subject 仍是 partial
- Historical Activation Selector profile version 有 material rule change，需要建立新的 calibration baseline
- 原本 Case 有 BLOCKING conflict，新版專門修正該問題
- 使用者提供更精確出生資料，跨越原本 precision gate
- 新 External cross-check 足以改變 Resolved basis

單純文件、CLI、bundle、dependency doctor、Case export 或 qualification 補強，不應自動重算本命。

已完成並鎖定的 Historical Blind Calibration 不應因小版本 Runtime 更新自動覆寫；未來若 profile 升版要重測，應建立新的 calibration id，保留舊紀錄。

## 十、更新後快速檢查

讓 AI 執行：

```text
runtime_info
```

至少確認：

- Project Contract version
- Runtime schema / runtime version
- Case Schema version
- supported actions
- capability implementation / maturity / routing
- external dependencies

一般使用者不用自己判讀全部 technical fields；若系統回報不相容或需要 migration，再依 Release 說明處理。

## 十一、版本歷史與尚未發布內容

- 正式版本與 release snapshot：`VERSION.md`
- 完整 Release / Unreleased 技術歷史：`CHANGELOG.md`
- 一般使用者 v1.4.0 發布說明：`發布說明-v1.4.0.md`
- 歷史 v1.3.0 發布說明：`發布說明-v1.3.0.md`

Phase 2C0、Phase 2B、Phase 2C 等名稱屬開發／技術歷史；一般更新不需要先理解這些 Phase。

任何 Experimental capability 都不會因文件整理、合併 `main` 或一般 patch 自動升 Stable。
