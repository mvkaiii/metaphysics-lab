# 更新與版本同步

本文件說明 GitHub 的 Metaphysics Lab 更新後，如何安全同步到自己的 ChatGPT Project，而不覆蓋私人 Case。

核心原則：

> GitHub 是系統核心的正式版本來源；私人 Project 是實際個案資料與分析環境。

兩者更新方向不同。

---

## 一、先看版本與變更紀錄

每次更新前先查看：

```text
VERSION.md
CHANGELOG.md
```

`VERSION.md` 告訴你目前正式組合；`CHANGELOG.md` 告訴你這一版新增、修改、停用或固定了哪些規則。

不要只看 Python 檔案是否有變化。規則文件與 Project Instructions 也可能影響分析行為。

---

## 二、哪些屬於共用核心

基礎 Project 通常需要同步：

```text
core/核心提示詞.md
core/命理分析作業規範.md
core/命理推導計算規則.md
core/紫微流月推導規則.md
engine/project_bazi_calendar.py
engine/project_ziwei_month.py
```

若要使用 v1.2 紫微流日 On-demand Capability，再同步：

```text
core/紫微流日推導規則.md
engine/project_ziwei_day.py
```

若要使用 v1.2 紫微流時 On-demand Capability，再同步：

```text
core/紫微流時推導規則.md
engine/project_ziwei_hour.py
```

若需要在 Python 環境**實際執行** wrapper／package，請同步對應正式實作：

```text
engine/bazi/__init__.py
engine/bazi/calendar.py
engine/ziwei/__init__.py
engine/ziwei/common.py
engine/ziwei/capabilities.py
engine/ziwei/month.py
engine/ziwei/day.py
engine/ziwei/hour.py
```

若測試基準有更新，也建議同步：

```text
tests/命理推導測試案例.md
tests/紫微流月推導測試案例.md
tests/紫微流日推導測試案例.md
tests/紫微流時推導測試案例.md
```

薄 wrapper 主要維持 repo 的相容 import / CLI 路徑；wrapper 不是獨立單檔引擎，實際執行仍需具備它依賴的 package modules，且 wrapper 與 package 必須同版。

流時另要注意：`hour.py` 依賴既有 day / month / common / capabilities；只替換 `project_ziwei_hour.py` 或 `hour.py` 都不算完整同步。

---

## 三、核心提示詞的更新方式

`core/核心提示詞.md` 最重要的用途是更新 ChatGPT Project Instructions。

因此 GitHub 的核心提示詞有變更時：

1. 開啟最新 `core/核心提示詞.md`。
2. 更新 Project Instructions。
3. 不要只把新檔上傳，卻保留舊的 Instructions。

如果 Project Instructions 與上傳的規則檔互相矛盾，容易出現「文件說能力已實作，但 AI 還是認為不存在」的狀況。

---

## 四、Python 引擎需要同步嗎

需要。

如果 GitHub 的引擎版本更新，Project 中保存的 `.py` 也要替換成同版。

目前相容入口：

```text
engine/project_bazi_calendar.py
engine/project_ziwei_month.py
engine/project_ziwei_day.py
engine/project_ziwei_hour.py
```

其中：

- `project_ziwei_day.py` 對應 v1.2 Experimental / On-demand 流日能力。
- `project_ziwei_hour.py` 對應 v1.2 Experimental / On-demand 流時能力。

v1.2 內部模組化後，正式 Python 實作分別位於 package 路徑。既有程式不需要因模組化把舊入口全部改名，但若需要真正執行 wrapper，必須一起提供其 package 依賴；只替換 wrapper 而不帶 package，實際執行會失敗。

要注意：

> `.py` 放在 Project 中代表保存正式算法，不代表每次對話都自動執行 Python。

AI 若沒有實際執行證據，不得宣稱程式已跑過。

---

## 五、Capability 狀態要一起同步

v1.2 把三件事分開：

```text
implementation
maturity
routing
```

目前開發線：

```text
紫微流月 = implemented / stable / default
紫微流日 = implemented / experimental / on_demand
紫微流時 = implemented / experimental / on_demand
細部四化／流曜／飛化 = planned / on_demand
Calendar / Input Resolver = planned
Cross-System Validation = planned
```

因此：

- `implemented`：Python 能力真的存在。
- `on_demand`：平常不預設跑，需要時才調用。
- `experimental`：可執行，但分析時降權。
- `planned`：尚不能執行。

不要再用 `enabled = false` 直接推論某能力不存在。

流時 core 採 1.5 架構：它只接受已解析的農曆日期與時辰地支。民用 datetime、timezone、DST、國曆轉農曆與 23:00 日界仍由未來 Resolver 處理，不能因 flow-hour 已 implemented 就推論 Resolver 也存在。

---

## 六、哪些私人檔案絕對不要被更新覆蓋

不要用 GitHub 的模板或共用檔案覆蓋自己的：

```text
命盤核心摘要.md
命盤資料校驗紀錄.md
驗證事件紀錄.md
流年追蹤紀錄.md
問事追蹤紀錄.md
重大決策紀錄.md
八字原始資料
紫微原始資料
個人命盤 PDF／截圖
```

`templates/` 只用來建立新檔，不是日後更新私人 Case 的來源。

---

## 七、建議同步流程

### Step 1｜查看版本

先確認 GitHub 的 `VERSION.md` 與 `CHANGELOG.md`。

### Step 2｜確認自己要哪些 capability

例如只用月份分析，就不需要每次自動跑流日或流時；希望指定日期可細看，就同步流日；希望指定時辰或比較時段，再同步流時規則與引擎。

### Step 3｜更新規則文件

替換 Project 中對應的 `core/` 規則檔。

### Step 4｜更新 Python 引擎

如果 Project 只把 Python 當知識來源，可以保留 `project_*.py` 相容入口作索引；若環境要實際執行，請同步 wrapper **以及**其 package 依賴：

```text
engine/project_bazi_calendar.py
engine/bazi/__init__.py
engine/bazi/calendar.py

engine/project_ziwei_month.py
engine/ziwei/__init__.py
engine/ziwei/common.py
engine/ziwei/month.py

# 若要流日 on-demand
engine/project_ziwei_day.py
engine/ziwei/capabilities.py
engine/ziwei/day.py

# 若要流時 on-demand
engine/project_ziwei_hour.py
engine/ziwei/hour.py
```

完整 Python 環境可直接使用 `engine.bazi` 與 `engine.ziwei` package。

### Step 5｜更新 Project Instructions

若 `core/核心提示詞.md` 有改，重新同步 Instructions。

### Step 6｜保留私人 Case

不要更動自己的命盤摘要、事件紀錄與追蹤資料。

### Step 7｜做版本確認

可以在 Project 裡問：

> 請只根據目前上傳的核心檔案，列出 Metaphysics Lab Core、八字引擎、紫微流月／流日／流時 capability 的 implementation、maturity 與 routing，並指出哪些能力可以執行但預設不跑，以及哪些民用時間解析能力仍未實作。

如果回答與 GitHub `CHANGELOG.md` 或 capability registry 不一致，表示 Project 還有舊檔或舊 Instructions 未替換。

## 八、v1.0 → v1.1 的特別升級項目

從沒有紫微流月的舊 Project 升到 v1.1，至少需要：

```text
更新 core/核心提示詞.md → 同步到 Project Instructions
更新 core/命理分析作業規範.md
更新 core/命理推導計算規則.md
新增 core/紫微流月推導規則.md
新增 engine/project_ziwei_month.py
```

建議再加入：

```text
tests/紫微流月推導測試案例.md
```

完成後，Project 應知道紫微流月只做到斗君、流月命宮與流月十二宮，且紫微流月採農曆月、八字流月採節氣月。

若要在 v1.2 模組化後的 Python 環境執行相容入口，還必須補齊對應 `engine/ziwei/` package。

---

## 九、v1.1 → v1.2 流日與流時 Capability

要加入可按需執行的紫微流日與流時，至少同步：

```text
core/紫微流月推導規則.md
core/紫微流日推導規則.md
core/紫微流時推導規則.md
engine/project_ziwei_month.py
engine/project_ziwei_day.py
engine/project_ziwei_hour.py
```

完整 Python 執行環境另同步：

```text
engine/ziwei/__init__.py
engine/ziwei/common.py
engine/ziwei/capabilities.py
engine/ziwei/month.py
engine/ziwei/day.py
engine/ziwei/hour.py
```

完成後應得到：

```text
流月：Stable / Default
流日：Experimental / On-demand
流時：Experimental / On-demand
```

這代表流日與流時**都已經可以算宮位定位**，只是一般年度／月份問題不預設執行；流時也不代表民用 datetime Resolver 已存在。

目前仍未代表：

- 流時四化已實作
- 細部四化已實作
- 流曜或細層飛化已實作
- Calendar / Input Resolver 已實作
- Cross-System Validation 已實作

這些會在各自算法、測試與外部校驗完成後另行加入。

## 十、如果更新後回答變怪，先檢查什麼

依序檢查：

1. Project Instructions 是否仍是舊版。
2. `命理分析作業規範.md` 是否已替換。
3. `命理推導計算規則.md` 是否已替換。
4. `紫微流月推導規則.md` 是否存在且為新版。
5. 若要用流日，`紫微流日推導規則.md` 是否存在。
6. 若要用流時，`紫微流時推導規則.md` 是否存在，且 `hour.py` / `day.py` / `month.py` / `capabilities.py` 是否同版。
7. wrappers 與 package modules 是否版本一致且依賴齊全。
8. 是否同時保留多個舊版同名／近似檔案。
9. capability registry 是否與文件敘述一致。
10. `VERSION.md` / `CHANGELOG.md` 與實際 Project 檔案是否一致。

不要先修改命盤或私人事件來「配合」新版系統。

---

## 十一、GitHub 與 Project 不會自動同步

目前應把兩者視為兩套環境：

- GitHub：正式核心版本庫
- ChatGPT Project：實際使用副本

GitHub 更新後，Project 端仍需要手動替換／上傳新版檔案與更新 Instructions，除非未來另外建立自動部署流程。

因此每次重要版本更新，都應在 CHANGELOG 明確列出「Project 需要同步哪些檔案」。
