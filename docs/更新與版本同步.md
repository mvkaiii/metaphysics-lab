# 更新與版本同步

Metaphysics Lab 的更新分成三個彼此獨立的層級：**Project Contract、Runtime、Case Schema**。先判斷變更屬於哪一層，再決定要替換什麼；不要每次更新都重建整個 Project。

目前正式 release identity 仍為 **v1.2.0｜2026-08-21**。AI Distribution Pack 是 Unreleased 工作，不因此修改 `VERSION.md`、Git tag 或既有正式 release。

## 一、三種版本邊界

### Project Contract

負責 AI 的固定治理與工作方式，主要對應：

```text
PROJECT_INSTRUCTIONS.md
METAPHYSICS_CORE.md
```

若只是 deterministic runtime 修正，Project Contract 不一定需要變。

### Runtime

負責可重現計算與 structured actions：

```text
metaphysics_lab.py
```

一般演算法修正、新 capability、dependency doctor 或 bundle 修正，通常只屬 Runtime 更新。

### Case Schema

負責私人九份 Case Markdown 的欄位、metadata 與 mutation 規則。

Case Schema 只有在明確需要資料結構 migration 時才變。Runtime 更新不應默認重寫私人 Case。

## 二、一般更新｜只換 Runtime

最常見的更新方式：

1. 下載新版 `metaphysics_lab.py`。
2. 在自己的 Project **只替換 `metaphysics_lab.py`**。
3. 保留原本的 `METAPHYSICS_CORE.md`、Project Instructions 與九份私人 Case。
4. 讓 AI 執行 `runtime_info`，確認 runtime version、capability 與 dependency 狀態。

若 Project Contract 與 Case Schema 都沒變，就到這裡為止。

不要因 runtime 更新而重新建立本命、清空驗證事件或覆寫第一版盲判。

## 三、Project Contract 更新

只有 release notes 明確說 Project Contract 改版時，才同步：

- 新的 `METAPHYSICS_CORE.md`
- 新的 `PROJECT_INSTRUCTIONS.md`

更新方式：

1. 替換 Project 中的 `METAPHYSICS_CORE.md`。
2. 把新版 `PROJECT_INSTRUCTIONS.md` 全文重新貼到 Project Instructions。
3. 保留私人 Case。
4. 重新開一個對話，讓 AI 先讀 Case index 並確認 schema compatibility。

Project Contract 更新不代表一定要重新排盤；是否重算由 release notes 與 runtime migration 要求決定。

## 四、Case Schema 更新

只有 release notes 明確寫出 **schema migration** 時才處理私人 Case。

AI 應先呼叫 `validate_case` / `migrate_case`，並遵守這些原則：

- same-schema compatible → `no_change`
- migration 只改需要改的檔案
- 不捏造事件、預測或決策
- 已記錄的第一版 blind forecast 不可覆寫
- subject identity 不可混用

如果 runtime 尚未提供對應 migration path，就不要自行猜欄位轉換方式。

## 五、能力狀態不要從固定文件猜

固定 Markdown 不再維護會快速過期的 capability matrix。

更新後讓 AI 呼叫：

```text
runtime_info
```

以 runtime 回傳的 implementation、maturity、routing、版本與 dependency status 為目前執行狀態。

`README.md`、歷史 CHANGELOG 或舊 release snapshot 可以說明某一時間點發生過什麼，但不能覆蓋 runtime 的自我描述。

## 六、什麼情況要重新計算

不是每次更新都要重算。

建議重新計算的情況：

- release notes 明確標示 natal / calendar / time-profile algorithm 有 material change
- 原本 Case 有 BLOCKING conflict，且新版專門修正該問題
- 使用者提供更精確出生資料，跨越原本 precision gate
- external cross-check 新增足以改變 Resolved basis 的可信資料

單純文件、CLI、bundle、dependency doctor 或 Case export 修正，不應自動重算本命。

## 七、更新後快速檢查

讓 AI 先做：

```text
runtime_info
```

至少確認：

- Project Contract version
- Runtime schema / runtime version
- Case Schema version
- supported actions
- capability implementation / maturity / routing
- external dependencies

若已有 Case，再跑 `validate_case`。兩者都可用後再進分析。

## 八、AI 環境不能執行 Runtime

若 Project 當次無法執行 Python，AI 必須明講，不能用「已更新」或「已驗證」暗示程式真的跑過。

本機可用：

```bash
python metaphysics_lab.py runtime-info --pretty
python metaphysics_lab.py request --input request.json --pretty
```

把輸出交回 AI 後再繼續。

## 九、私人資料永遠不被共用更新覆蓋

以下都屬使用者私人 Case／來源，不是 distribution update target：

```text
00_專案索引.md
01_命盤核心摘要.md
02_命盤資料校驗紀錄.md
03_八字結構化資料包.md
04_紫微基礎資料包.md
05_驗證事件紀錄.md
06_流年追蹤紀錄.md
07_問事追蹤紀錄.md
08_重大決策紀錄.md
Astralium raw chart
個人 PDF／截圖
私人事件資料
```

共用 distribution 不應包含上述私人資料。

## 十、版本文件的責任

- `VERSION.md`：正式 release identity。
- `CHANGELOG.md`：Release / Unreleased 歷史與 migration 通知。
- `runtime_info`：目前 runtime 真正能做什麼。
- 本文件：告訴使用者該替換哪些檔案。

這四者回答的是不同問題，不應互相複製一份容易過期的 capability snapshot。
