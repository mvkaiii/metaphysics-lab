# 更新與版本同步

一般使用者先記住一件事：**大多數 Runtime-only 更新只要替換 `metaphysics_lab.py`，不需要重建整個命理 Project。** 但如果 Release 明確變更 Project Contract，就要同步核心規則與 Project Instructions。

目前最新正式版本為 **v1.7.1｜2026-09-25**。Release Version 為 1.7.1；Project Contract 仍是 1.2、Runtime Schema 1.1、**Case Schema 1.1**、AI Distribution Runtime 1.2-exp。v1.7.1 只補 release identity metadata，既有私人 Case 不需要重建，也不要求 destructive migration。`v1.7.1` GitHub Release 已正式建立；歷史 tag / Release snapshot 不回頭改寫。

> 以下姓名與識別碼皆為虛構示例。

## 一、三種更新層級

### Project Contract

負責 AI 的固定治理與工作方式，主要對應：

```text
project_instructions.txt
metaphysics_core.md
```

如果 Release 說明明確寫 Project Contract 改版，這兩份要一起同步。

### Runtime

負責可重現計算與 structured actions：

```text
metaphysics_lab.py
```

一般演算法修正、新 capability、dependency doctor 或 bundle 修正通常屬 Runtime 更新。

### Case Schema

負責私人 Case Markdown 的 identity metadata、欄位、materialization 與 mutation 規則。Case Schema 1.1 的 canonical slot 仍是 00～08；實際 persisted filename 為：

```text
<filename_label>_<SUBJECT_SHORT_ID>_<slot>_<canonical_title>.md
```

虛構範例：

```text
Alex_7F3A2C_01_命盤核心摘要.md
```

schema 1.1 同時採 Progressive Case：**Base5** = 00～04；**Progressive4** = 05～08 有真正內容時才 materialize。

## 二、最常見更新｜只換 Runtime

如果 Release 說明只說 Runtime 更新：

1. 下載新版 `metaphysics_lab.py`。
2. 在自己的 Project **只替換 `metaphysics_lab.py`**。
3. 保留原本的 `metaphysics_core.md`、Project Instructions、`命主索引.md` 與私人 Case。
4. 讓 AI 執行 `runtime_info`，確認目前程式版本、能力與 dependency 狀態。

如果 Project Contract 與 Case Schema 都沒變，到這裡就完成。不要因 Runtime 更新而重新建立本命、清空驗證事件、重建 `subject_id` 或覆寫第一版盲判。

## 三、v1.3.0 → v1.4.0

v1.4.0 明確包含 Project Contract / Case Schema 1.1，因此不是「只換 Runtime」：替換 runtime 與核心規則，並以當時的 `project_instructions.md` 重新貼 Project Instructions，保留既有 `命主索引.md` 與私人 Case。若舊 Case 真的需要 schema migration，再依正式 `validate_case` / `migrate_case` 回傳處理；沒有 migration 要求就不做破壞性重建。

## 四、v1.4.0 → v1.5.0

v1.5.0 的一般使用者發行面改成三檔 User Package，Case Schema 仍維持 1.1，不要求重建私人 Case。

1. 下載 `Metaphysics-Lab-v1.5.0-User-Package.zip`。
2. 替換 `metaphysics_lab.py` 與 `metaphysics_core.md`。
3. 打開 `project_instructions.txt`，把全文重新貼到 Project Instructions。
4. 保留既有 `命主索引.md`、命盤資料與 05～08 追蹤紀錄。
5. 更新後執行 `runtime_info`。

Project Instructions 的發行副檔名改成 `.txt` 是為了手機／電腦開啟與複製方便；不是 Case Schema migration，也不代表要重新排盤。

## 五、v1.5.0 → v1.6.0

v1.6.0 的 User Package 仍是同一個三檔安裝面，建議三個檔案一起同步；Case Schema 仍維持 1.1，不要求重建私人 Case。

1. 下載 `Metaphysics-Lab-v1.6.0-User-Package.zip`。
2. 替換 Project 中的 `metaphysics_lab.py`。
3. 替換 `metaphysics_core.md`。
4. 打開新版 `project_instructions.txt`，把全文重新貼到 Project Instructions。
5. **保留**既有 `命主索引.md`、出生盤、驗證事件、流年／問事／重大決策紀錄與已鎖定的第一版預測。
6. 更新後執行 `runtime_info`。

v1.6.0 的 Y1 年度紫微四化 Project 推導能力維持 **Experimental / Project-derived**；正式納入軟體不等於已證明比舊方法更準，也不代表 selector v2 / interpretation v2 已取得 default promotion。

## 六、v1.6.0 → v1.7.0

v1.7.0 是 reliability / usability release。Project Contract 從 1.1 升到 1.2，但 **Case Schema 1.1 unchanged**；因此這次三個發行檔案要一起同步，私人 Case 則原樣保留。

更新方式：

1. 下載 `Metaphysics-Lab-v1.7.0-User-Package.zip`。
2. 替換 Project 中的 `metaphysics_lab.py`。
3. 替換 `metaphysics_core.md`。
4. 打開新版 `project_instructions.txt`，把全文重新貼到 Project Instructions。
5. **三個檔案一起**完成後，保留既有 `命主索引.md`、本命資料、External raw chart、驗證事件、流年／問事／重大決策紀錄與所有已鎖定預測。
6. 執行 `runtime_info`，確認 Project Contract 1.2、Runtime Schema 1.1、Case Schema 1.1 與 capability manifest/runtime 狀態。

本次不需要重建 Case、重新產生 `subject_id`、清空 05～08，或把舊預測重新鎖定。Case Doctor 可以診斷 legacy / duplicate / conflict 並提出 dry-run reconciliation plan，但**不自動刪除**檔案；需要 mutation 時仍遵守既有確認與 migration/update action 邊界。

Prospective Validation 2.0 會把 `clean_prospective`、`conditional_prospective`、`hidden_existing_reality`、`retrospective_calibration` 分開。已知安排或 lock 前已存在的隱藏事實不得灌入 clean prospective denominator。

Guided Inquiry 會主動提供 3～4 個後續詢問方向，預設 3 個；這些只是導航，不是新命理證據，也不會提高 specificity 或 confidence authority。

## 七、v1.7.0 → v1.7.1

v1.7.1 是 **Runtime metadata-only patch**。它的目的，是讓 `runtime_info` 明確同時回報：

```text
Release Version            1.7.1
AI Distribution Runtime    1.2-exp
Project Contract            1.2
Runtime Schema              1.1
Case Schema                 1.1
```

這兩個版本層級不要混在一起：`v1.7.1` 是整體 Metaphysics Lab Release；`1.2-exp` 是內部 AI Distribution Runtime component version。

如果目前已經是 **v1.7.0**：

1. 下載 v1.7.1 Release Asset 的新版 `metaphysics_lab.py`，或下載 `Metaphysics-Lab-v1.7.1-User-Package.zip` 後只取出該檔。
2. **只替換 `metaphysics_lab.py`**。
3. `metaphysics_core.md` 不需要替換；Project Instructions 也不需要重貼。
4. 保留 `命主索引.md`、所有私人 Case、命盤、驗證事件、追蹤紀錄與已鎖定預測。
5. 執行 `runtime_info`，確認 `release_version = 1.7.1`、`distribution_runtime_version = 1.2-exp`。

舊 Case 裡的 `project_contract_version: 1.1` 或 `runtime_version_if_applicable: 1.1-exp` 可能是建立當時的歷史 provenance；v1.7.1 **不要求批次覆寫這些欄位**。只要 Case Schema 1.1 可被新版 runtime 正常 validate，就不是升級失敗。

## 八、Project Contract 更新

只有 Release 說明明確寫 Project Contract 改版時，才同步新的 `metaphysics_core.md` 與 `project_instructions.txt`。更新後保留 `命主索引.md` 與私人 Case，再讓 AI resolve subject、讀 Case index 並確認 schema compatibility。

Project Contract 更新不代表一定要重新排盤；是否重算由 Release 說明與 migration 要求決定。v1.7 的 Project Contract 1.2 **不伴隨 Case Schema migration**。

## 九、Case Schema 更新

只有 Release 說明明確寫出 **schema migration** 時，才處理私人 Case。正式流程先呼叫 `validate_case` / `migrate_case`，並遵守：

- same-schema compatible → `no_change`
- migration 只改真正需要改的檔案
- 不捏造事件、預測或決策
- 第一版 blind forecast 不可覆寫
- subject identity 不可混用
- 不為了 Progressive Case 而刪除既有合法紀錄

### Legacy Case 1.0

Legacy Case 1.0 是完整九檔、使用 bare filename 的合法歷史格式。新版 runtime 必須繼續 readable；升級到 1.1 不強制先 migration，也不要求 destructive rename。只有使用者明確執行正式 migration path 時，runtime 才建立 subject identity、更新 front matter / manifest 並回傳 old → new rename mapping。

### 新 Case 1.1

新建 Case 使用 Base5（00～04）＋ Progressive4（05～08 按需求 materialize），實體檔名維持 `<filename_label>_<SUBJECT_SHORT_ID>_<slot>_<canonical_title>.md`。如果 runtime 尚未提供某條 migration path，就不要自行猜欄位轉換方式。

## 十、Subject Identity 更新規則

`命主索引.md` 是 Project-level Subject Registry。rename 命主時 `subject_id` / `subject_short_id` 不變，`subject_display_name` / `filename_label` 可變；已存在 Case 必須一致更新 registry、materialized filenames、front matter、00 manifest 與 rename mapping。不能只改 registry 留下 metadata 不一致。

## 十一、Candidate Envelope 與 partial Case

出生時間仍是 `bounded` 或 `unknown_time` 的 Case 屬 `partial`。即使 Candidate Envelope 壓縮後只剩一個 material state，也不能因 runtime 升級就自動宣稱出生時間唯一確定。需要唯一出生時間的結論保持 blocked，除非真的有新證據解除不確定性。

## 十二、能力狀態不要從固定文件猜

固定 Markdown 不維護會快速過期的 capability matrix。更新後讓 AI 呼叫：

```text
runtime_info
```

以 runtime 回傳的 implementation、maturity、routing、版本與 dependency status 為目前技術執行狀態。任何 Experimental capability 都**不因 v1.7 發布而自動升級**或因文件整理、合併 `main` 自動變 Stable。

## 十三、什麼情況需要重新計算？

建議重新計算的情況包括：Release 明確標示 natal/calendar/time-profile algorithm 有 material change、Candidate Envelope material-state algorithm 有 material change且 subject 仍 partial、profile 版本 material rule change、原 Case 有 BLOCKING conflict且新版專門修正、使用者提供更精確出生資料，或新的 External cross-check 改變 Resolved basis。

單純文件、CLI、bundle、dependency doctor、Case export 或 qualification 補強，不應自動重算本命。已完成並鎖定的 Historical Blind Calibration 也不應因小版本 Runtime 更新自動覆寫。

## 十四、更新後快速檢查

讓 AI 執行 `runtime_info`，至少確認：Project Contract version、Runtime schema/runtime version、Case Schema version、supported actions、capability implementation/maturity/routing、external dependencies。若系統回報不相容或需要 migration，再依 Release 說明處理。
