# 更新與版本同步

Metaphysics Lab 的更新分成三個彼此獨立的層級：**Project Contract、Runtime、Case Schema**。先判斷變更屬於哪一層，再決定要替換什麼；不要每次更新都重建整個 Project。

目前正式 release identity 仍為 **v1.3.0｜2026-08-23**。本文件所在的 Subject Identity + Candidate Envelope + Progressive Case + Historical Blind Calibration 變更仍屬 **Unreleased**；在正式 release 前，不因此修改既有 Git tag 或把 feature branch 當正式版本。

## 一、三種版本邊界

### Project Contract

負責 AI 的固定治理與工作方式，主要對應：

```text
PROJECT_INSTRUCTIONS.md
METAPHYSICS_CORE.md
```

若只是 deterministic runtime 修正，Project Contract 不一定需要變。Subject resolution、Candidate Envelope、Progressive Case 與 Historical Blind Calibration 會改變 AI 初始化／未來問事工作流，因此屬 Project Contract 變更。

### Runtime

負責可重現計算與 structured actions：

```text
metaphysics_lab.py
```

一般演算法修正、新 capability、dependency doctor 或 bundle 修正，通常只屬 Runtime 更新。Subject Registry、`natal.candidate_envelope`、Historical Activation Selector 與 Case migration 都由 runtime 實作。

### Case Schema

負責私人 Case Markdown 的 identity metadata、欄位、materialization 與 mutation 規則。

內部 record type / **canonical slot** 仍是：

```text
00_專案索引.md
01_命盤核心摘要.md
02_命盤資料校驗紀錄.md
03_八字結構化資料包.md
04_紫微基礎資料包.md
05_驗證事件紀錄.md
06_流年追蹤紀錄.md
07_問事追蹤紀錄.md
08_重大決策紀錄.md
```

Case Schema 1.1 的 persisted filename 不再是上面的裸 slot name，而固定為：

```text
<filename_label>_<SUBJECT_SHORT_ID>_<slot>_<canonical_title>.md
```

例如：

```text
Kai_7F3A2C_01_命盤核心摘要.md
```

也就是 `01_命盤核心摘要.md` 是 canonical slot，`Kai_7F3A2C_01_命盤核心摘要.md` 才是 schema 1.1 實際檔名。

schema 1.1 同時採 Progressive Case：**Base5** = 00～04 初始化就存在；**Progressive4** = 05～08 第一次真正有內容時才 materialize。Runtime 更新不應默認重寫私人 Case。

## 二、一般更新｜只換 Runtime

最常見的更新方式：

1. 下載新版 `metaphysics_lab.py`。
2. 在自己的 Project **只替換 `metaphysics_lab.py`**。
3. 保留原本的 `METAPHYSICS_CORE.md`、Project Instructions、`命主索引.md` 與已存在的私人 Case。
4. 讓 AI 執行 `runtime_info`，確認 runtime version、capability 與 dependency 狀態。

若 Project Contract 與 Case Schema 都沒變，就到這裡為止。

不要因 runtime 更新而重新建立本命、清空驗證事件、重建 `subject_id` 或覆寫第一版盲判。

## 三、Project Contract 更新

只有 release notes 明確說 Project Contract 改版時，才同步：

- 新的 `METAPHYSICS_CORE.md`
- 新的 `PROJECT_INSTRUCTIONS.md`

更新方式：

1. 替換 Project 中的 `METAPHYSICS_CORE.md`。
2. 把新版 `PROJECT_INSTRUCTIONS.md` 全文重新貼到 Project Instructions。
3. 保留 `命主索引.md` 與私人 Case。
4. 重新開一個對話，讓 AI 先 resolve subject、讀 Case index 並確認 schema compatibility。

Project Contract 更新不代表一定要重新排盤；是否重算由 release notes 與 runtime migration 要求決定。

這類工作流改版正式發布時，Runtime、`METAPHYSICS_CORE.md` 與 Project Instructions 應同步；不能只換 Python 卻讓 AI 繼續按照舊的單命主／初始化九檔流程工作。

## 四、Case Schema 1.0 → 1.1 相容與 migration

只有 release notes 明確寫出 **schema migration** 時才處理私人 Case。AI 應先呼叫 `validate_case` / `migrate_case`，並遵守：

- same-schema compatible → `no_change`
- migration 只改需要改的檔案
- 不捏造事件、預測或決策
- 已記錄的第一版 blind forecast 不可覆寫
- subject identity 不可混用
- 不為了符合新 Progressive Case 規則而刪除舊 Case 已存在的 05～08

### Legacy Case 1.0

**Legacy Case 1.0** 是完整九檔、使用 **bare filename** 的合法歷史格式，例如：

```text
00_專案索引.md
01_命盤核心摘要.md
...
08_重大決策紀錄.md
```

新版 runtime 必須繼續 readable。升級到 1.1 **不強制**先做 migration，也不要求使用者做 destructive rename 才能讀舊 Case。

因此：

- legacy 1.0 九檔可以原樣留存並驗證／讀取。
- 不因 1.1 的 Base5 + Progressive4 就刪除 legacy 已存在的 05～08。
- 不因新 filename contract 就直接批次改舊檔名。
- 只有使用者明確執行正式 migration path 時，runtime 才建立 subject identity、更新 front matter / manifest，並回傳 old → new rename mapping。

### 新 Case 1.1

新建 Case 使用 schema 1.1：

```text
Base5：00～04
Progressive4：05～08 按需求 materialize
```

實體檔名一律為：

```text
<filename_label>_<SUBJECT_SHORT_ID>_<slot>_<canonical_title>.md
```

例如：

```text
Kai_7F3A2C_00_專案索引.md
Kai_7F3A2C_01_命盤核心摘要.md
```

該 subject 的實際 `00` 是 manifest；新增 05～08 時應同步更新該 `00` 的 materialized file 狀態與 calibration metadata。

如果 runtime 尚未提供某一條 migration path，就不要自行猜欄位轉換方式。

## 五、Subject Identity 更新規則

`命主索引.md` 是 Project-level Subject Registry。rename 命主時：

- `subject_id` 不變。
- `subject_short_id` 不變。
- `subject_display_name` / `filename_label` 可變。
- 已存在 Case 必須一次更新 registry、該 subject 全部 materialized filenames、front matter、00 manifest 與 old → new rename mapping。
- 不能只改 registry，留下 Case 名稱與 metadata 不一致。

同名命主依不同 opaque `subject_id` 共存；不得以姓名、生日或出生地重新 derive identity。

## 六、Candidate Envelope 與 partial Case 更新規則

出生時間仍是 `bounded` 或 `unknown_time` 的 Case 屬 `partial`，即使 Candidate Envelope 壓縮後只剩一個 material state，也不能因 runtime 升級自動改成唯一完整盤。

下列 blocked scopes 必須持續保留，直到有足夠證據真正解除出生時間不確定性：

- unique birth time claim
- unique hour pillar conclusion
- unique Ziwei natal conclusion
- single-chart personalized forecast

演算法更新若改變候選 material state 分組，可依 release notes重算 Candidate Envelope，但不得以 majority voting、midpoint 或舊候選的「最常見值」覆蓋不確定性。

## 七、能力狀態不要從固定文件猜

固定 Markdown 不維護會快速過期的 capability matrix。更新後讓 AI 呼叫：

```text
runtime_info
```

以 runtime 回傳的 implementation、maturity、routing、版本與 dependency status 為目前執行狀態。

`README.md`、歷史 CHANGELOG 或舊 release snapshot 可以說明某一時間點發生過什麼，但不能覆蓋 runtime 的自我描述。

## 八、什麼情況要重新計算

不是每次更新都要重算。建議重新計算的情況：

- release notes 明確標示 natal / calendar / time-profile algorithm 有 material change
- Candidate Envelope material-state algorithm 有 material change，且該 subject 仍是 partial
- Historical Activation Selector profile version 發生 material rule change，且使用者要重新建立 calibration baseline
- 原本 Case 有 BLOCKING conflict，且新版專門修正該問題
- 使用者提供更精確出生資料，跨越原本 precision gate
- external cross-check 新增足以改變 Resolved basis 的可信資料

單純文件、CLI、bundle、dependency doctor 或 Case export 修正，不應自動重算本命。

已經完成並鎖定的 Historical Blind Calibration 不應因小版本 runtime 更新自動覆寫；若未來 profile 升版需要重測，應建立新的 calibration id，保留舊紀錄。

## 九、更新後快速檢查

讓 AI 先做：

```text
runtime_info
```

至少確認：

- Project Contract version
- Runtime schema / runtime version
- Case Schema version
- supported actions
- capability implementation / maturity / routing
- external dependencies

若已有 `命主索引.md` 與 Case，先 resolve subject，再跑 `validate_case`。兩者都可用後再進分析。

若 Case 尚未校準且使用者要問未來，應依目前 contract 先鎖 Stage 1，再執行 Historical Blind Calibration；不要因為 Case 是舊版本就跳過 anti-contamination 流程。

## 十、AI 環境不能執行 Runtime

若 Project 當次無法執行 Python，AI 必須明講，不能用「已更新」或「已驗證」暗示程式真的跑過。

本機可用：

```bash
python metaphysics_lab.py runtime-info --pretty
python metaphysics_lab.py request --input request.json --pretty
```

把輸出交回 AI 後再繼續。

## 十一、私人資料永遠不被共用更新覆蓋

以下都屬使用者私人 Case／來源，不是 distribution update target：

```text
命主索引.md
<filename_label>_<SUBJECT_SHORT_ID>_<slot>_<canonical_title>.md
Astralium raw chart
個人 PDF／截圖
私人事件資料
Historical Calibration 回答
```

其中 schema 1.1 例如 `Kai_7F3A2C_01_命盤核心摘要.md`；legacy schema 1.0 也可能仍使用 bare filename。共用 distribution 不應包含上述私人資料。

## 十二、版本文件的責任

- `VERSION.md`：正式 release identity。
- `CHANGELOG.md`：Release / Unreleased 歷史與 migration 通知。
- `runtime_info`：目前 runtime 真正能做什麼。
- 本文件：告訴使用者該替換哪些檔案、何時 migration。

這四者回答的是不同問題，不應互相複製一份容易過期的 capability snapshot。
