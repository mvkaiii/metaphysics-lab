# 命理分析作業規範

## 文件定位

本文件是 Metaphysics Lab 的最高層命理分析作業規範。它規範資料讀取順序、命盤建立、八字／紫微／奇門邊界、問事盲判、Project 原生盤面與 Project 推導盤面、事件校準、信心與資料治理。

本文件是分析規則來源，不是任何命主的盤面事實來源。

---

# 一、固定資料讀取順序

回答任何命理、本命、流年、決策或多人合盤問題時：

1. 完整讀取並遵循 `命理分析作業規範.md`。
2. 判斷問題類型：建立命盤、命盤驗證、本命分析、流年問事、行動決策、合盤多人。
3. 依問題讀取命盤資料校驗紀錄、命盤核心摘要、八字／紫微資料包、推導規則、必要現實條件與追蹤紀錄。
4. 區分資料類型、來源與版本。
5. 通過 Input Resolution / Precision Gate 後，才建立需要的時間層級。
6. 再開始正式分析。

若本文件不存在、無法存取或讀取失敗，必須明確告知使用者，不得假裝已遵循，也不得依記憶補造規範內容。

## Input Resolution / Precision Gate

固定原則：

> **Precision must be earned by input.**

- 先判斷 target capability 所需的最低精度。
- 輸入不足或不唯一時，只能追問、保留候選或降級分析。
- 只追問缺少欄位，不重問已知資料。
- 不得自行補值；不得為了滿足下游 API 補假日期、假時間、假出生地、假 timezone、假性別或假四柱。
- Calendar Resolver 只建立 neutral civil/calendar context；Bazi、Ziwei、Qimen 的命理日界與時間 profile 必須分離。

完整本命 Mode A 的最低使用者輸入為：性別、Gregorian 出生日期、出生時間、出生地。出生地由 Location Resolver 轉成座標與 IANA timezone；普通使用者不必手動提供經緯度或 timezone。

若只有四柱，可建立八字 imported/external natal view；不得反推出唯一的紫微完整本命盤。若有 Astralium 或其他第三方結構化命盤，視為 external source，不得覆寫 Project 自算結果。

# 二、問事採雙階段流程

流年問事、未來趨勢與行動決策，在不是歷史回顧或驗盤時必須採：

**第一階段盲判 → 第二階段事件校準**

## 第一階段：盲判

第一版判斷前不讀「驗證事件紀錄.md」中的既有事件。先讀命盤事實、已校驗資料、必要現實條件與正式規則，完成純盤面前向判斷。

至少回答：

- 哪些領域最活躍
- 最可能的事件類型
- 機會來源
- 風險來源
- 有利與不利時間窗
- 應進攻、觀察或防守
- 最重要觀察指標

不得利用已知歷史事件製造「原本就預測到」的效果。

## 第二階段：事件校準

第一版盲判完成並鎖定後，才讀驗證事件與已確認歷史事件，用於校準落地形式、提高或降低信心、修正策略。

不得改寫第一版盲判、刪掉失準判斷、把已知事件反寫成原本就預測到，或為了顯得準而事後硬套。

命盤驗證問題可直接使用驗證事件，不需盲判隔離。

---

# 三、八種資料類型必須分開

分析時永遠區分：

1. 原始盤面事實
2. 已校驗資料
3. Project 原生盤面
4. Project 推導盤面
5. 已驗證事件
6. 命理推論
7. 研究假說
8. 當次現實背景

## 1. 原始盤面事實

第三方或原始來源直接列出的欄位，例如 Astralium、原始 PDF、正式結構化資料中的四柱、宮位、星曜、四化、大限等。來源沒有列出的欄位，不得宣稱是該來源直接輸出。

## 2. 已校驗資料

不同來源比對後已確認的出生時間、四柱、時辰、排盤體系、真太陽時口徑與其他穩定欄位。

## 3. Project 原生盤面

Metaphysics Lab 由出生資料經固定、版本化、可重現的 Natal Engine 建立的本命盤，例如 Project Bazi Natal 與 Project Ziwei Natal。

Project 原生盤面不是 Astralium 原始輸出，也不是未來流年／流月／流日／流時的 Project 推導盤面。Bazi Natal 與 Ziwei Natal 目前 maturity 均為 **Experimental**，可執行但不得假裝 Stable。

## 4. Project 推導盤面

依固定算法由本命、運限與目標時間衍生出的流年、流月、流日、流時、四化／飛化等盤面。必須標示為 Project 推導，不得冒充第三方直接輸出。

## 5. 已驗證事件

只指真正已發生或已確認的人生事件。

## 6. 命理推論

對盤面事實的解讀，不是盤面事實，也不是已驗證事件。

## 7. 研究假說

過去 AI、命理師或不同流派提出但尚未充分驗證的觀點，只能作參考。

## 8. 當次現實背景

使用者本次提供的現實條件。重大決策時，現實背景具有最高實務權重。

# 四、Natal Chart Foundation｜External / Project / Resolved

Phase 2C0 的本命資料固定保留三層：

- **External**：Astralium、已知四柱或其他第三方結構化命盤。
- **Project**：Metaphysics Lab deterministic Natal Engine 建立的 Project 原生盤面。
- **Resolved**：欄位級 reconciliation 後供下游使用的選擇結果。

固定比較狀態：

`MATCH / EQUIVALENT / CONFLICT / NOT_COMPARABLE`

固定嚴重度：

`INFO / CAUTION / BLOCKING`

External / Project raw views 必須永久分開保存，不得覆寫。Resolved 只代表當前 authority policy 的選擇，不得把 CONFLICT 改寫成 MATCH。

### Authority policy

- Project Natal Engine 為 **Experimental** 時，若 Astralium 等 external source 與 Project 發生實質衝突，Resolved 預設採 external；衝突狀態仍保留。
- 未來若對應 Project capability 經獨立 promotion 成為 **Stable**，可改由 Project 作預設 Resolved source；既有 conflict 仍不得消失。
- Astralium 為可選 external qualification source，不是 Project runtime dependency。

只有實質影響盤面的差異才需要在普通使用者介面突出顯示。單純分鐘差但不改變有效時辰／依賴欄位時，可標為 EQUIVALENT。

---

# 五、出生時間與真太陽時

必須分開保存原始與有效時間，不得把校正後時間覆蓋原始輸入。Phase 2C0 至少保留：

- `reported_civil_time`
- `normalized_civil_time`
- `bazi_effective_time`
- `ziwei_effective_time`

各 view 必須帶 profile、rule version、adjustment、calculation basis 與 provenance。

Calendar Resolver 不負責真太陽時；它只處理 civil datetime、timezone、DST、農曆與 neutral hour branch 等基礎曆法責任。

八字與紫微使用獨立 time profile。不得因紫微使用真太陽時，就把同一校正無條件套到八字或未來事件時間。

若時間校正跨越日期、日柱、時辰或其他會改盤的邊界，必須顯示原始時間、校正後時間與影響，進入校驗／reconciliation；不得靜默選邊。

# 六、八字使用原則

子平八字主要負責本命底層結構、日主、格局、十神、五行、喜忌、長期決策模式、八字大運與流年／流月／流日／流時。

Project Bazi Natal 只輸出 deterministic facts，例如四柱、日主、藏干、十神、五行基礎資料與大運資料。主觀格局、喜用神、神煞總表等不因 Natal Builder 可計算就自動變成盤面事實。

不同來源若採不同真太陽時、子時換日、起運算法、五行計數或神煞規則，必須保留來源與 profile，不得無說明混用。

八字大運與紫微大限不得混稱。

---

# 七、紫微斗數使用原則

紫微主要負責十二宮、星曜、命身宮、生年四化、自化／飛化、大限、小限、流年與已正式啟用的細時間層。

Project Ziwei Natal 由 versioned profile 建立本命宮位、星曜、亮度資料（來源有定義時）、生年四化／飛化、五行局與大限等 deterministic facts；目前為 Experimental。

目前時間 capability：

```text
紫微流月定位 = implemented / stable / default
紫微流日定位 = implemented / experimental / on_demand
紫微流時定位 = implemented / experimental / on_demand
Ziwei Transformation Core = implemented / stable / on_demand
Ziwei Flying Core = implemented / stable / on_demand
Fine Cycle stem/transformations/flying = implemented / experimental / on_demand
ziwei.flowing_stars = planned / on_demand
```

Fine Cycle profile：`ziwei-fine-cycle-lunar-late-zi-v1`；day boundary：`late_zi_forward-v1`。Calendar Resolver 維持 neutral；23:00 紫微 effective-day 前進只由 fine-cycle profile 負責。

不得因宮位、stem、四化或飛化可執行，就自行宣稱 `ziwei.flowing_stars` 已實作。

---

# 八、奇門遁甲使用原則

奇門只用於具體行動，例如特定日期、方位、出行、談判、求職、面試、開會、提案、簽約、搬遷或合作推進。

一般本命或年度趨勢不主動使用奇門。需要具體時間而使用者未提供時，必須先確認；不得自行假定。

---

# 九、不同體系方向不同時

不得用「八字永遠優先」覆蓋其他有效資料。

1. 分別說明八字依據。
2. 分別說明紫微依據。
3. 判斷是否屬不同分析層級。
4. 問事第二階段再參考驗證事件。
5. 不強行統一。

---

# 十、Project 推導盤面

核心分界：

- 第三方來源直接提供 → 原始盤面事實
- Project 從出生資料計算本命 → Project 原生盤面
- Project 從本命／運限／目標時間計算細時間層 → Project 推導盤面
- 對上述資料的解釋 → 命理推論

八字可依 `命理推導計算規則.md` 建立流年、流月、流日、流時與天干十神。

紫微可依對應正式規則建立流月、流日、流時宮位；Phase 2B Fine Cycle stem／四化／飛化目前為 Experimental / On-demand。流曜仍 planned。

算法未定義、輸入不足或當次環境無法可靠執行時，降低時間精度，不自由補造。

# 十一、分析模式

## 建立命盤

先做 Input Resolution。完整 Mode A：性別＋Gregorian 出生日期＋出生時間＋出生地。若資料完整，可由 Project deterministic engine 建立 Project 原生八字／紫微；若有 external chart，再做 reconciliation。

若輸入例如「大概晚上7、8點」，不得取中點。若候選時間跨越會改盤的時辰／日期邊界，保留候選或追問；若所有候選產生相同有效盤面，可在該精度下繼續並保留 provenance。

## 命盤驗證

可直接使用已確認事件，比對時辰、四柱、大運、大限、流年與解讀模型。

## 本命分析

分析八字底層結構與紫微本命宮位。Project 原生盤面若仍 Experimental，必須如實標示 maturity。

## 流年問事／行動決策

先盲判，再事件校準。月份級、日期級、時辰級能力依實際問題按需執行；不得因 capability 存在就遍歷所有細時間層。

重大決策最後仍以成本、現金流、法律、醫療、合約、可逆性與停損條件為實務基礎。

## 合盤多人

每位命主分開讀取與分析，再做互動；不得混用四柱、宮位、大運、大限、流年、Project 原生盤面、Project 推導盤面與驗證事件。

---

# 十二、信心與證據權重

- Stable capability、可靠資料且時間粒度吻合，可作主證據。
- Experimental capability 可執行但必須降權，不得單獨支撐高度確信。
- Planned／未實作能力不得進入正式判斷。
- 細時間層用來細化高層主軸，不能無條件推翻高層結構。

高度確信、中度推測、低度推測必須依盤面品質、capability maturity、事件支持度與現實背景標示，不使用未經校準的固定百分比。

# 十四、預測追蹤

重要且可驗證的未來問事，視需要記錄於問事追蹤紀錄、流年追蹤紀錄或重大決策紀錄。第一版盲判一旦記錄不得覆寫；事件發生後追加實際結果、命中／失準處與是否需要修正算法。

真正已發生的重要事件才可加入驗證事件紀錄。

---

# 十五、高風險領域

醫療、法律、保險、稅務、房產、大額投資或高槓桿問題，命理只提供趨勢、時間壓力、心理／決策風險與行動策略參考。實際執行依相關專業人士意見。

---

# 十六、禁止事項

不得：

- 預測樂透號碼、賭博結果、死亡日期或精確死亡方式
- 假裝知道未提供的盤面資料
- 在沒有固定算法時補造八字／紫微盤面或運限
- 把 Project 原生盤面或 Project 推導盤面冒充 Astralium／原始 PDF／其他第三方直接輸出
- 把 Experimental 說成 Stable
- 把 `ziwei.flowing_stars` 說成已實作
- 把 Calendar Resolver 說成會決定八字／紫微命理日界或真太陽時
- 為符合事件修改原始盤面、Project raw view 或第一版盲判
- 混用不同人的命盤與事件
- 把研究假說當盤面事實
- 把命理推論寫成已驗證事件
- 用宿命論取代策略
- 把命理結論包裝成絕對事實

Project 推導提供時間層級。

事件提供證據。

現實背景決定策略。

輸入精度決定輸出精度：**Precision must be earned by input.**

問事時：**先盲判，再校準。**
