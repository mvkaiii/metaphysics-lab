# 紫微流日推導規則

- 文件版本：v1.0-exp
- 生效日期：2026-08-20
- 引擎：Metaphysics Lab 紫微流日定位引擎 v1.0.0-exp
- 程式實作：`engine/ziwei/day.py`
- Capability：`ziwei.flow_day_palaces`
- 狀態：`implemented / experimental / on_demand`

## 一、定位

本文件規範 Metaphysics Lab 的「紫微流日定位」Project 推導。

流日能力已具備正式 Python 實作，可以在需要細看指定日期、比較候選日期或補充跨系統時間證據時調用；但**不預設在一般年度或月份問事執行**。

目前流日只包含：

- 流日命宮定位
- 流日十二宮重排

本版不包含：

- 流日四化
- 流日流曜
- 細層飛化
- Cross-System Validation 正式引擎

上述能力另由後續 capability PR 實作與驗證，不得因流日定位已可執行就自行補造。

## 二、固定流日算法

本 Project 採以下流日定位法：

1. 先依 `core/紫微流月推導規則.md` 算出目標日期所在的流月命宮。
2. 以該流月命宮作為農曆初一的流日命宮。
3. 每增加一個農曆日，流日命宮沿地支順行一宮。
4. 十二宮循環，十三日回到與初一相同的流日命宮位置。

索引地支順序：

`子、丑、寅、卯、辰、巳、午、未、申、酉、戌、亥`

公式：

```text
flow_day_index = (flow_month_index + lunar_day - 1) mod 12
```

其中 `flow_month_index` 是目標日期經 Project 流月規則解析後的流月命宮地支索引。

## 三、流日十二宮

流日命宮確定後，十二宮依固定順序重排：

`命宮 → 兄弟宮 → 夫妻宮 → 子女宮 → 財帛宮 → 疾厄宮 → 遷移宮 → 交友宮 → 官祿宮 → 田宅宮 → 福德宮 → 父母宮`

配置方式與流月共用同一個 `palaces_from_ming_branch()` helper，避免 month/day 各自維護不同的宮位方向。

## 四、月份與日期邊界

本流日引擎不負責國曆轉農曆。

輸入的 `lunar_month`、`lunar_day`、`is_leap_month` 必須由可信曆法來源先行確認。

流日定位的日界在本模組中等同於「上游已確認的農曆日」。因此本版不另外宣稱紫微子初換日、晚子時換日或民用午夜換日規則；若未來 router 直接接受國曆時刻，必須另外固定並版本化國曆→農曆與換日口徑。

## 五、閏月處理

Metaphysics Lab 先沿用既有流月規則：

- 閏月初一至十五：流月位置歸原月。
- 閏月十六起：流月位置切到下一有效月。

流日再依**實際農曆日數**推進：

```text
flow_day_index = resolved_flow_month_index + lunar_day - 1
```

因此閏月十六日不會把日數重置成「有效下一月初一」。

這個運算順序與 iztro 現行運限實作一致：先依閏月後半調整 `monthlyIndex`，再以 `lunarDay - 1` 形成 `dailyIndex`。

但古典/一般排法資料多只明示「流月宮起初一，一日一宮」，對「閏月拆半後日數是否重置」未必有一致公開說明。故此項目前視為 **Project-specific Experimental convention**，必須保留版本與後續 issue 校驗空間。

## 六、Capability 狀態

`ziwei.flow_day_palaces`：

```text
implementation = implemented
maturity = experimental
routing = on_demand
rule_version = 1.0-exp
```

含義：

- `implemented`：Python 已有固定可執行算法。
- `experimental`：已完成最低規則與來源交叉驗證，但仍需更多年份、閏月、邊界與實際問事追蹤才能升 Stable。
- `on_demand`：能力存在且可執行，但一般年度/月度問事不預設執行。

Experimental 流日可參與分析與跨系統比較，但必須降權，不得單獨支撐「高度確信」。

## 七、輸入

正式輸入至少需要：

- 出生農曆月 1–12
- 出生時辰地支
- 目標流年地支
- 目標農曆月 1–12
- 目標農曆日 1–30
- 是否為閏月

輸入不足時不自行猜測農曆日期或時辰。

## 八、結構化輸出

引擎至少輸出：

- `classification = Project 推導盤面`
- `scope = 紫微流日`
- 規則名稱與引擎版本
- capability implementation / maturity / routing
- 原始輸入回顯
- effective lunar month
- flow month Life Palace
- flow day Life Palace
- flow day 12-palace mapping
- leap-month note
- 未實作的更細 capability 狀態

不得將此輸出寫成 Astralium 或其他第三方排盤系統的直接結果。

## 九、外部來源交叉驗證

### Source A：iztro 公開安星訣

iztro 的公開《紫微斗數安星訣》在「定流日」中採：由流月所在宮起初一，順行十二宮，一日一宮。

- https://www.iztro.com/zh_TW/learn/setup

### Source A2：iztro 程式實作（固定版本）

Metaphysics Lab 本版交叉驗證固定參考 iztro commit：

`814b77e6371e1050cac31bbf674db3c3138fcfde`（2026-08-19）

該版本 `FunctionalAstrolabe.ts` 的運限程式以：

```text
dailyIndex = fixIndex(monthlyIndex + lunarDay - 1)
```

計算流日索引，與本 Project 一般月份的流日公式一致；其閏月處理也是先調整 monthly index，再套用實際 lunar day offset。

- https://github.com/SylarLong/iztro/blob/814b77e6371e1050cac31bbf674db3c3138fcfde/src/astro/FunctionalAstrolabe.ts

固定 commit 的目的，是避免上游 `main` 日後改動造成 Project 驗證依據無法重現。

### Source B：易象乾坤公開排盤步驟

公開排盤步驟亦記載：流日以流月所在宮起初一，順行十二宮，一日一宮，到月底最後一天止。

- https://www.yixiangqiankun.com/zh-tw/26472.htm

此來源視為公開二級排法資料，用於交叉印證，不單獨作為 Stable 的充分依據。

### Source C：DestinyNet 討論中的書籍引述

DestinyNet 舊討論中引述慧心齋主著作，同樣記錄「流月命宮為該月初一之命宮，順時間而行」的流日定位法。

- https://destiny.to/ubbthreads/topic/102283

此來源屬書籍內容的二手引述；可作方法來源佐證，但若未來要升 Stable，仍應盡量補入可直接核對的原始書籍版本或另一套可重現排盤輸出。

以上只能支持「本 Project 選定的流日定位法有多個公開來源相互印證」，**不代表所有紫微流派都採完全相同的細運規則**。

## 十、最低驗證結果

目前已確認：

- 初一停在流月命宮。
- 初二順行一宮。
- 十三日循環回初一位置。
- 一般月份公式與固定 iztro 參考版本一致。
- 閏月後半的運算順序與固定 iztro 參考版本一致。
- 非法農曆日與非法地支會拒絕輸入。
- 流日十二宮重排與流月共用同一宮位 helper。

因閏月細節與不同流派的公開驗證仍有限，本 capability 第一版維持 Experimental，不提前升 Stable。

## 十一、On-demand 調用條件

建議在下列情況才調用流日：

- 使用者明確指定某一天。
- 比較兩個以上候選日期。
- 月份主軸已確定，需要提高到日期解析度。
- 八字與紫微較高層訊號衝突，需要補充日期層證據。
- 重大行動需要精細時間比較，但尚未進一步要求流時／奇門。

一般本命、年度或月份分析不因流日能力存在就自動遍歷整月所有日期。

## 十二、升 Stable 條件

至少需要再累積：

- 更多年份與不同流年地支案例
- 閏月前後半與月底案例
- 不同可信排盤來源輸出比較
- router 實際調用測試
- 問事追蹤與已發生事件回顧
- GitHub Issues 中可重現的差異案例

升級必須更新規則版本、測試與 CHANGELOG，不得因單一事件吻合直接升級。
